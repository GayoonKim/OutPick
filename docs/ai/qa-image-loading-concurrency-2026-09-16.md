# 이미지 로딩 단계별 동시성 — 구현 및 검증

2026-09-16 사용자와 Phase 0~5를 순차 진행하고 현재 설정을 채택했다. 이번 범위는 공용 이미지 파이프라인, 룩북 홈·브랜드 시즌 목록·시즌 포스트 목록, 관련 소비자 회귀다.

## 최종 구조와 설정

- 메모리 캐시는 즉시 조회한다. 디스크 읽기와 이미지 준비, 네트워크 다운로드, 비동기 디스크 저장은 서로 다른 제한을 사용한다.
- 공용 네트워크 6, 디코딩 2, 디스크 I/O 2(동시 쓰기 1). 압축 데이터 디코딩/저장 대기 예산은 각각 16MiB다. 큰 요청은 제한된 임시 파일 경로로 처리한다.
- 동일 경로·다운로드 제한의 요청은 합류한다. 소비자별 취소, 마지막 소비자 취소 시 작업 취소, 캐시 무효화 세대로 늦은 결과의 재저장을 차단한다.
- 외부 URL 대체 이미지도 공용 네트워크 예산과 메모리·디스크 캐시를 사용한다. HTTP 유효기간, ETag/Last-Modified, 304, no-cache/no-store 및 일시/영구 오류를 처리한다.
- 목록 데이터가 준비되면 먼저 공개하고 개별 이미지를 채운다. 프리패치는 진행 방향 1.5화면·반대 방향 0.5화면, 최대 24장, 이탈 취소 유예 300ms를 사용한다. 실패 이미지 재시도와 카드 상세 이동은 분리한다.

## 자동·수동 검증

- Phase 5 집중 테스트 64개와 관련 소비자 26개, 실패 이미지 재시도 UI 테스트 1개 통과.
- iPhone 14, OutPick-DEV, 아모멘토 `2026 Spring-Summer Collection`에서 최초 진입·하향 스크롤·빠른 왕복·재진입, 브랜드/시즌 좋아요·포스트 상세·공유 확인. 첫 다운로드 중 일시적인 로딩 표시 후 이미지가 채워지며, 이후 빈 이미지가 남지 않았다.
- 머지 전 리뷰에서 HTTP 디스크 본문을 바이트 예약 전에 읽는 경로를 발견했다. 디스크 크기 확인 → 용량 예약 → 본문 읽기 → 디코딩 순서로 수정했다. 예약 대기 중 파일 제거를 제어하는 회귀 테스트가 기존 코드에서 실패하는 것을 확인했고, 수정 후 최종 **91개/14 suite 전체 통과**를 확인했다(Development Simulator, 2026-09-16). 기존 UI1개 결과도 유지한다.
- 주요 테스트: `ImageLoadCoordinatorTests`, `ImageCacheRevisionTests`, `ImagePipelineResourcesTests`, `LookbookHTTPImageCacheTests`, `LookbookViewportPrefetchTests`, 룩북 ViewModel 테스트, `LookbookSmokeUITests.testImageRetryDoesNotOpenCardDetail`.

## 같은 시즌의 스크롤 통합 계측

Instruments의 Animation Hitches와 Activity Monitor를 함께 사용했다. 각 앱의 시즌 화면 준비를 확인한 뒤 기록을 시작하고, 하향 스크롤·빠른 상하 왕복 3회 완료 응답 직후 종료했다.

| 지표 | Phase 0 | 최신 Phase 5 |
|---|---:|---:|
| 기록 길이 / 앱 Activity 표본 | 41.22초 / 40개 | 38.85초 / 38개 |
| CPU 최대 / p95 | 42.41% / 40.68% | 43.54% / 42.23% |
| 물리 footprint 최대 | 77.77MiB | 77.19MiB |
| Real Mem 최대 | 160.19MiB | 124.36MiB |
| OutPick에 연결된 hitch | 1건·16.67ms | 0건 |
| 브랜드 시즌 목록 데이터 공개 | 692.6ms | 79.1ms |
| 시즌 포스트 목록 데이터 공개 | 89.5ms | 53.3ms |

최신 앱이 다운로드한 브랜드·시즌 이미지 42건(1,152,606B)은 Phase 0의 이미지 키와 본문 크기가 전부 일치했다. Phase 0에는 홈 이미지 2건이 더 포함됐다. 최신 앱에는 홈 캐시가 남아 있어 전체 실행이 완전히 동일한 cold 조건은 아니다.

이전 별도 비교에서도 목록 공개는 홈 912→48ms, 브랜드 612→89ms, 시즌 97→69ms였다. CPU 최대는 47.78→47.56%, footprint 최대는 78.84→77.45MiB였으나 그 기록은 정확한 스크롤 구간과 정렬되지 않았다.

## 채택 근거와 한계

기능 QA와 자원 제한 검증, 위 비교 결과를 근거로 사용자가 현재값 채택과 Phase 5 완료를 승인했다. 추가 튜닝 필요성을 보여주는 뚜렷한 근거는 발견하지 못했다. 소수 표본·수동 스크롤 속도·대기 시간·홈 캐시 차이 때문에 통계적 우월성이나 모든 기기의 최적값을 주장하지 않는다. 목록 데이터 공개 시점은 첫 픽셀이 아니며 성공 이미지 본문 바이트는 전체 회선 사용량이 아니다. 마지막 HTTP 예약 순서 수정은 자동 회귀로 검증하며 위 기기 수치는 수정 직전 빌드의 결과다.

채팅 과거 사진의 첫 표시 지연과 화면 근처 썸네일 선로딩은 별도 후속 작업이다. 원본/GIF 직접 경로와 관리자 외부 URL 미리보기의 모든 정책을 이번 룩북 HTTP 캐시로 통합하지 않았다. 서버 코드·스키마·Production 배포 변경은 없다.

상세 계측 로그와 phase별 논의는 로컬 `docs/ai/tasks/image-loading-stage-concurrency/` 하네스에서 관리한다. 해당 로컬 문서·기기 로그·토큰은 이 공개 검증 요약에 포함하지 않는다.
