# 브랜드 순차·내부 병렬 — 구현·검증·20회 비교 결과

2026-10-04(KST). [승인된 설계·계획](phase-3-brand-fifo-design.md)의 구현, Mac/Linux 필수 게이트, 고정20회 실측, 독립 재집계와 컨테이너 정리를 완료했다.

**브랜드 순차·내부 병렬은 이번 대용량 입력에서 속도를 거의 유지하며 메모리와 원본 읽기량을 줄였다.** 전체 시간 10% 개선 목표는 달성하지 못했다. 현재 자원 제약을 유지하는 후속 후보로 추천하며, 제품 최종 채택이나 실제 분산 순서 보장 완료로 해석하지 않는다.

## 자원·실험 범위

현재 배포 인스턴스당1CPU/2GiB와 같은 로컬 한도를 유지했다. 클라우드 min/max인스턴스·요청동시성·배포·Firebase 데이터는 변경하지 않았다. 사용자 설명의 현재 추가 요금 없음은 제약으로 유지하되 청구내역/무료잔여량은 미조회다. 설정만으로 추가 요금0을 보장하지 않는다.

두 구조 모두 P4(시즌마다 미완료 이미지4개), 공유 다운로드4/변환1/업로드4/경로 저장 무제한, 재사용128MiB, 커버 선준비다. 차이는 여러 브랜드를 함께 시작하는 P와 브랜드 하나씩 시작하는 S다. S에서도 활성 브랜드의 두 시즌은 함께 실행한다.

일반/대용량 각각 UNAFFECTED 자료의 합성3브랜드×2시즌을 두 구조로5회씩, 총20회 실행했다. 매 회차 새 Linux ARM64 컨테이너, 네트워크 차단, 읽기전용 입력 volume, 추가swap 없음이다. 실제 sharp와 대체 Storage/경로 저장을 사용했다. 파일 무결성 사전 검사 뒤 측정하며 cold-cache라고 표시하지 않는다. 브랜드 전환마다 프로세스를 재시작하거나 강제GC·예산 초기화를 하지 않았다.

## 구현과 코드 진입점

- `performance/season-runner.ts::runSeasons`: `serial-brands` 추가. 브랜드 최초 등장 FIFO, 내부 시즌 병렬, 저장/review/최종실패·형제 정리 후 전환, 최초 포함5회 재시도 동안 차례 유지. 기존 parallel/serial-per-brand 의미는 보존했다.
- `brand-comparison.ts`: 엄격20회 계획,3×2입력 매핑, 새 input/settings digest.
- `brand-metrics.ts`: 첫 등록 브랜드 기준, 대기/입장/정리/성공 완료 시각. review/실패의 release를 성공 완료로 바꾸지 않는다.
- `brand-statistics.ts`/`brand-report.ts`: 전체/첫 시즌/첫 브랜드/각 브랜드5쌍 판정, 실패·중단·미수행 분모와 중복·다른 이미지 거절.
- `brand-progress.ts`: 실행 중 최소 경계 JSONL,256KiB 상한, 순서/backpressure, 출력 실패 시 신규 작업 중단. OOM 직전까지의 기록을 보장한다고 가정하지 않는다.
- `reuse-comparison.ts`/`reuse-entry.ts`: 새 marker에만 연결. `container-runner.ts`는 증거 상한/출력 실패를 실패로 보존한다.
- `brand-scheduling.test.ts`6개, `brand-comparison.test.ts`6개, `brand-fixture.ts`: BF01~12. 실제 작은 JPEG 검사는 집계용 가짜 사건과 구분한다.

UI·앱 DI·제품API·Firestore schema·분산 대기열은 이번에 변경하지 않았다.

## 다음 권고와 미검증 범위

**현재 자원에서 메모리 경쟁과 원본 재다운로드를 줄이는 후속 후보로 S(브랜드 순차·내부 병렬)를 추천한다.** 속도10% 목표 달성이나 최종 최적값 확정으로 처리하지 않는다. 기존 합의처럼 시간 차이가 작을 때 자원·복잡도·실제 비용을 함께 검토한다.

다음 핵심 작업은 제품의 브랜드 입장/대기열·시즌 job claim·최초 포함5회·lease 복구를 연결하는 세부 설계다. 현재 실제CloudRun은 요청동시성2·복수인스턴스가 가능하므로 이 프로세스 내부 큐만으로 전역 FIFO를 보장할 수 없다. 대기 작업이 HTTP 슬롯을 점유하지 않으면서 저장/review/최종실패와 실행 중 정리를 마친 뒤 다음 브랜드로 넘어가는 경계를 설계해야 한다.

브랜드 하나에 큰 시즌6개가 몰리는 경우는 이번3×2브랜드 비교로 해결됐다고 볼 수 없다. 실제 URL·Storage·Firestore/OIDC·재시도/분산 복구와 네트워크 대역폭/실패율, Development 비용 검증은 여전히 별도다. 현재 CPU/메모리 증설 없이 다음 설계를 진행하고, Development 실행안은 합의된 비용·시간·요청량 범위로 구체화한다.
