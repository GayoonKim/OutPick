# 후속 부하·보관 예산 압박 검증안

2026-10-03. 사용자는 두 방식의 차이를 확인한 뒤 **기존 입력·작은 예산부터 총45회** 추천안을 승인했다. 아래 추천안을 확정해 구현·필수 게이트·실측·결과 기록을 진행한다. 대용량 입력과 Development 원격 실행은 별도 후속이다. 이전 [커버 선준비 15회](phase-3-cover-preparation.md)의 표본·원본은 보존한다.

## 목적과 고정 조건

- 커버 선준비 + 같은 실행 원본 재사용 후보가 단일 시즌과 합성3브랜드에서 정합성·종료 지연을 유지하는지 확인한다.
- 공용 보관 예산 부족 시 기다리지 않고 다시 읽는 fallback, 본문 cache hit/miss 혼합 시 제출 순서, 종료/실패/취소의 scope·슬롯·바이트 반환을 확인한다.
- 1CPU/2GiB/swap·네트워크 없음, 새 고정 Linux ARM64 이미지·회차별 새 컨테이너, 기존 입력 SHA·JPEG golden, 다운로드4/변환1/업로드4/경로 제한 없음, 시즌 병렬 최대6을 유지한다.
- 메모리100ms 표본/간격500ms 초과 미검증 중단/85% 1초 중단, 전체·첫 입력 시즌의5쌍 반복 악화식과 실패 분모 보존을 유지한다. 이전 표본을 새 코드의5쌍에 섞지 않는다.
- prepared의 커버는 항상1회 선준비한다. cache miss 본문은 다운로드가 필요하므로 모든 본문·커버 변환 제출의 연속성이나 특정 완료 순서를 정답으로 요구하지 않는다. actual trace로 그 영향을 분석한다.

## 1. 다른 부하 확인 제안 — 20회

기존 `comparisonInputs(single/synthetic-three)`를 사용한다. 단일2026SS, 연도별 합성3브랜드에 FW/SS 각2시즌을 두고, 각 부하에서 off/커버 선준비+256MiB를5쌍 비교한다. 두 조건 순서와 부하 순서는 반복마다 교차한다.

단일은 후보30개/본문30개+커버1개다. 합성3브랜드는 기존6시즌과 이미지·job 수가 같고 brandID만 다르다. 현재 C 경로는 브랜드별 제한을 사용하지 않으므로 합성3브랜드는 분류가 달라도 계약을 유지하는지 확인하는 용도다. 실제 여러 브랜드 사이트의 네트워크 차이나 새로운 총 부하를 검증했다고 표시하지 않는다.

## 2. 확정한 압박 방식

### 추천: 같은 입력에 작은 보관 예산부터 — 추가25회

기존6시즌에서 off/선준비16MiB/32MiB/64MiB/128MiB를 각5회, 총25회로 제안한다. 다섯 조건 순서를 반복마다 회전한다. off는 기존 비재사용 동작, 재사용 조건은 모두 커버 선준비다. off 대조는 후보 전체 구성의 효과이고, 재사용 후보끼리는 예산만 다른 비교다.

현재 원본 보관 peak는111,028,402바이트(약105.89MiB), 2026FW 후보 원본 합계는51,079,588바이트다. 16/32/64MiB로 예산 부족을 유도하고128MiB를 비압박 대조로 둔다. 실제 `rejectedByBudget`, cache miss, 재다운로드를 확인해야 압박이 성립했다고 판단한다. 예산보다 작게 보관하는데 해당 회차에서 거절이 없었다면 압박 성공으로 처리하지 않는다. miss 수는 실행 순서에 따라 달라질 수 있어 사전에 임의의 고정값을 정답으로 두지 않는다.

장점: 이미 검증한 원본·JPEG golden을 유지하고 예산이라는 한 축을 바꿀 수 있다. 새로운 원격 요청·합성 이미지 생성이 필요 없다. 단점: 128/256/512MiB를 실제로 넘는 대용량 입력 검증은 별도로 남으며, 이 결과로 그 세 수치 중 운영 최적값을 확정할 수 없다.

총 로컬45회(20+25)다. 기존1시즌 약2초·6시즌 약38초를 근거로 순수 처리 약23분을 예상한다. 준비·게이트·이미지 빌드 시간은 별도이며 예상값은 새 실측 결과가 아니다. 클라우드 비용은 발생시키지 않는다.

### 대안: 대용량 입력부터 설계

128/256/512MiB 경계를 실제로 넘도록 원본/시즌 조합을 확장한다. 장점은 원래 예산 후보의 차이를 직접 확인할 수 있다는 것이다. 단점은 현재 자료로는 부족해 추가 실제 URL 또는 합성 job/이미지 조합과 유지 수명을 결정해야 하며, 총 작업량·메모리·변환량이 함께 달라진다는 점이다. 동일 이미지를 같은 시즌에서 단순 복제하면 해시 중복 제거로 사라지므로 유효한 압박 입력이 되지 않는다. 이 대안의 구체적인 입력/회차는 아직 미확정이며45회안에 임의로 더하지 않는다.

## 구현·검증 계획

1. 새 실험 식별자와 행렬을 추가하고 기존15회/2회 계획의 검증 계약을 보존한다. 변경 후보는 `performance/reuse-comparison.ts`, `reuse-entry.ts`, `reuse-trace.ts`, 필요 시 별도 부하 계약 모듈이다.
2. trace 검증의 현재137자산/6시즌 고정을 입력 계약으로 바꾸되, 허용하지 않은 시즌/대상 누락·중복은 계속 거절한다. `reuse-input.ts`는 기존 입력 executor를 재사용한다.
3. 입력 manifest/golden에서 기대 대상·파일·바이트를 산출한다. 압박 조건의 cache hit/miss와 trace 재사용 표식을 교차 확인하고, 해시용 읽기+miss 본문+커버1회의 실제 읽기 횟수·바이트를 대조한다. 모든 출력 SHA/규격 검사는 유지한다.
4. 필요한 자동 테스트: 단일/합성 입력 계약, 예산별 엄격한 행렬, hit/miss 혼합의 실제 JPEG·읽기/준비 경계·취소/실패 정리, 잘못된 cache 통계/trace/바이트 거절, 중단·누락 포함5쌍 판정. `test-design-workflow`를 적용하며 fake transport/저장소와 실제 sharp를 사용한다.
5. Mac/Linux 필수 게이트에 새 테스트 ID를 연결하고 둘 다 통과한 고정 이미지로 실행한다. 모든 manifest/원본/분석·실패/중단·미수행을 저장한다. raw 자원 시계열 전체를 수집했다고 표현하지 않고 실제 저장한 자원 통계/단계 trace 범위를 명시한다.
6. ENTRYPOINTS/LOOKBOOK/TESTS와 본 task에 코드·검증·원본·한계를 갱신한다. 제품 API/DI/Firestore/기본값 변화는 없다. 실제 관리자 화면과 원격 연동은 이 로컬 게이트가 검증하지 않는다.

16/32/64MiB는 각각5/5회에서 보관 거절·본문 cache miss·재다운로드가 발생해 **압박 성립**을 확인했다. 본문 hit/miss는 각각21/110,25/106,67/64이고, 커버는 매번6개 선준비였다. 보관 거절은 중복 후보까지 포함해111/107/65건이다. 읽기 횟수는248/244/202회다. 32MiB는 같은 hit 수여도 선택된 이미지 차이로 읽기 바이트가190,285,976 또는190,269,087로 달랐다. 원본별 trace로 바이트를 대조했으며 횟수만으로 같다고 처리하지 않았다. 128MiB는 hit131/miss0/거절0으로 비압박 대조다.

- **16MiB·32MiB: 채택 보류.** 첫 시즌10% 이상 느린 쌍이 각각3/5이고 중앙값도10% 이상 악화해 합의한 판정식에 해당한다. 16MiB5회차는+10.0299%로 임계에 매우 가깝다. 판정식은 그대로 적용하되,5회 표본만으로 모든 입력에서의 성능 열위를 일반화하지 않는다.
- **64MiB: 보류식에는 미해당, 개선 확정도 아님.** 첫 시즌 중앙값+10.63%지만 해당 쌍은2/5여서3회 요건을 충족하지 않는다. 이 결과를 ‘악화가 전혀 없다’ 또는 ‘최적값’으로 해석하지 않는다.
- **128MiB: 이 입력의 후속 후보 유지.** 첫 시즌10% 악화0/5, 전체는 off 대비1.07% 단축이다. 전체10% 개선에는 미달하며 대용량/128·256·512MiB 최적값을 검증한 것은 아니다.
- 전체 완료 시간에는 어느 예산도10% 이상 느린 쌍이 없었다. 재사용128MiB를 기준으로 같은 반복을 보조 비교해도16/32MiB의 첫 시즌 보류식이 성립했다(각4/5).64MiB는2/5다. 원본 `budgetRegressions`에 보존했다.

### 지연 양상 — 기존 trace의 읽기 전용 분석

16/32MiB의 첫 시즌에서 마지막에 완료된 본문은5회 모두 `post-23`이며 cache miss였다. 첫 본문 제출부터 마지막 본문 제출 사이에 다른 시즌 변환이16MiB에서44~52건,32MiB에서34~52건 끼었다. off에서는2~10건이었다. 비교는 단조 trace 시각을 사용하며 다운로드 준비/등록/실행을 구별한다.

32MiB1회차에서 마지막 본문 원본은0.333초에 준비되고0.334초에 변환 제출됐지만17.001초에야 변환을 시작해17.444초에 끝났다. 커버는9.878초에 이미 끝났으므로 이번 시즌 지연은 커버 완료 대기가 아니다. cache hit 본문/준비 커버가 먼저 등록되는 동안 다운로드가 필요한 본문이 뒤에 등록되고, 다른 시즌 작업이 사이에 들어온 큐 순서가 직접 관측됐다. 대기 시간 차이 전부를 단일 요인의 인과 효과로 분리한 실험은 아니다.

64MiB에서는 첫 시즌 본문이 모두 재사용됐고 본문 제출 사이 끼어듦이0건이었다. 대신 느린1/3/4회차에서2026SS의 변환62건이2026FW보다 먼저 큐에 있었으며2/5회차는0건이었다.128MiB도3회차에 같은62건이 먼저 있었지만 나머지4회차는0건이다. 이 경우는 부분 재사용으로 본문이 갈라진 경우와 구별한다. 시즌 준비 순서를 고정하는 정책은 이번에 추가하지 않았다.

메모리 최고치의 변동 원인은 이번 통계만으로 확정하지 않았다. 작은 예산이 cache 보관량을 줄이는 것은 확인했지만, fallback 입력·변환 native 메모리 등을 포함한 컨테이너 최고치를 항상 낮춘다는 보장은 없었다.

## 판정과 다음 권고

승인한45회 구현·필수 검증·실측·원본 기록은 완료했다. 다른 부하에서 선준비 후보의 큰 지연은 재현되지 않았지만, 압박 시 **부분 재사용과 재다운로드가 섞이는 제출 순서 문제**가 남았다. 따라서 바로 제품 적용이나 Development 부하 실행으로 넘어가는 것을 추천하지 않는다.

다음 권고는 기존 trace를 근거로 부분 재사용 시 시즌별 이미지 묶음/실행 폭/공용 큐 순서를 어떻게 조정할지 세부 설계하는 것이다. 전체 원본을 무조건 더 보관하는 방식은 메모리 예산 취지와 충돌할 수 있으므로 대안의 메모리·완료 순서·복잡도를 비교한다. 실제 정책 변경과 새 비교 회차는 사용자와 구체화한 뒤 진행한다. 그다음128/256/512MiB를 넘는 대용량 입력 확인과 Development 실제 URL·Storage·Firestore 검증을 이어간다. 제품 기본값·영구 캐시·원격 배포는 아직 변경하지 않았다.
