## 목표와 승인 경계

현재 제한값을 그대로 높이는 대신, 동일 입력에서 시즌 스케줄링·이미지 묶음·단계별 동시성·다운로드 재사용의 효과를 분리한다. 정확성과 실패율을 유지하며 전체 완료 중앙값 10% 이상 개선을 우선한다. 수치가 작은 CPU 변환이 병목인지, 업로드 대기와 바이트 보관이 병목인지 계측으로 판단한다. 변환 전체 제출도 비교하지만 CPU 처리량 증가를 미리 보장하지 않는다.

현재 저장물은 썸네일과 상세용 JPEG다. 다운로드한 원본 파일 그대로를 별도로 보관하는 기능을 이번 범위에 추가하지 않는다. 후보 추출·해시 검증·품질 판단이 끝나야 등록을 진행하는 기존 계약을 유지한다.

사용자의 추천 순서 진행 승인에 따라 로컬 구현·필수 검사를 진행한다. UNAFFECTED 실제 추출/검토와 승인 후 저장을 분리하고, 실행 내 재사용은 별도 로컬 연결 실험으로 비교하는 범위도 확정했다. 클라우드 후보 배포와 유료 실험은 대상·입력 manifest·예상 요청량·격리 설정을 갖춘 실행안을 제시한 뒤 진행한다. 최종 제품 기본값 변경과 운영 배포는 측정 결과 검토 후 별도 범위다. 모델은 사용자가 직접 선택하며 현재 설정을 임의로 단정하지 않는다.

Worker 경로는 모두 `tools/lookbook-import-worker/` 기준이다. 추상화는 실행 정책·공용 자원·자료 소유권에 필요한 경계로 한정한다. 이미지 한 장의 두 출력 수를 늘리지 않는다. 파일 업로드 동시성은 여러 이미지의 파일을 합산한 값으로 비교한다. 해시는 동기 CPU 작업이므로 다운로드와 시간을 분리해 계측하되, 초기부터 별도 Worker Thread를 도입하지 않는다.

서버 DI는 `index.ts`에서 공용 자원·정책을 만들고 `server.ts`를 통해 요청 processor에 전달하는 안이다. 앱 Container·Coordinator 변경은 없다. Firestore·Cloud Tasks 계약을 건드리는 단계와 공용 processor 변경은 순차 진행한다. 다음 phase 시작 전에 변경 파일·의존성·계약 충돌을 다시 확인한다.

## Phase 0 — 계측·기준선·필수 게이트 연결

- 목표: 현재 방식의 비용과 정확성을 재현할 측정 기반을 만든다.
- 변경 범위: 위 metrics/result, 기존 processor의 단계 경계, Worker 테스트 runner와 전용 게이트. 계측 비활성 시 기존 실행 정책을 유지한다.
- 입력: 사용자 지정 UNAFFECTED 목록을 우선 사용한다. 현재 2024~2026년 SS/FW 6개 시즌 정적 후보 합계 132개를 확인했고 단일 시즌은 2026 SS 30개 후보를 제안한다. 실제 이미지·순서·중복·크기·해상도·품질 분기를 확인한 뒤 manifest로 고정한다. 아직 정상 자동 등록 자료로 확정된 것은 아니다. 기존 Hatchingroom/Outstanding/YOUTH 조사와 다중 브랜드 실제 자료 확보는 별도 기록을 따른다.
- 계측: 단조 시계 단계 시간과 대기 시간, CPU/process memory, 컨테이너 memory, sharp 대기/실행, 수신·송신 bytes/requests, DB 호출, 실패/중단, 코드·입력 digest. 원본 이미지·URL query·인증값은 로그에서 제외한다.
- 완료 기준: 입력·설정·코드가 결과에 연결되고 성공/실패/중단 모두 보존된다. 제품 함수를 사용하는 기준선이 기존 후보·순서·품질·저장 경로 계약을 유지한다. 성능 실행기가 별도 모조 알고리즘만 측정하지 않는다.
- 검증: 계측 시간 순서, 누락 결과 거절, 입력 digest 불일치 거절, reporter 필수 ID 누락/skip/0개 차단, 기존 Worker 테스트·추출 fixture 회귀.
- 논의 필요: 고정 자료의 실제 정답·측정 분기와 실행 요청량. 자료 미확정이어도 합성 자료로 로컬 자동 검증은 가능하며, 실제 URL 정확성 검증 완료로 보고하지 않는다.

## Phase 1 — 묶음·단계 분리·전체 제출 비교 경로

- 목표: A/B/C/F와 D/E의 이미지 처리 부분을 같은 함수와 입력으로 비교한다.
- 변경 범위: policy/resources/asset-scheduler, processor와 dedupe의 정책 전달, config/index/server 조립. 기본 정책은 기존 A를 유지하고 실험 설정을 명시한 실행만 다른 경로를 사용한다.
- 흐름: 시즌 내부의 해시 후보 다운로드 묶음과 품질 통과 후 asset 묶음을 구분한다. 해시 검증 장벽을 없애지 않는다. 묶음 크기·묶음 내부 실행 폭을 따로 기록한다.
- 단계 분리: 다운로드 permit은 수신 종료 후, 변환 permit은 출력 생성 종료 후, 업로드 permit은 파일 요청 종료 후 반환한다. 다음 단계 대기 중 이전 단계 permit을 잡지 않는다. 입력·JPEG 출력 바이트의 소유권은 소비 완료까지 유지한다.
- 공용 범위: 다운로드·변환·업로드·DB의 제한은 인스턴스 전체에서 공유한다. 시즌별 묶음 제한과 공유 제한을 모두 기록한다. F는 앱 작업 수 제한 최소화이며 libuv/libvips/SDK pool 및 안전 감독기 한도를 별도 표시한다.
- 완료 기준: 여러 job 합산 실행 수가 설정을 지키고, 묶음은 소속 작업의 성공/실패 정리까지 기다린다. 한 업로드가 실패해도 형제 업로드가 살아 있는 동안 상위 작업을 완료로 처리하지 않는다. 두 파일 성공 이전 ready 저장을 금지한다.
- 검증: 결정적으로 멈출 수 있는 fake 다운로드·변환·Storage·Firestore와 barrier/spy로 슬롯 수, 공용 제한, 묶음 경계, 종료 대기, 교착·permit 누수, 오류 전파와 부분 재시도를 검사한다. 실제 sharp 출력 규격도 기존 정책과 대조한다.
- 논의 필요: 묶음 8/16/32/all, 다운로드 4/8/16/all, 변환 1/2/4/8/all, 업로드 4/8/16/all은 탐색 후보다. 초기 조합은 실행 전 manifest로 제시하며 최적값으로 확정하지 않는다. 중간 바이트 제한 유무도 설정 차이로 기록한다.

## Phase 2 — 같은 실행 안의 다운로드 재사용

- 목표: 해시에 사용한 바이트를 자동 등록·변환에서 재사용하는 효과를 독립 측정한다.
- 변경 범위: source-buffer-store, dedupe의 결과 전달, processor 실행 수명 연결. 별도 영구 저장소·TTL 작업은 추가하지 않는다.
- 계약: job 실행 식별과 canonical URL·요청 맥락으로 구분한다. 인스턴스 공용 예산은 다른 job의 보관량도 합산한다. 보관 슬롯을 기다리지 않으며 예산 초과는 miss다. 같은 원본을 커버와 포스트가 소비할 때 최종 소비 전 해제하지 않는다.
- 완료 기준: 재사용 bytes와 hash 입력이 같고, 오류 응답은 게시하지 않는다. 성공/실패/취소/검토 대기/실행 종료 시 참조가 정리된다. 새 실행과 review 승인 뒤 실행은 miss다. 캐시 보관 예산과 전체 RSS를 같은 값으로 취급하지 않는다.
- 검증: 예산 경계·다중 job 합산·중복 후보 제거·다중 소비자·늦은 완료·취소·재다운로드 경로·원본 변경을 자동 검증한다. 공개 URL은 성능 반복마다 재수집하지 않는다.
- 논의 필요: 구조 비교는 우선 재사용 off로 고정한다. 유력 구조에서 off/128/256/512MiB/all을 대조하고, 선택 조합을 결합 재검증한다. 이 추가 측정은 로컬 54회에 포함되지 않으므로 실행 전 회차를 산출해 제시한다.

## Phase 3 — 로컬 구조 비교와 수치 조정

- 목표: 54회 탐색으로 유력 구조를 좁히고 한 요소씩 조정한다.
- 변경 범위: performance manifest/runner/report, 로컬 fake transport와 실제 sharp 연결. 제품 Worker의 공개 URL 보안 검사를 우회하는 endpoint는 만들지 않는다.
- 실행: A~F의 입력·retry·CPU/메모리 조건을 맞춘다. D/E는 실행기에서 브랜드 내 시즌 순서를 제어한다. 한 시즌의 검토 대기·최종 실패 시 다음 시즌으로 넘어간다. 이 결과만으로 다중 인스턴스의 분산 순차 구현 완료를 선언하지 않는다.
- 공정성: 기준선 계측 on/off의 오버헤드를 점검한다. 실행 순서를 교차하고 준비 실행과 cold/warm을 분리한다. A 기존 retry 조건의 기록과 총 5회로 맞춘 구조 비교를 구분한다. 사람 검토 대기시간을 전체 자동 처리시간에 섞지 않는다.
- 조정: 다운로드→변환→업로드→DB 각 대기/실행/바이트 지표를 보고 한 축씩 비교한다. job 생성 10/20/all, 큐 6, 요청 2 조정은 이미지 내부 구조 비교와 별도 실험이다. 중복 확인은 현재 별도 5개 제한으로 확인되지 않았으므로 가상의 설정을 만들지 않는다.
- 완료 기준: 54회 각각 결과 또는 실패/중단 사유가 있고, 정확성 통과 후보만 순위를 낸다. 더 빠른 결과가 없으면 현재 방식 유지도 유효한 결론이다. 최적값을 전수 탐색했다고 주장하지 않는다.
- 검증: 결과 schema·횟수·정책·입력 일치·불완전 결과 차단·실패 분모·중앙값 계산을 프로그램 검사한다. 보고서는 단계별 병목·최대 동시성·메모리·bytes·원본 결과를 연결한다.
- 논의 필요: 54회 이후 추가 수치·재사용 대조 회차와 채택 후보를 결과에 따라 제안한다. 로컬 시간을 Cloud Run 예상 속도로 단정하지 않는다.

## Phase 4 — 실제 job 시도 계약·유력 후보의 분산 동작

- 순서 변경: 2026-10-04 사용자 선택에 따라 [Development 격리 비교 연결](development-comparison-plan.md)을 먼저 구현·검증하는 순서로 조정한다. 아래 제품 계약은 성능 결과 검토 후 확정한다.
- 목표: 실험용 순서 제어와 실제 Cloud Tasks/Firestore 상태 전이의 차이를 해소한다.
- 의존성: Phase 3 결과와 아래 계약 검토 완료. processor·Functions·데이터 계약을 순차 변경한다.
- 변경 범위: claim/lease, 실제 실행 횟수, dispatch generation, queue retry 계약과 테스트. 후속 S 브랜드 순차 후보를 대상으로 [실제 접수·실행·복구 설계](phase-4-brand-dispatch-design.md)를 구체화한다. S는 로컬 자원 개선 후보이며 최종 제품 채택은 미확정이다.
- 확정 사항: 실제 job 자동 실행은 최초 포함 총 5회. 중복 전달·stale task·claim 거절·브랜드 차례 대기는 실행 횟수를 소비하지 않는다. transport 전달 실패 횟수와 실제 claim 횟수를 분리한다. dispatch 재생성으로 자동 예산이 조용히 초기화되면 안 된다.
- 검토 제안: 기존 누적 attemptCount는 관측용으로 보존하고 자동 실행 예산의 범위를 별도 명시한다. review 승인 후 재개는 자동 실패 재시도와 구별해야 하며, 수동 재시도는 사용자 명시 동작에 따른 새 실행 회차로 둘지 결정해야 한다. 별도 retrySeasonAssets job의 예산도 함께 대조한다. 이 선택은 아직 확정하지 않았다.
- 브랜드 순차 설계: Firestore transaction 기반 실행권, owner/generation/lease, 요청 묶음 순서, 실행 종료 증거와 복구 주체를 확정한다. lease 만료만으로 이전 실행이 종료됐다고 간주하지 않는다. 대기 HTTP 요청으로 슬롯을 점유하거나 정상 대기를 오류로 만들어 재시도 횟수를 소비하지 않는다. 재승인된 시즌이 브랜드 대기열의 어느 위치로 들어갈지도 검토한다.
- 완료 기준: crash·중복 전달·만료·재전달·리뷰·수동 재시도의 상태 표와 테스트가 일치한다. 총 5회의 성공적 claim 상한, 마지막 실패의 최종 상태, 다음 시즌 진행을 실제 공유 저장소 경합으로 검증한다.
- 검증: 제어 가능한 clock·fake repository unit과 Firestore emulator 경합 검사. 기존 Functions 게이트와 새 계약 필수 ID를 연결한다. 필요한 emulator 검사가 없으면 분산 계약은 미검증이다.
- 논의 필요: 요청 묶음 경계, Worker 실행 구조, review/수동 재시도 예산 경계, 영속 실행권·종료 복구·Storage 쓰기 보호 계약. 해당 결정과 세부 구현 계획 승인 전 이 phase의 제품 변경은 진행하지 않는다.

## Phase 5 — Development 연동·성능 검증

- 선행 연결: [D0~D4 검토본](development-comparison-plan.md)의 개발 전용 유한 비교를 제품 대기열 전체 구현보다 먼저 준비한다. 이 비교는 실제 제품의 분산 FIFO·관리자 검토 재개까지 검증하는 단계와 구별한다.
- 목표: 최대 두 유력 후보가 실제 Storage·Firestore·Cloud Run에서도 정확성과 성능을 유지하는지 확인한다.
- 사전 실행안: 리비전·정확한 프로젝트/버킷·큐·테스트 문서/객체 범위·실행 정책·입력 manifest·예상 요청/bytes/비용·중단과 복구 명령을 제시한다. 실제 원격 자원 설정은 그때 읽어서 고정한다.
- 격리: no-traffic 후보와 인증된 task 호출을 우선 검토한다. 정상 queued 문서를 만들어 기존 Firestore trigger가 기존 Worker에 중복 dispatch하지 않는지 검증해야 한다. run ID만 붙인다고 라우팅이 격리되지는 않는다. 테스트 큐/trigger 경계가 검증되기 전 부하를 넣지 않는다. canonical audience와 기존 권한 경계를 유지한다.
- 조건: 기준선/후보 동일 1 vCPU·2GiB를 초기 비교안으로 두고, 인스턴스 수·요청/큐 동시성·cold/warm을 결과에 기록한다. 최대 3개는 실험 관련 인스턴스를 합산하며 리비전별 3개씩 허용하는 것으로 해석하지 않는다. 기존 개발 작업이 간섭하면 실험을 보류하거나 분리한다.
- 감독: 컨테이너 전체 사용량/한도를 측정할 수 있는지 먼저 검증한다. 100ms 간격 표본과 단조 시각으로 85% 이상 구간 1초 지속을 판단하는 안을 제안한다. 읽을 수 없거나 표본이 끊기면 안전 조건 미검증으로 중단한다. Node RSS만으로 Chromium 포함 메모리 기준을 통과시키지 않는다.
- 중단 동작: 감독기는 신규 dispatch를 멈추고 실행 중 작업의 취소·종료를 추적한다. 취소가 불가능한 SDK 요청은 종료까지 기록하며 즉시 메모리 회수가 보장된다고 주장하지 않는다. 중단 뒤 Cloud Tasks가 자동으로 같은 부하를 재개하지 않게 큐 상태를 함께 제어한다.
- 완료 기준: 최대 45회 내 유효 결과·실패·중단·미수행이 구분되고 정확성·파일·DB 계약이 일치한다. 2시간/추정 US$10/메모리 한도 도달 시 남은 회차는 미수행이다. 실패율 평가에서 중단을 삭제하지 않는다.
- 검증: 실제 OIDC 허용/거부, trigger 중복 방지, 실제 JPEG/Storage/DB 일치, 실패 복구와 기존 관리자 화면의 진행·검토·부분 실패·재시도 수동 QA. 구조 비교와 별개로 실제 URL 연동 확인 결과를 남긴다.
- 논의 필요: 구체적 배포·실험 실행안 승인. 테스트 자료 삭제는 생성 manifest와 exact 경로를 갖춰 별도 승인하며 기존 개발 자료를 포괄 삭제하지 않는다.

## Phase 6 — 결과 분석·최종안 반영

- 목표: 구조·수치·재사용을 실측으로 선택하고 회귀가 없는 최종 설정을 확정한다.
- 분석: workload별 전체 완료·첫 시즌 중앙값, 개별 반복, 실패/중단 비율, bytes/비용, 메모리와 실행 복잡도를 함께 본다. workload를 가중 합산해 약한 결과를 숨기지 않는다. 가중 종합 점수를 쓸 경우 별도 합의한다.
- 반복 악화의 확정식: 같은 workload·cold/warm 조건의 기준선과 후보를 짝지은 5회에서 3회 이상 10% 악화하고 중앙값도 10% 악화하면 자동 채택을 보류한다. 2026-10-03 사용자 확정이며 실험 조기 중단 기준은 아니다. 표본 부족·큰 변동은 개선 확정으로 처리하지 않는다.
- 변경 범위: 승인한 최종 정책/설정만 기본값에 반영하고 전용 게이트를 다시 실행한다. 조건부 분산 구조는 실제 검증을 통과한 경우만 포함한다. 변경한 API·데이터 계약은 DATA_SCHEMA/관련 진입점, 결정은 ADR, 검증 위치는 TESTS, 실행은 runbook에 연결한다.
- 완료 기준: 정확성·복구·성능 결과와 한계를 사용자와 검토하고 최종 조합을 선택한다. 최종 소스 digest의 필수 검사·원본 로그·수동 QA·남은 위험이 기록된다. 운영 배포는 별도 승인 전 미실행으로 남긴다.
- 논의 필요: 10% 미만 개선 또는 일부 부하 악화 시 단순성·비용과의 선택. 실측에서 개선되지 않으면 수치를 억지로 변경하지 않는다.

## 필수 검증 계약

테스트 설계: 대상은 비동기 파이프라인·공용 자원·캐시 수명·job 상태 전이다. fake HTTP/Storage/repository·barrier·clock으로 실패와 경합을 검증한다. 화면 배치·터치 감각은 자동 테스트 추가 없이 기존 관리자 흐름 수동 QA로 확인한다. 구현 승인에는 해당 phase의 필수 검사 실행을 포함한다.

| 필수 그룹 | 통과해야 하는 동작 |
| --- | --- |
| G1 기존 계약 | 후보·순서·해시 실패 보존·quality/review snapshot·deterministic ID·인증/URL 보안 |
| G2 실행 수명 | 여러 job 공용 상한·묶음 경계·빈자리 보충·형제 작업 drain·permit/bytes 해제·교착 없음 |
| G3 저장 | 두 파일 완료 전 ready 금지·업로드/DB 일부 실패·부분 재시도·완료 대상 중복 저장 방지 |
| G4 재사용 | 해시/변환 입력 일치·예산 합산·miss fallback·review/새 실행 격리·다중 소비와 종료 정리 |
| G5 실제 job 계약 | 총 5회·중복/stale 미소비·review/수동 경계·lease 복구·조건부 브랜드 분산 순서 |
| G6 실험 판정 | 코드/입력/설정 digest·회차·실패/중단 포함·메모리 지속 구간·누락 표본·중앙값/악화 계산 |

G1~G6은 계획상 요구 ID다. 구현 시 실제 파일/테스트 이름의 requiredTests로 연결하며 목록과 명령을 사용자 검토 기준으로 고정한다. phase별 아직 구현하지 않은 그룹을 통과로 표시하지 않는다. 작은 표본의 0건 실패를 실패 확률 0으로 보고하지 않는다.

Worker 게이트 명령은 `node tools/verification-gate/gate.mjs --project . --config verification/lookbook-import.json`이다. 2026-10-03 Worker lint/build/전체 Node 테스트/추출 fixture와 기존 계약 필수 ID 10개를 연결하고 실행했다. 결과는 [입력·검증 결과](input-manifest.md)에 기록했다. 새 동시성·계측·캐시·재시도 검사는 해당 구현과 함께 필수 ID로 추가한다. Functions를 변경한 phase는 기존 `verification/functions.json`과 신규 계약 검사를 실행한다. rules/indexes 변경이 필요하면 범위 검토 후 해당 게이트를 추가한다.

게이트 원본은 `output/verification/<실행 ID>/summary.json` 및 각 검사 로그다. 성능 원본은 별도 run ID로 연결한다. 검사 실패·미실행·skip·0개·timeout·환경 미준비·사람 QA 미완료를 통과로 처리하지 않는다. 문서에 명령을 적은 것과 도구가 실제 실행한 결과를 구분한다.
