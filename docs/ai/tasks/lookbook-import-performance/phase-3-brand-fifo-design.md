# 브랜드 순차·내부 병렬 비교 — 승인된 세부 설계와 구현 계획

작성일: 2026-10-04(KST). 상태: 사용자가 현재 배포 자원 제약을 문서·세부 구현 계획에 반영하고 다음 핵심 작업을 진행하도록 승인했다. 로컬 구현·Mac/Linux265개/필수157개 게이트·20회 비교·독립 재집계·정리를 완료했다. **20/20 성공**, 대용량 전체0.86%단축/최고메모리93.37→83.36%/읽기량22.29%감소다. 속도10%목표는 미달이며 [실제 결과·원본·남은 범위](phase-3-brand-fifo-results.md)를 따른다. 아래 조건은 결과를 보기 전에 고정한 승인 계획이다.

## 1. 요구와 승인 범위

사용자는 먼저 등록한 브랜드가 자원을 사용해 완료한 뒤 다음 브랜드를 처리하는 비교를 추가하도록 요청했다. 브랜드 전환은 추출만 끝난 때가 아니라 썸네일/상세 변환, 두 파일 업로드, 경로 저장과 시작한 작업 정리가 끝난 뒤다. 브랜드 내부에서는 시즌과 이미지를 제한된 폭으로 병렬 처리한다.

이후 사용자 선택으로 다음 설계 조건을 확정했다.

- 현재 병렬 구조와 브랜드 순차·내부 병렬의 두 구조, 일반/대용량 두 입력, 각5회: 총20회.
- 원본 재사용 예산은 두 구조 모두 인스턴스 공용128MiB. 이번에는 off/256 비교를 추가하지 않는다.
- 모든 선택 시즌이 저장 완료·검토 대기·최종 실패 중 하나로 끝나고 실행 중 작업이 정리되면 다음 브랜드를 허용한다. 검토 대기와 최종 실패를 저장 성공으로 기록하지 않는다.
- 자동 재시도 대기는 해당 브랜드 차례를 유지한다. 시즌 최초 시도 포함 총5회, 시간에 따른 추가 조기 종료 없음. 대기 중인 다음 브랜드는 시도 횟수를 소비하지 않는다.
- 현재 CPU1개/메모리2GiB 조건을 유지하며 자원 증설 없이 비교한다. 이 자원 설정이 실제 배포의 최저 요금/무료 조건이라고 확인된 것은 아니다.

### 현재 배포 자원 읽기 확인(2026-10-04)

사용자의 현재 Firebase 설정 기준 요청에 따라 `gcloud run services describe`와 실제100% traffic revision의 `gcloud run revisions describe`로 읽기만 수행했다. 배포·설정 변경·Worker 작업 호출은 하지 않았다. 룩북의 무거운 이미지 작업은 관련 Cloud Run Worker에서 처리한다.

| --- | --- | --- | --- | --- | --- |
|운영 outpick-664ae |lookbook-import-worker-00026-qes |1/2Gi |2 |명시값 없음: 기본0 |20/5 |

두 환경의 timeout은900초, startup CPU boost는true였다. 공식 [최소 인스턴스](https://docs.cloud.google.com/run/docs/configuring/min-instances) 및 [최대 인스턴스](https://docs.cloud.google.com/run/docs/configuring/max-instances) 문서에 따라 기본 최소는0이고 서비스/리비전 최대를 함께 설정하면 작은 값이 적용된다. 따라서 현재 주력 revision의 적용 최대 설정은 각각5이며 한 대 고정 설정이 아니다. 이 수치는 순간 실행 개수를 측정한 결과나 엄격한 비용 상한이 아니다.

로컬1CPU/2GiB는 **현재 인스턴스당 자원 한도와 일치**한다. 단일 컨테이너 내부 유한 작업 실험이므로 여러 Cloud Run 요청/인스턴스·자동확장·startup boost·원격 네트워크까지 동일하게 재현한 것은 아니다. 현재 자원 설정을 올리지 않고 단일 인스턴스 내부의 브랜드 입장/동시성을 비교한다. 향후 전역 브랜드 순차를 보장하려면 인스턴스 내부 큐뿐 아니라 실제 dispatcher/claim 경계가 필요하며 이번 로컬 비교의 완료로 간주하지 않는다.

사용자가 현재 추가 요금이 없다고 설명한 사실은 비용 제약으로 유지한다. 이번에는 청구 내역/무료 잔여량을 조회하지 않았다. [공식 요금](https://cloud.google.com/run/pricing)은 무료 구간 적용 후 사용량으로 계산되므로 같은 설정 자체가 추가 요금0을 보장한다고 기록하지 않는다. 실제 클라우드 실험·자원 증설은 아직 하지 않았고20회 설계의 자원 조건을 바꾸지 않는다.

현재 작업은 승인된 로컬 구조 비교다. 현재 배포의 인스턴스당1CPU/2GiB를 올리지 않고 한 로컬 컨테이너씩 실행한다. min/max인스턴스·요청동시성 등 클라우드 설정은 변경하지 않는다. 제품의 분산 대기열/claim/lease, UI, Functions, Firestore 데이터/API 변경과 Development/운영 배포는 이번 범위에 포함하지 않는다.

## 2. 기존 근거와 비교 누락

- 기존 A~F 중 D/E는 **같은 브랜드의 시즌 순차·다른 브랜드 병렬**이었다. 이번 **브랜드 사이 순차·같은 브랜드 시즌 병렬**은 별도 비교축이다. `performance/comparison.ts::comparisonPolicy`와 [기존54회](phase-3-comparison.md)를 참조한다.
- 최신 P4는 시즌6개 병렬, 시즌마다 미완료 이미지4개까지 빈자리 보충, 준비된 변환을 입력 시즌 순위로 선택한다. 다운로드4/변환1/업로드4/경로 저장 제한없음이다. 입력 시즌 우선 변환이 뒤 브랜드의 해시·다운로드 시작까지 막는 것은 아니다.
- [최신15회](phase-3-p4-confirmation.md)는 **합성 브랜드 하나의 큰 시즌 작업6개**였다. off3/5,128MiB5/5,256MiB3/5 성공이며 실제 OOM1회가 있었다. 다른 브랜드 경쟁이 OOM 원인이라는 증거는 아니다.
- 새 다중 브랜드 결과가 좋아져도 단일 브랜드 내부의 큰 입력 문제까지 해결했다고 선언하지 않는다. 이번 목적은 브랜드 입장 제한의 효과를 분리하는 것이다.

## 3. 비교 구조와 실행 흐름

| 항목 | P: 현재 병렬 대조군 | S: 브랜드 순차 후보 |
| --- | --- | --- |
| 브랜드 작업 시작 | 입력 시즌 순서에 따라 여러 브랜드 허용 | 등록 순서의 한 브랜드만 허용 |
| 시즌 실행 폭 | 전체 최대6 | 현재 브랜드 안에서 최대6 |
| 이번 입력의 실제 시즌 동시 수 | 최대6 | 한 브랜드가2시즌이므로 최대2 |
| 이미지 작업 | 시즌마다 P4, 최대4개 미완료 후 빈자리 보충 | 동일 |
| 단계 공유 상한 | 다운로드4/변환1/업로드4/경로 저장 제한없음 | 동일 |
| 변환 우선순위 | 준비된 작업 중 원래 입력 시즌 순위·동순위FIFO | 동일 |
| 재사용·커버 | 공용128MiB, 커버 선준비 | 동일 |

S의 흐름: A 입장 → A의 두 시즌 병렬 → 각 시즌 해시 확인·본문/커버 저장 → A의 모든 시즌 종료와 정리 → B 입장 → 같은 방식으로 C까지 진행한다. 대기 브랜드의 네트워크·해시·커버 준비·원본 캐시 보관·변환을 미리 시작하지 않는다. 실험 전체의 입력 파일 무결성 사전 검사는 측정 전 공통 준비이며 브랜드의 실제 처리와 구분한다.

브랜드가 바뀌어도 **같은 프로세스·같은 공유 runtime·같은 공용128MiB 예산**을 유지한다. 브랜드마다 프로세스/컨테이너 재시작, 강제GC, sharp 설정 변경, 추가 메모리 할당은 하지 않는다. 원본 scope는 기존처럼 각 시즌 실행 종료에 닫힌다. 이 때문에 원본 읽기량/cache hit가 두 구조에서 달라질 수 있으며, 이는 같은 예산을 가진 실행 구조의 결과로 측정한다. 과거128MiB의 hits154를 새 구조의 고정 기대값으로 재사용하지 않는다.

브랜드 순서는 로컬 고정 manifest의 최초 등장 순서다. 비연속적으로 입력된 같은 브랜드의 시즌도 같은 그룹으로 묶고 시즌 내부의 원래 순서를 보존한다. 이번20회는 전체3브랜드가 처음부터 등록 대기 중인 유한 입력을 비교한다. 실행 도중 새 등록/동일 브랜드 추가 요청/취소 요청 병합의 제품 정책은 별도 설계 범위다.

## 4. 브랜드 완료와 예외 전환 계약

정상 저장 성공은 모든 선택 시즌의 본문·커버 썸네일/상세 업로드와 경로 저장이 완료된 상태다. 해당 브랜드의 모든 시즌 실행 Promise가 종료되고, 해당 작업의 형제 작업·lease·source scope가 반환된 후 처리권을 넘긴다. 전역 runtime의 빈 상태를 병렬 대조군의 개별 브랜드 완료 조건으로 사용하지 않는다. 병렬 대조군에는 다른 브랜드의 작업이 정상적으로 남아 있을 수 있다.

`reuse-input.ts`의 기존 `season-end` trace는 `withSourceBufferScope` 내부에서 기록되고 scope close는 그 뒤 finally에서 실행된다. 따라서 이 trace 하나로 전환하지 않는다. `execute()` 반환 후 시도 종료 기록과 정리 증거를 기준으로 삼는다. `drainAll`/`mapScheduled`의 이미 시작한 형제 종료 대기 계약을 유지한다.

| 상황 | 현재 브랜드 | 다음 브랜드 |
| --- | --- | --- |
| 모든 시즌 저장 성공 | 성공·정리 시각 기록 | 정리 후 허용 |
| 일부 시즌 검토 대기 | 다른 선택 시즌 처리 계속, review 상태 보존 | 모든 시즌이 종료 상태이고 정리됐을 때 허용 |
| 일부 시즌 최종 실패 | 다른 선택 시즌 처리 계속, 실패 상태 보존 | 모든 시즌 종료·정리 후 허용 |
| 시즌 자동 재시도 대기 | 해당 시즌 총5회 범위에서 현재 브랜드 유지 | 시작 금지 |
| 취소/메모리 감독 중단 | 새 작업 금지, 시작한 형제 정리 | 해당 회차에서 시작 금지 |
| 실제 OOM | 컨테이너 외부 종료 증거 보존, 내부 정리는 미확인 | 해당 회차에서 시작 불가 |

검토/실패를 포함한 브랜드는 `settled/released`와 성공 완료를 구분한다. 성공 완료 시간은 모든 시즌 성공일 때만 산출한다. 성능 입력은 모두 저장까지 이어지는 기존 로컬 연결 fixture이며, review/재시도/실패 경계는 제어 가능한 자동 테스트로 검증한다. 실제 UNAFFECTED의 품질 검토 승인을 우회하지 않는다.

메모리 중단은 회차 분모에 남기고 컨테이너 정리 후 다음 독립 회차를 진행하는 기존 규칙을 유지한다. 환경 미검증·정합성 실패·컨테이너 정리 실패는 나머지 회차를 미수행으로 기록한다. 실제 OOM의 내부 반환 미확인을 컨테이너 제거 실패와 혼동하지 않는다.

1CPU/2GiB/추가swap없음/Linux ARM64/네트워크없음/읽기전용 입력 volume/회차마다 새 컨테이너/단일고정이미지 조건을 유지한다. 무결성 검사 뒤 측정하며 cold-cache라고 표시하지 않는다. 실제 sharp와 대체 Storage/경로 저장을 사용하며 Firebase 요청은 없다.

### 결과를 보기 전 고정하는20회 순서

P는 병렬, S는 브랜드 순차다. 한 반복 번호 안에서 같은 부하의 P/S를 짝짓는다.

| 반복 | 첫 부하·순서 | 다음 부하·순서 |
| --- | --- | --- |
|1 |일반 P→S |대용량 S→P |
|2 |대용량 P→S |일반 S→P |
|3 |일반 P→S |대용량 S→P |
|4 |대용량 P→S |일반 S→P |
|5 |일반 P→S |대용량 S→P |

실행 수는2구조×2부하×5회=20회다. 기존 시간에 근거한 순수 처리 약45분은 추정이며 게이트·빌드·분석은 별도다. 실패 표본 대체나 추가 준비 측정은 자동으로 늘리지 않는다. 20회 전부 성공할 경우 JPEG18,580개/2,924,423,050B/경로9,290건이며 실제 합계는 성공한 회차만 따로 집계한다.

## 6. 측정·판정·OOM 증거

공통 T0는 무결성 사전 확인 후 본 작업을 시작하는 단조 시각이다. `firstBrand`는 가장 빨리 끝난 브랜드가 아닌 등록 순서 첫 브랜드A다.

- 브랜드별 등록 대기 시각(본 비교에서는 모두T0), 입장/첫 실제 작업 시각, 모든 시즌 종료·정리 시각, 성공 완료 시각을 기록한다.
- 첫 브랜드 완료 시간은 A 성공 완료−T0다. 각 브랜드 전체 대기 포함 완료 시간, 대기 시간, 입장 후 처리 시간을 구분한다. 총 완료 시간은 모든 브랜드 작업과 정리가 끝난 시각−T0다.
- 기존 첫 시즌 및 시즌별 완료, CPU 사용·컨테이너 메모리·RSS/heap/external/Buffer 최고치·원본 읽기/cache hit·단계 대기·동시 작업 최고치를 함께 기록한다. 독립 최고치들을 합산해 순간 메모리 구성이라고 표시하지 않는다.
-100ms 메모리 표본,500ms초과 환경 미검증 중단,85%이상1초지속 메모리 중단을 유지한다. 순간 최고치와 지속 중단, 실제 OOM을 각각 구분한다.
- 정확성·실패/중단 악화 없음이 선행 조건이다. 양쪽5회 성공한 부하에서만 짝 비교·중앙값·전체10%개선 우선 기준을 적용한다. 첫 시즌/특정 부하 반복악화(5쌍 중3쌍이상10%느림+중앙값10%느림)의 기존 보류 기준을 유지한다.
- 첫 브랜드와 뒤 브랜드의 대기 포함 완료 변화도 각각 보고한다. 첫 브랜드가 빨라지고 전체 개선이10%미만이면 메모리·복잡도와 함께 사용자 검토 대상으로 남긴다. 첫 브랜드 개선만으로 자동 채택하거나 뒤 브랜드의 대기를 숨기지 않는다. 서로 다른 부하를 가중 합산하지 않는다.

OOM 증거는 기존 종료 시 전체 payload에만 의존하지 않도록 **최소 진행 경계 기록**을 추가하는 구현안을 제안한다. 사전 확인 시작/끝, 측정 시작, 브랜드 입장/정리, 시즌 시도 시작/종료를 작은 JSONL로 실행 중 기록한다. URL/이미지 바이트/인증값은 기록하지 않고 run/brand/season/attempt/단조시각만 사용한다. 현재 end-only asset trace의 의미를 변경하지 않는다. 새 기록 방식은 P/S 동일하게 적용하고 두 구조 모두 새 이미지에서 비교한다.

구현안은 최대256KiB/회, 순서가 보존되는 출력과 backpressure 처리를 사용하고 Docker 로그를 삭제 전에 보존하는 것이다. 한도 초과는 `failed/evidence-limit`, 출력 실패는 `failed/evidence-write`로 기록하고 새 작업을 막은 뒤 시작한 형제를 정리한다. 후속 회차는 기존 일반 실패 규칙대로 미수행으로 남긴다. 마지막 출력도 OOM 순간까지 도달했음을 보장하지 않으며 결과 없으면 최고치·표본 간격·세부 이미지/단계·내부 반환을 미확인으로 남긴다. 이는 상세 네이티브 메모리 프로파일러가 아니며 계측 부하가0이라고 가정하지 않는다. 별도 계측 부하 비교가 필요해지면 회차를 임의로 추가하지 않고 논의한다.

## 7. 기술·데이터·아키텍처와 변경 후보

기술은 기존 Node24/TypeScript, sharp, Node test runner, Docker와 프로그램적 게이트를 유지한다. 화면/사용자 UI 흐름/앱 DI·Container·Coordinator 변경은 없다. Firebase API/Firestore schema/인증/배포 설정도 이번에 바꾸지 않는다. 데이터 변경은 로컬 계획·입력 매핑·브랜드 시각·실험 결과 schema에 한정한다.

| 책임 | 예상 파일 후보 | 경계 |
| --- | --- | --- |
| 브랜드 사이 직렬·내부 병렬 |`performance/season-runner.ts` 및 관련 테스트 |기존 parallel/serial-per-brand 의미 유지, 새 정책 별도 추가 |
| 입력 매핑·20회 계획·엄격 검증 |신규 `performance/brand-comparison.ts` |두 입력/순서/128MiB/5회/marker·digest 고정 |
| 브랜드 지표·분모·짝 비교 |신규 `performance/brand-report.ts` 및 비교 테스트 |성공과 release 구분, 이전표본/중복ID/다른이미지 거절 |

## 8. 테스트 설계

대상은 비동기 실행 순서·재시도·정리·캐시 수명·측정 집계다. fake executor/deferred barrier/clock/wait/Storage·경로 저장 spy와 작은 실제 sharp fixture를 사용한다. 신규12개 필수 시나리오를 계획하며 구현 시 고유 requiredTests 이름으로 연결한다. 기존253개·필수145개를 유지하고 신규12개가 각각 하나의 테스트로 연결되면 전체265개·필수157개가 목표다. 실제 개수·통과는 실행 결과로 확인한다.

| ID | 필수 시나리오 |
| --- | --- |
| BF01 |브랜드 최초 등장FIFO·비연속 동일브랜드 묶음·내부 시즌 병렬/상한·대기 브랜드 미시작 |
| BF02 |앞 브랜드의 마지막 업로드/경로 저장/lease 정리 barrier가 풀리기 전 뒤 브랜드 다운로드·해시·캐시 시작 금지 |
| BF03 |review·최종 실패 뒤 형제 종료/정리 후 다음 브랜드 진행, 실패/review를 성공 완료로 집계하지 않음 |
| BF04 |재시도 대기 시 브랜드 유지·최초포함5회·브랜드 대기가 시도 횟수를 소비하지 않음 |
| BF05 |취소/메모리중단 신호에서 다음 브랜드/새시도 금지·이미 실행 중 형제 drain·원본/permit 반환 |
| BF06 |한 브랜드 입력에서 기존 P와 S의 실행 허용 범위 동일·기존 D/E와 의미 혼동 없음 |

단순 화면 happy path·실기기 UI 테스트는 화면 변경이 없어 추가하지 않는다. 실제 원격 업로드/Storage/Firestore/OIDC 및 관리자 검토 재개는 이번 로컬 검증으로 통과 처리하지 않는다. 기존 회귀와 신규 필수 검사를 Mac/Linux에서 실행해 전체265개·필수157개와 lint/build/fixture가 통과했다. 원본은 결과 문서에 연결했다.

프로그램적 검증 명령은 프로젝트 루트의 `node tools/verification-gate/gate.mjs --project . --config verification/lookbook-import.json`이며 Linux도 같은 필수 목록과 source를 고정한다. 구체적인 build/driver 명령·image ID·gate 결과 경로는 구현 후 실제 산출물로 연결한다. 명령이 문서에 있다는 이유로 게이트 연결/실행 통과를 선언하지 않는다.

최종 산출물은 설계/계획, 실행 소스, 필수 게이트 원본,20회 manifest/plan/result/finished/log/summary/브랜드 지표/독립 재집계/정리 확인이다. 코드 변경 후 ENTRYPOINTS와 LOOKBOOK/TESTS를 갱신하고 관련 없는 사용자 변경을 보존한다. 커밋·배포는 별도 요청 전 수행하지 않는다.
