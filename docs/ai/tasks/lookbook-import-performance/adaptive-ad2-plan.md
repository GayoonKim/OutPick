# AD2 — 실제 계측·메모리 예약·이미지 연결 설계

후속 세부안: [AD2b 예약·커버·실제 연결 계획](adaptive-ad2b-plan.md). AD2a 결과를 반영해 초기 예약 후보·원본/이미지 토큰·CPU 준비·반환 후 새 표본·AB01~12를 구체화했다. 초기 예약량과 커버 방식 결정 전에는 AD2b 구현하지 않는다.

2026-10-04. 사용자 “모호해서 논의 필요한 부분 없으면 진행하자” 지시로 추천 AD2a 구현·필수 검사·로컬18회 측정을 진행했다. **AD2a 완료: Mac/Linux292개·필수184개,18/18회·42변환 통과.** [실제 코드·원본·결과](adaptive-ad2a-results.md)를 우선한다. 75% 제동 세분화와 보수적 예약은 AD2b 연결 설계이며 E·안전 여유·압박 검증은 측정 결과로 구체화해야 한다. AD1 증거는 이전 결과에 보존한다.

## 1. 확인한 입력과 구현 제약

[원본 조사 JSON](../../../../output/lookbook-import-performance/adaptive-ad2-metadata.json)은 기존 로컬 파일을 하나씩 읽어 SHA-256/bytes를 검증하고 헤더만 다시 조회한 결과다. 원격 다운로드·이미지 변환·Firebase 쓰기는 없었다. manifest/covers hash와 실행 라이브러리 버전도 기록했다.

| 항목 | 확인값 |
| --- | --- |
| 원본 참조 / 고유 내용 hash | 138 / 137 |
| 형식·깊이·채널·프레임 | JPEG/PNG, uchar, 3/4채널, 모두1프레임 |
| 압축 파일 크기 | 41,521~2,737,602 bytes |
| 가장 큰 해상도 | 4050×5400,3채널 |
| 최대 width×height×channels | 65,610,000 bytes(약62.57MiB) |
| 참조별 압축 bytes 합계 | 112,771,684 bytes |

픽셀·채널 곱은 단순한 비교 지표이지 sharp/native/인코딩 중간 버퍼 전체의 상한이 아니다. `.metadata()`는 원본 헤더를 조회하며 resize/rotate 결과나 실제 디코드 메모리를 측정하지 않는다. [sharp metadata 공식 문서](https://sharp.pixelplumbing.com/api-input/).

현재 `jpegBytes`는 `sharp(input,{failOn:"none"}).rotate().resize(...).jpeg({quality,mozjpeg:true}).toBuffer()`다. 한 이미지의 두 변환 결과를 모두 보유한 뒤 두 업로드를 실행하고, 둘 다 끝나야 경로를 저장한다. 같은 source를 두 출력이 참조하므로 source Buffer를 두 번 합산하지 않는다. `responseBytes`는 chunks를 모아 `Buffer.concat`하므로 수신 완료 부근에서 원본 길이 하나만큼의 메모리만 필요하다고 가정하지 않는다.

`SourceBufferScope`는 시즌 종료까지 원본을 retain하며 소비자가 끝났다는 이유만으로 retained 원본이 사라지지 않는다. 재사용128MiB는 이 보관의 공용 예산이고 전체메모리가 아니다. 기존 대용량 fixture는 132개 후보를 각 합성 시즌에 반복 배치하는 구조다. 사진 자체의 최대 해상도는 일반 입력과 같고 중복 실행/보유 수요가 증가한다.

## 2. 연결 흐름 추천

`100ms 공통 표본 → 구간 CPU/작업 관측 → AdaptiveController → 공유 시작 허용량`

`고정 원본 메타데이터 → 이미지 전체 예약 → 필요 원본 읽기/재사용 → 변환 슬롯 → 두 JPEG → 업로드 슬롯 → 경로 기록 → 소비자 종료 → 예약 반환`

- 새 이미지에는 이미지 슬롯과 예약을 함께 승인한다. 예약을 기다리면서 이미지/다운로드/변환 슬롯을 잡지 않는다. 예약 승인과 슬롯 선택 사이에 비동기 틈을 두지 않고 하나의 pump에서 결정한다.
- `canAdmit`는 증속을 위한 현재 가능성 요약이다. 같은 true 값을 받은 여러 작업이 동시에 예산을 소비하지 않도록 실제 시작 직전에 원자적 예약을 다시 한다.
- hash용 다운로드, 커버 선준비, 캐시 miss 재다운로드까지 같은 다운로드 개수/예약 경계를 사용한다. hash 검증 장벽과 시즌의 quality/review 결과는 바꾸지 않는다. 커버는 준비 토큰에서 이미지 토큰으로 소유권을 넘기며 같은 bytes를 다시 예약하지 않는다.
- 이미 입장한 이미지의 두 변환·두 출력 보유까지 예약해 두고 단계 이동마다 동일한 예산을 새로 요청하지 않는다. 별도의 단계 슬롯은 CPU/네트워크 실행 수를 제어한다. 다음 단계 대기 중 이전 단계 슬롯을 보유하지 않는다.
- 입력/두 JPEG/부분 업로드의 실제 소비자가 끝나기 전 예약을 반환하지 않는다. 취소도 SDK/변환 반환과 형제 drain을 기다린다. 같은 파일 요청의 내부 재시도는 같은 토큰 안에서 수행하며, 시즌 재시도는 이전 토큰이 정리된 후 새로 예약한다.
- P/S는 기존 실행 정책을 유지한다. 비교 시 계측만 동일하게 연결하고 R에서만 공용 이미지 투입/예약/가변 슬롯을 켠다. 앱·Functions·제품 job API·rules·분산 큐는 변경하지 않는다.

## 3. AD1 제동 규칙에서 보완할 경계 — 확인 필요

AD1은75%에서 이미지/다운로드 허용량을 모두0으로 만든다. 실제 연결에서는 이미 입장한 이미지가 캐시 miss 다운로드를 기다리거나, 완료에 필요한 커버 원본을 기다릴 수 있다. 모두 막으면 사용 중 데이터를 정리하는 작업도 진행하지 못할 수 있다. 코드 흐름으로 확인한 가능성이며 실제 교착을 재현한 결과는 아니다.

추천: **75% 제동을 신규 작업과 이미 예약한 작업으로 구분**한다.

- 신규 이미지·새 hash 읽기·미예약 커버 준비는 보류한다.
- 이미 예약한 이미지/커버의 필수 읽기는 기존 다운로드 목표 폭 안에서 계속 허용한다. 다운로드 슬롯을 무제한으로 여는 예외가 아니다. source/출력/변환까지 예약한 토큰을 검증하고 같은 전체 다운로드 수에 합산한다.
- 이미 입장한 변환은 폭1, 업로드·경로 저장은 기존 계약으로 진행한다.85% 이상1초·500ms 표본 지연·사용자 취소·원본 불일치는 이 예외보다 우선해 전체 중단한다.
- 모든 token이 정리돼도 cgroup 사용량이65% 미만으로 내려오지 않으면 자동 안전 기준 완화나 강제 GC로 성공시키지 않는다. 대기 원인과 timeout/미수행을 기록한다.

대안은 AD1의 전체 다운로드 보류를 그대로 유지하는 것이다. 구현이 단순하지만 정리 가능한 작업도 timeout까지 막힐 수 있다. 새 구분은 제어기 출력/API/회귀 테스트 변경이므로 사용자 확인 후 구현한다.

## 4. 첫 메모리 예약 방식 추천 — 확인 필요

현재 cgroup 값만으로 native 메모리를 어느 이미지가 차지하는지 정확히 나눌 수 없다. 첫 연결은 **예약 전액을 종료까지 유지하는 보수적 방식**을 추천한다. 다중 작업의 native 할당을 추정해서 빠르게 예약에서 빼는 방식은 후속 후보로 둔다.

새 입장 조건의 제안식은 `최근 cgroup 사용량 M + 미반환 예약 R + 새 예약 E ≤ 0.75 × 한도 L`이다. 같은 동기 pump에서 예약 합계를 변경한다. 표본이 없거나500ms보다 오래되면 입장시키지 않는다. 시작한 작업이 실제 메모리를 사용하면 M과 R의 일부가 겹칠 수 있다. **이 겹침은 보수적인 입장 제약이며 실제 사용량으로 보고하지 않는다.** 원본 캐시/논리 Buffer/RSS를 M에 다시 더하는 우발적 이중 합산과 구분한다. 사용량·예약량·추정 여유·거부 사유를 별도로 기록한다.

장점은 소비자 종료 전 예산을 조기 반환하지 않고 구현·실패 경계를 검증하기 쉽다는 것이다. 단점은 실제 여유보다 많은 예약을 잡아 동시성을 과도하게 줄일 수 있다는 것이다. 정확한 native 소유권을 확인하지 못한 채 예약을 줄여 속도만 개선하는 안은 추천하지 않는다. R의 성능 결과에는 이 보수성을 명시한다.

E의 실제 수치/계수는 아래 준비 측정 후 결정한다. 파일 bytes 또는 픽셀·채널 곱만으로 확정하지 않는다. 수신/concat, source/cache hit 여부, 두 변환의 중첩, 두 JPEG 보유, native 잔류를 포함한 envelope 후보를 산출하고 안전 여유를 제시한다. 지원 범위는 고정 hash·해상도·형식·단일 프레임·동일 sharp/libvips/아키텍처로 한정한다. 범위를 벗어나면 준비 미검증으로 멈추며 웹의 임의 이미지를 허용하지 않는다.

캐시에 넘겨 계속 보관하는 source는 token 반환 시 메모리에서 사라졌다고 처리하지 않는다. 종료 뒤 새 cgroup 표본으로 다음 입장을 재평가한다. Buffer view·동일 bytes의 여러 소비는 backing allocation/소유 token을 기준으로 한 번만 회계 처리한다. 현재 BufferInventory의 객체별 관측값은 진단용으로 유지하고 이를 물리 메모리 원장으로 재사용하지 않는다.

## 5. 실제 계측 계약

- 컨테이너의 동일 cgroup에서 memory와 CPU 누적 시간을 읽는다. v2 `cpu.stat`의 usage_usec, quota/period 및 cpuset 제약을 확인해 실효 CPU를 구한다. v1에서는 cpuacct 사용량의 ns 단위와 quota/period를 별도로 파싱한다. 지원하는 컨테이너 루트·quota/cpuset과 Docker HostConfig의1CPU를 확인하며 다른 배치를 추정하지 않는다. 숨겨진 상위 호스트의 경쟁/제약까지 독점1CPU로 검증한 것은 아니다. 실제 연결 대상의 계측 지원 여부는 별도 확인한다. [Linux cgroup v2 공식 문서](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).
- CPU 비율은 최근2초의 `누적 CPU 차이 / 실제 경과시간 / 실효 CPU 수`다. 첫2초는 CPU 증속 준비 전이며 작업은 초기 허용량에서 시작할 수 있다. 분모/카운터 역행·할당량 변경·지원되지 않는 계측은 중단한다.100%를 조금 넘는 값을 억지로100%로 자르지 않는다.
- 메모리 표본100ms·500ms 초과 중단은 그대로다. 작은 cgroup 파일만 동기 조회하고 같은 표본을 안전 감독기/제어기에 공유한다. 임의 async cgroup 읽기로 기존 libuv 지연 문제를 재도입하지 않는다. 이벤트 루프 지연도 기록한다.
- 완료량은 표본 사이의 증분 이벤트로 딱 한 번 전달한다. 성공/실패/취소·SDK retry를 분리하고 단위는 전송 bytes, 실제 출력 pixels, 완료 이미지 수다. 작업 대기와 실제 실행시간을 나눠 측정한다. 측정 누락을0이나 빠른 성공으로 처리하지 않는다.
- 시작 직전부터 완료까지의 active·대기queued·앞으로 남은 작업remaining을 구분한다. 다운스트림 증가량은 raw source/JPEG의 살아 있는 소유 bytes를 구간별로 비교한다. URL/자격증명/원본 바이트는 trace에 넣지 않는다.
- 제어 결정을 내릴 때 검사한 조건과 실제 적용/입장/예약 시각을 함께 기록한다. 변화가 없는 표본의 trace도 정해진 용량 안에서 보존하고, 누락을 조용히 허용하지 않는다. 시간·용량 상한은 실행 manifest와 묶는다.

| 사례 | 원본 | 목적 |
| --- | --- | --- |
| 중앙 크기 JPEG | 2025SS-010,1350×1687 | 일반 작업 |
| 최대 픽셀 JPEG | 2025FW-006,4050×5400 | 디코드/변환 압박 |
| 최대 파일 JPEG | 2026FW-008,3240×4050 | source/수신 보유 |

- 단일 이미지5종×각3회=15개 새 컨테이너. 원본 하나를 읽고 실제 `jpegBytes`로 해당 종류의 썸네일·상세를 순차 생성한다. 두 출력을 모두 보유한 시점과 참조 해제 뒤를 측정한다. 총30변환이다. 실제 기존 golden hash/bytes와 대조한다.
- 중첩 확인3회는 최대 픽셀 원본의 독립 이미지2개(서로 다른 Buffer 소유)에서 두 출력씩 총4개 변환을 동시에 제출한다. 총12변환. AD1의 변환 최대4 조건에서 단일 측정의 단순 배수와 실제 중첩을 대조한다. libuv/sharp 설정은 변경하지 않는다.
- 합계18개 컨테이너·42변환이며 **6시즌 전체 처리18회가 아니다.** 이 준비는 후속 P/S/R15회와 분리한다. 원본 읽기/I/O는 로컬이고 upload는 보유/해제만 흉내 내므로 네트워크 메모리나 실제 Storage SDK 비용 검증이 아니다.
- 모든 컨테이너는1CPU/2GiB·추가swap 없음·네트워크 없음·같은 고정 이미지다. 파일 무결성 확인 뒤 새 프로세스로 측정하며 파일 캐시가 비었다고 주장하지 않는다. 시작/입력/각 변환/두 출력 보유/정리 후의 memory·CPU·RSS·logical bytes를 기록한다. 강제GC/sharp cache 변경 없이 현재 설정을 사용한다.
- 기존100ms/500ms/85%1초 감독과 외부 OOM/종료 증거를 유지한다. 가능한 경우 cgroup memory.peak도 전후 기록하지만 프로세스/페이지 캐시/시작 비용이 포함된 최고값이며 개별 sharp의 정확한 메모리라고 부르지 않는다. 과거 peak 재설정 권한이 없으면 새 cgroup 전체 peak로 보고한다.
- 승인된 첫 준비 창은 최대30분, 컨테이너당 timeout120초다. 중단/누락/OOM이면 나머지는 미수행으로 남기고 자동 재실행하지 않는다. 이 시간은 로컬 준비 상한이며 기존 시즌5회 재시도를5분으로 대체하지 않는다.
