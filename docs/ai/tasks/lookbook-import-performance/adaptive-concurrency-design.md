# 자원 기반 동시성 조절 — 설계와 구현 범위 검토

**현재 단계(2026-10-04):** 사용자가 다운로드4·변환1·업로드4를 유지한 다음 구현을 승인했다. [version2 네 구조20회+smoke1회 로컬 구현·검증 기록](development-network-implementation.md)과 [실행 대상·요청량·비용](development-network-comparison-plan.md)을 따른다. remote-contract/runner와 remote-campaign/report/target/CLI가 진입점이다. 이미지별 예약/R 연결은 보류했고 기존 결과는 보존한다. 배포·유료 실험은 미실행이다. 아래 ‘다음’과 AD2b 결정 대기는 이전 이력이다.

최신 후속: [AD2a 계측·준비18회 완료](adaptive-ad2a-results.md). 실제 cgroup·완료 이벤트·준비 실행기를 구현했다. Mac/Linux292개·필수184개,18/18회·42변환 통과. 예약 E·75% 신규/기예약 구분·실제 R 연결은 AD2b에 남아 있다. 이번 측정으로 성능 최적값을 확정하지 않는다.

2026-10-04. 사용자 진행 지시에 따라 추천 AD1의 유한 범위 제어기·가변 슬롯·필수 테스트를 구현했다. [실제 구현·검사·AD2 경계](adaptive-ad1-results.md)를 우선한다. 아래 초기 수치는 로컬 제어기 검증용으로 적용했으며 최적값이 아니다. 실제 이미지 연결·15회 성능 실험·원격 배포는 미실행이다.

## 목적·범위

같은 1 CPU·2GiB에서 정적 슬롯보다 처리량·첫 브랜드 완료·메모리·실패/중단이 개선되는지 확인한다. 재사용128MiB, 고정 입력·품질·JPEG 규격·재시도 총5회·종료 정리·중단 기준을 유지한다. 비용0이나 최적값을 보장하지 않는다.

새 후보 명칭은 `R(resource-adaptive)`로 제안한다. 이전 로컬 A~F의 A 또는 R4와 구분한다. 첫 R은 P와 같은 브랜드 병렬·시즌 최대6을 유지하고 이미지 투입과 단계별 동시성만 바꾼다. 시즌 최대6은 이 유한 입력 비교의 조건이며 제품 최적값이 아니다. S+자동 조절이나 시즌 접수 수 자체의 자동 조절은 별도 후보로 남긴다. 기존 F의 유한 입력 전체 제출은 피드백 제어의 검증이 아니다.

작업을 전부 실행한 뒤 취소하는 대신, 대기 중 작업의 **시작 허용량**을 조절한다. 감소 시 이미 실행 중인 변환/SDK 요청을 강제 종료하지 않고 종료를 기다린다. 안전 중단·외부 취소는 기존 abort/drain 규칙이 우선한다. 적용 범위는 실험 Runtime 하나를 공유하는 모든 시즌이다. 다른 Cloud Run 인스턴스까지 합산하는 제품 분산 제어는 아니다.

## 제어 설계 추천안

처음부터 무제한을 허용하는 안은 반응 전에 여러 변환이 시작될 수 있다. 먼저 **유한 범위에서 점진적으로 늘리고 압박 시 줄이는 제어기**를 검증하는 안을 추천한다. 장점은 과부하와 진동을 재현하기 쉽다는 점이며, 단점은 짧은 시즌에서는 증속 전에 끝날 수 있고 임시 상한이 최적값을 가릴 수 있다는 점이다. 각 상한 도달 시간·대기량을 기록해 후속 범위 확대의 근거로 쓴다.

아래 수치는 **AD1 로컬 제어기 검증용 초깃값**으로 적용했다. 실측 최적값이나 실제 이미지 처리의 메모리 안전 보장이 아니다.

| 항목 | 시작·범위 제안 | 의미 |
| --- | --- | --- |
| 다운로드 | 4, 1~16 | 해시용·저장용·커버 요청을 모두 합산 |
| 변환 | 1, 1~4 | 이미지 수가 아니라 썸네일/상세 각각의 sharp 호출 수 |
| 업로드 | 4, 1~16 | 모든 이미지의 두 출력 파일을 합산 |
| 전체 미완료 이미지 | 4, 1~24 | 시즌당4를 제거하고 공용 허용량 사용. 시작부터 두 파일·경로 저장·정리까지 보유 |
| 경로 저장 | 별도 개수 제한 없음 | 미완료 이미지 허용량·메모리·전체 timeout의 적용은 받음 |
| 관찰/결정 | 100ms 표본, 2초 창 | 기존 메모리100ms·500ms 누락 중단과 분리하지 않고 공통 표본 사용 |
| 증속/관찰 | 한 번에 한 축 +1, 변경 후 최소4초 관찰 | 동시에 여러 축을 바꿔 개선 원인을 잃지 않음 |
| 메모리 사전 제동 | 75%부터 새 이미지·다운로드 투입 보류, 65% 미만이1초 유지되면 재개 | 기존85% 이상1초 중단보다 먼저 반응. 75%가 OOM 방지 보장은 아님 |

결정 순서는 안전 중단 → 압박에 따른 투입 보류/감속 → 변경 결과 관찰 → 증속이다. 메모리 압박 때 업로드와 경로 저장은 계속 진행해 이미 만들어진 결과를 배출한다. 변환은 폭1로 줄여 이미 입장한 이미지의 완료를 진행하되, 예상 작업 메모리를 수용할 수 없으면 시작하지 않는다. 이때 처리 가능한 작업 없이 보유량만 남으면 대기 이유를 기록하고 회차 timeout으로 중단한다. 안전 기준을 완화해 탈출하지 않는다.

증속은 해당 대기열이 있고, 하류의 보유 데이터가 증가 중이지 않고, 메모리 admission을 통과할 때만 허용한다. 한 축을 늘린 뒤 같은 단계의 유효 bytes/초(변환은 출력 pixels/초)와 작업 실행 지연을 이전 창과 대조한다. 최소4개 완료 표본이 없으면 판정을 보류한다. 임시 기준은 처리량5% 이상 증가·실행 지연 중앙값10% 이상 악화 없음·새 오류 없음이면 유지, 아니면 이전 폭으로 복귀다. 마지막 입장 후 남은 입력이 적으면 증속을 멈춘다. 이 비교는 서로 다른 이미지·네트워크 편차의 영향을 받으므로 인과적 성능 증명으로 쓰지 않는다.

다운로드/업로드는 bytes·활성 요청 시간·타임아웃/429/5xx·대기 bytes를 본다. CPU가 높다는 이유만으로 네트워크를 일괄 축소하지 않는다. 변환은 CPU 포화·throttling·sharp 대기·출력 처리량을 함께 본다. 초기 CPU 증속 조건은 최근 창의 정규화 사용률80% 미만을 제안하며, CPU가80% 이상이어도 실행 폭을 자동 축소하지 않는다. 네트워크 일시 오류는 해당 단계의 폭을 절반(최소1)로 줄이는 안을 제안하고, 원본 불일치·인증·데이터 손상은 동시성 문제로 재해석하지 않고 기존 중단 규칙을 따른다.

단계가 늘어날 자격이 여러 개면 이미 보유한 데이터를 줄이는 업로드 → 변환 → 다운로드 → 새 이미지 투입 순으로 한 축씩 탐색한다. 변경 전후 조건·표본·사유·제한값·실제 active·queued·되돌림을 기록한다. 특정 단계의 기아 여부도 테스트한다. 이 순서는 제어기 정책이며 최종 제품 채택 규칙이 아니다.

## 메모리 추정과 계측의 한계

메모리 표본만으로 다음 sharp 호출의 native 메모리를 정확하게 예측할 수 없다. 압축 파일 bytes 또는 `width×height×channels`를 전체 사용량의 상한으로 취급하지 않는다. 공유 캐시128MiB 또한 전체 메모리 한도가 아니다.

구현을 분리한다. 먼저 AD1에서 제어기와 `canAdmit` 메모리 예산 경계를 fake로 검증한다. 다음 AD2 연결 설계에서 기존 로컬 원본의 **원본 해상도·채널·포맷**과 단일 변환의 증분 메모리를 측정해 예약 추정과 여유값을 제시한다. 현재 fixture의 출력 width/height를 원본 크기로 사용하지 않는다. 표본에 이미 반영된 사용량과 미반영 예약을 이중 합산하거나 native 메모리를 누락하지 않는 회계·실패 시 반환 규칙을 확정한 뒤 이미지 연결을 구현한다. 준비 측정 횟수는 그 실행안에서 산출한다.

CPU는 제어 대상과 같은 cgroup의 누적 CPU 사용량 차이를 wall time·실효 CPU 할당량으로 정규화하고 throttling을 별도 기록한다. cgroup v2/v1/Cloud Run에서 읽을 수 있는 경로와 단위는 환경 준비 검사로 확인한다. 읽기 실패·counter 역행·할당량 변경·표본 지연을 0%로 취급하지 않는다. 미지원이면 R을 환경 미검증으로 중단하고 P로 조용히 바꿔 성공 처리하지 않는다.

근거: Linux [cgroup v2 공식 문서](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)는 CPU 사용/제한과 컨테이너 메모리 계측 필드를 설명한다. [sharp 공식 문서](https://sharp.pixelplumbing.com/api-utility/)의 concurrency는 이미지별 libvips 스레드 설정이고 counters는 libuv 대기/처리 상태다. 앱의 변환 슬롯과 같은 값으로 해석하지 않는다. 이번 비교에서는 sharp/libuv 스레드 설정을 함께 바꾸지 않는다.

## 비교 행렬 변경 제안

1. 로컬 필수 게이트와 계측·예약 준비 검증 후, **일반3브랜드×2시즌에서 P/S/R 각5회=15회**를 먼저 비교한다. 코드·계측 변경이 있으므로 과거 P/S20회 결과를 새15회의 대조군으로 재사용하지 않는다.
2. 로컬 대용량 입력은 원격에 없으므로 별도 압박 확인으로 둔다. 반복 횟수는 준비 검사 결과와 비용을 보고 정하며 15회에 숨겨 포함하지 않는다. R을 Development로 넘기기 전 압박·취소·정리 검증은 필요하다.
3. 로컬 준비를 통과하면 Development도 우선 **실제 원본 기반 합성3브랜드×2시즌에서 P/S/R 각5회=15회**를 제안한다. 동일 사이트를 세 브랜드로 나눈 부하이며 서로 다른 호스트 검증은 아니다. 총45회·2시간·추정US$10 상한은 늘리지 않는다.
4. 단일 시즌/동일브랜드6시즌은 이후 유력 후보 회귀 확인으로 분리한다. 추가 회차를 자동 실행하지 않는다. 기존30회 요청량 표는 역사적 계산이며 새15회 비용표로 재사용하지 않는다.

각 반복 안에서 세 후보 순서를 회전하고, 순서와 대조군을 결과 확인 전에 manifest로 고정한다. R 대 P, R 대 S를 모두 제시한다. 기존5회 반복 악화식·중앙값10% 개선 우선·정확성/실패율 전제 유지. 전체/첫 시즌/등록 순서별 브랜드 완료, 사용량·중단·오류·bytes/재시도, 동시성 궤적·증감 횟수·상한 체류를 기록한다. 준비·성공·실패·중단·미수행을 분리하고 좋은 회차만 골라 비교하지 않는다.

AD1 필수 AP01~08을 작성·연결·실행했다. 범위/잘못된 표본, 감속/재개, 한 축 증속/최소표본/복귀, CPU 포화, 메모리 제동/하류 정리/예약 거절, 취소/실패/슬롯 반환, 시즌 우선순위/맥락/유한 입력 완료, 결정 trace 및 P/S 불변을 검사한다. [실제 결과](adaptive-ad1-results.md)를 따른다.

단위 테스트는 주입 시각·resource samples·barrier·메모리 admission fake로 결정적으로 실행했다. `verification/lookbook-import.json`에 새 필수 ID를 연결해 Mac/Linux 게이트를 통과했다. 실제 CPU/네트워크 성능 개선의 근거는 아니다. 원격 계약을 바꾸는 AD4에서는 emulator 필수 검증도 다시 실행한다. UI 자동 테스트는 추가하지 않는다. 실제 IAM·원격 계측·비용·사이트 변화는 Development 준비 확인 대상이다.

## 결정 상태와 다음 범위

- 제어 방식: 사용자 진행 지시로 유한 범위 점진 조절 AD1을 적용했다. 개수 상한 없는 예측 admission은 이번 AD1에 포함하지 않았다.
- 첫 비교는 일반3브랜드 P/S/R15회부터라는 추천 방향을 유지한다. 실제 성능 실행 전 AD2 준비·예약 설계와 실행 manifest를 먼저 확인한다. Development 회차와 준비 규모도 배포 승인 전 따로 확정한다.

최종 제품 정책이나 안전 상한을 채택한 문서가 아니다. 기존278개/필수170개·emulator4개 통과는 D0~D3 코드에 대한 결과이며 R의 검증으로 인용하지 않는다.
