# 로컬 Linux 컨테이너 비교 실행안 — 검토본

**후속 상태(2026-10-03):** 사용자 승인 후 Docker Desktop/Linux ARM64·고정 이미지를 준비했고, 측정기 보완과 준비 18회·본 54회를 완료했다. 본 결과 48성공/6메모리 중단, Mac/Linux 207개/필수 99개 통과. [최신 결과·원본·후속 추천](phase-3-comparison.md)을 우선한다. 아래는 설치 전 제안 당시의 이력이며 현재 승인·실행 상태가 아니다.

2026-10-03. 사용자는 컨테이너 환경을 임의 설치하기보다 실행안을 먼저 제시하는 선택을 했다. **이 문서는 제안이며 Docker 설치, 이미지 빌드, 54회 실행 승인을 완료했다고 취급하지 않는다.** 기존 로컬 코드 구현과 필수 게이트는 승인 범위로 계속 진행했다. [최신 결과](phase-3-runner.md).

## 확인한 환경과 추천

현재 실행 환경은 Darwin/arm64다. PATH에서 Docker·Podman을 찾지 못했고 `/Applications`에서 Docker/OrbStack/Podman/Rancher 이름을 찾지 못했다. 모든 사용자 경로의 설치 부재를 증명한 것은 아니다. 현재 Mac에서 cgroup 메모리를 읽을 수 없어 합의한 컨테이너 85%/1초 조건을 검증할 수 없다. 호스트 CPU 개수/메모리는 sandbox의 sysctl 접근 제한으로 확인하지 못했다.

**Docker Desktop의 Apple Silicon용 설치와 네이티브 Linux/ARM64 컨테이너를 추천한다.** 프로젝트 Worker에 기존 Dockerfile이 있으므로 이를 바탕으로 같은 Node 24·의존성·sharp를 고정하기 쉽다. Mac용 설치와 시스템 요구 사항은 [Docker 공식 안내](https://docs.docker.com/desktop/setup/install/mac-install/)를 따른다. 지원 macOS와 메모리 여유는 설치 전에 확인하며, 약관 동의·계정 계약은 사용자가 확인한다. 설치 크기·빌드 소요 시간은 현재 측정하지 않아 잘 모르겠습니다.

대안은 이미 사용하는 Linux 호스트/컨테이너 환경을 지정하는 것이다. 별도 Mac 도구 설치는 줄지만 로컬 비교 장소가 달라지고 접근·파일 동기화 준비가 필요하다. Mac 프로세스 RSS만으로 대신 비교하면 합의한 컨테이너 기준과 달라져 이번 실행안에서 추천하지 않는다.

## 실행 조건 제안

| 항목 | 제안 | 이유/검증 |
| --- | --- | --- |
| 구조 | 컨테이너 한 개씩, 회차 간 병렬 실행 없음 | 다른 실험과 CPU·메모리 경쟁 분리 |
| 플랫폼 | Linux/ARM64 네이티브 | 이 Mac에서 에뮬레이션 비용을 구조 차이와 섞지 않음. 클라우드 절대 시간과 같다고 보지 않음 |
| CPU·메모리 | `--cpus=1 --memory=2g --memory-swap=2g` | Development 1CPU·2GiB 비교안과 자원 상한을 맞춤. quota와 cgroup 값 실제 확인 |
| 런타임 | 기존 Worker Dockerfile 기반 Node 24, lockfile npm ci, 이미지 ID/digest 고정 | ARM Linux sharp/libvips 및 Node 버전을 결과에 기록 |
| 네트워크 | 자료 준비 후 측정 컨테이너 `--network=none` | 고정 자료와 fake Storage/Firestore로 로컬 구조를 비교. 실제 대역폭 검증은 Development |
| 입력 | 이미 고정한 HTML·이미지 약 107.55MiB, 입력 hash 재검사 | 원 사이트 재수집 없음 |
| 출력 | 실험 전용 로컬 output만 쓰기 가능, 원본 read-only | 기존 자료·사용자 코드 오염 방지 |
| 메모리 감독 | 100ms 표본, 85%/1초 중단, 최대 표본 간격 500ms 제안 | 500ms는 아직 미채택 기준. 누락을 정상으로 간주하지 않고 환경 중단 |
| 외부 감독 | 회차 시작 기록을 먼저 저장하고 종료 코드/OOMKilled/완결 결과를 대조 | 컨테이너 내부 로그가 사라져도 중단을 성공 분모에서 숨기지 않음 |

Docker는 CPU quota와 메모리 제한을 지정할 수 있고 memory와 memory-swap을 같게 설정하면 swap 사용을 막는다. 실제 지원 여부는 실행 환경에서 확인한다. [공식 자원 제한 문서](https://docs.docker.com/engine/containers/resource_constraints/).

기존 Dockerfile은 HTTP 서버 실행용이며 전체 테스트 runner를 runtime에 포함하지 않는다. 전용 로컬 실행 entry와 gate용 build 단계 준비가 추가로 필요하다. Mac의 node_modules를 Linux 컨테이너에 재사용하지 않는다. 입력을 컨테이너 로컬 파일로 준비하고, Mac bind mount 읽기 비용이 측정에 섞이는 범위를 기록한다. 의존성 이미지 내려받기·빌드 때는 네트워크가 필요하며 측정 중 외부 API 호출은 없다.

## 입력·회차와 부하

한 브랜드 2026 SS 1시즌 / 한 브랜드 6시즌 / 세 합성 브랜드 각각 2시즌을 사용한다는 검토안을 유지한다. 세 번째는 같은 여섯 시즌을 나눠 배정하는 것으로 실제 세 원격 호스트의 성능을 뜻하지 않는다. 브랜드별 배정·시즌 순서·A~F 초기 동시성 조합은 **실행 manifest에 명시해 검토한 뒤 고정**한다. 현재 단위 테스트의 4/2/4/1 및 batch 8을 자동 채택하지 않는다.

6구조×3부하×3회 = 54회. 한 회차에서 실제 추출→검토 대기와 승인 후 저장을 분리된 구간으로 기록하고 사람 대기 시간을 합산하지 않는다. 입력의 needsReview 판정을 우회해 자동 등록 성공이라고 기록하지 않는다. 구조 비교는 재사용 off다.

재시도 없는 54회 합계의 로컬 원본 읽기는 10,782회 상당/8,148,833,838 bytes, 업로드는 10,980파일 상당/1,563,717,618 bytes다. [입력 산출 근거](input-manifest.md). 실제 외부 GET/Cloud Storage 업로드는 0인 로컬 재생안이다. 준비 실행, 계측 on/off, 수치 조정, 재사용 비교는 54회 밖이며 **추가 횟수·정확한 실행 순서는 manifest 검토 시 별도로 제시**한다. 아직 전체 실행 시간은 측정하지 않아 잘 모르겠습니다.

프로세스 시작/준비 실행/cold·warm 상태, 입력 준비와 출력 기록 시간을 측정 구간과 구분한다. OS 페이지 캐시를 비웠다고 근거 없이 쓰지 않는다. ARM64 로컬 결과는 구조 후보를 좁히는 근거이며 실제 URL·Storage·Firestore의 네트워크 속도·실패율 채택 근거는 Development 결과를 요구한다.

## 진행 순서와 보류 경계

1. 실행안 확인 후 Docker 설치·시작 및 호스트 자원/약관 조건을 확인한다. 현재 설치하지 않았다.
2. 실행기 연결·바이트 관측·외부 종료 감독·회차 manifest를 완성한다. 코드와 필수 게이트 갱신은 기존 승인 범위다.
3. 입력·이미지 ID·1CPU/2GiB·swap·cgroup 접근·간격 표본을 preflight로 확인하고 Linux 게이트를 실행한다. 안 되면 환경 미준비로 기록한다.
4. 준비 실행과 초기 수치/추가 회차를 검토한 뒤 54회를 실행한다. 중단/오류/OOM/누락은 결과에 남긴다. 3회 탐색을 5쌍 반복 악화 판정에 억지 적용하지 않는다.
5. 결과 분석으로 후보를 좁혀 Development 실행안을 별도로 제시한다. 이번 로컬안은 클라우드 배포·과금 실험을 포함하지 않는다.
