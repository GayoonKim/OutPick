# C 변환 1·2의 세 부하 다섯 쌍 확인

2026-10-03. 사용자의 ‘추천안으로 진행’으로 [12회 대조 후 추천](phase-3-transform-sweep.md)의 추가 30회를 승인받았다.

**완료:** Mac/Linux 213개·필수 105개 통과, 30/30회 성공, 원본 재집계 일치. 세 부하 모두 전체·첫 시즌 10% 이상 악화 쌍 0/5, 반복 악화 보류 조건 없음. 1/2 시간 차이는 0.36~2.38%로 작고 다중 시즌의 메모리 여유가 더 큰 변환 1을 우선 후속 후보로 유지한다. 제품 기본값·클라우드 최적값 확정은 아니다.

## 범위와 완료 기준

- C 구조의 변환 1(후보)·2(기준선), 기존 single/six/synthetic-three 3부하, 각 5회로 총 30회다. 같은 부하/반복 번호의 두 실행을 인접한 쌍으로 배치하고, 각 부하에서 매 반복 실행 순서를 뒤집는다. 부하 순서도 반복마다 회전한다.
- 다운로드 4/업로드 4/경로 제한 없음/시즌 병렬 폭 6/재사용 off/기존 이미지별 두 출력/원본 입력과 품질 판단은 유지한다. 단일은 2026SS, 다중은 2026FW부터 시작하는 기존 순서다.
- 새 이미지에서 1과 2 모두 재측정하고 기존 12회·54회 표본과 합치지 않는다. 각 회차는 새 Linux ARM64 컨테이너, 1 vCPU·2GiB·swap 없음·네트워크 없음, 읽기 전용 Linux 입력, 무결성 검사 후 측정이다. cold-cache라고 부르지 않는다.
- 100ms 표본/500ms 초과 환경 중단/85% 이상 1초 메모리 중단은 유지한다. 메모리 중단은 해당 회차 분모에 남긴다. 정합성/환경 실패 시 후속 실행을 보류한다.
- 판정은 부하별 전체 시간(분리된 두 구간 합)과 첫 입력 시즌의 **승인 후 저장 구간 완료 시간**을 각각 5쌍 비교한다. 이전 결과의 첫 시즌 지표 정의를 유지한다. 추출→검토 첫 시즌 시간은 원본에 남으며 새로운 별도 자동 채택 기준으로 추가하지 않는다.
- ‘3쌍 이상 10% 느림 + 중앙값도 10% 느림’이면 해당 지표 악화로 후보 1의 채택을 보류한다. 성공한 완전한 5쌍이 없으면 악화 없음으로 바꾸지 않는다. 부하별 실패/중단을 유지하고 성능 결과와 함께 검토한다. 로컬 판정 통과는 제품 기본값이나 클라우드 최적값 확정이 아니다.

## 구현 계획과 검증

변경 범위: Worker `src/performance/comparison.ts`, `comparison-report.ts`, 새 `transform-confirmation-report.ts`, `transform-confirmation.test.ts`, 필수 게이트 설정과 관련 하네스다. 기존 고정 입력/컨테이너 감독/공용 PipelineRuntime을 재사용한다. 앱 DI·Coordinator·화면, Firestore/API, 제품 기본 동시성 변경은 없다.

`makeTransformConfirmationPlan`과 명시적 experiment 값으로 30회를 식별하고 이전 12회/54회와 엄격히 분리한다. 다른 축 변경·다섯 쌍 초과·변환 4/null을 거절한다. `summarizeComparisons`는 5회씩 집계하며 전용 `summarizeTransformConfirmation`은 부하와 반복 번호로 짝을 재구성해 결과 파일 읽기 순서에 영향을 받지 않는다. 첫 입력 시즌 ID·구간·유효한 완료 시간도 검증한다.

추가 필수 테스트 3개는 30회 계획/교차 순서/기존 계약, 전체 시간은 같아도 첫 시즌 악화 시 보류, 중단·누락·잘못된 첫 시즌·이전 표본 혼입을 검증한다. 실제 실행기와 fake memory/비동기 callback을 사용한다. 전체 구성 213개/필수 ID 105개이며 Mac/Linux 게이트 후 실제 30회 JPEG 정합성·메모리 감독·종료 증거를 확인한다. UI/실제 Storage/Firestore 검사는 이번 로컬 범위 밖이다.

완료 기준은 새 코드의 두 환경 필수 게이트 통과, 계획 30회 결과 또는 중단/미실행 명시, 실패 분모·완전한 쌍 검증, 원본/source/input/settings/image 일치, 결과 분석과 하네스 갱신이다. 결과는 아래에 이어 기록한다.

## 판단과 남은 범위

**C 구조의 공용 변환 1을 우선 후속 후보로 유지한다.** 세 부하에서 반복 악화가 없고 다중 시즌의 관측 메모리 여유가 더 컸다. 2 대비 10% 속도 개선을 달성한 것은 아니며, 1 CPU/2GiB/이 고정 자료에서 비슷한 처리 시간과 메모리 여유를 함께 고려한 추천이다. 이전 54회에서 본 C 대 A의 개선율과 이번 1 대 2의 개선율은 서로 다른 실험이므로 합치지 않는다.

이번 구현은 비교 계획·집계/판정·테스트에 한정했고 제품 동시성 기본값이나 재시도 계약을 바꾸지 않았다. 다운로드/업로드 4의 최적성, 실제 네트워크/Storage/Firestore 성능·실패율, 더 많은 CPU·다른 크기 이미지의 최적값은 미검증이다. 30회 실패 0은 이 로컬 조건의 관측값이지 실제 운영 실패율 보장이 아니다.

다음 순서는 같은 실행 다운로드 재사용을 별도 축으로 비교하는 실험 입력·회차 구체화다. 기존 원본 합계 약 112.8MB가 128MiB보다 작아 128/256/512/전체 보관 간 예산 차이를 확인하기 어렵고, 실제 입력이 needsReview여서 자동 등록까지 이어지는 재사용 효과와 분리해야 한다. 이 제약을 명시한 추가 부하·실험 규모를 검토한 뒤 실행한다. Phase 4의 제품 job 총 5회 claim 계약과 Phase 5의 Development 대상/격리/실행안 검토도 남아 있다. 클라우드 배포·실험·쓰기·커밋은 이번 단계에서 수행하지 않았다.
