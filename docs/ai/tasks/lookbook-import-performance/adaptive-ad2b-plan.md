## 목표와 유지 조건

같은1CPU/2GiB·원본 재사용128MiB에서 자동 조절 제어기 R을 실제 해시·JPEG·저장 경로에 연결한다. 공용 이미지 입장 허용량과 메모리 예약을 함께 적용하고, 예약이 끝나기 전에 실제 소비자가 종료되도록 한다. 실제 사용량과 예약량은 별개로 기록한다.

기존 P/S 입력·출력·시즌 실행 순서·준비된 시즌 변환 우선순위, 원본 검증/중복 제거 장벽, 두 변환 뒤 업로드·두 업로드 뒤 경로 저장, 최초 포함 시즌5회와 내부 읽기 재시도 계층은 유지한다. R은 첫 설계대로 브랜드 병렬·시즌 최대6, 단계 시작4/1/4·이미지4와 기존 탐색 상한을 쓴다. 경로 저장에 새 개수 제한은 넣지 않는다. 앱/DI/제품 API·Functions·rules·배포 인스턴스 수·실제 원격30회 계약은 변경하지 않는다.

이번 완료 기준은 연결의 정합성과 중단/정리 검사다. 실제 처리량 향상·최적 수치 채택은 AD2c의 같은 계측을 적용한 비교 뒤에 판단한다. AD2a18회와 과거 P/S 실측을 새 R 성능 대조군으로 재사용하지 않는다.

## 결정 대기 1 — 초기 예약 프로필

추천 후보는 `Eimage = 256MiB + 2×B + J`다. B는 고정 manifest의 압축 원본 bytes, J는 해당 원본·종류·품질에서 기존 golden에 기록된 두 JPEG bytes 합계다. 커버도 같은 프로필을 사용해 먼저 검증하며 크기별 계수 학습은 추가하지 않는다. 캐시 hit도 첫 버전에서는 예약량을 줄이지 않는다.

256MiB는 단일 관측 최대194.67MiB 대비 약1.315배인 **검증용 변환 여유 제안**이다. 이 비율이 통계적으로 검증된 안전계수라는 뜻은 아니다. AD2a 단일 조건은 순차2변환이었고 중첩 조건은 최대 픽셀 원본2장만 확인했으므로 모든 이미지의 두 변환 중첩·오래 실행한 프로세스·HTTP/Storage SDK를 포괄하지 않는다. B/J를 더하는 것도 AD2a 관측값 일부와 겹칠 수 있는 의도적인 보수성이다.

대안은 변환 여유512MiB다. 더 보수적이지만 `M+R+E <=1536MiB`에서 양의 B/J까지 넣으면 새 프로세스에서도 대체로 이미지2개 이하만 입장할 수 있다. 그러므로 이를 곧바로 성능 최적 후보로 채택하는 것은 추천하지 않는다. 실제 압박 검사 실패 시 회차를 보존하고 별도 프로필로 비교하며 실행 도중 값을 자동 변경하지 않는다.

원본 전용 읽기 예약은 `Eread=2×B`다. 수신 chunk와 concat 원본이 겹칠 가능성을 반영하는 논리 수신 예산이며 Node/SDK 전체 할당의 보장 상한이 아니다. 프로세스/native 잔류·기타 비용은 실제 M과75% 입장 기준·85% 지속 중단으로 함께 관찰한다. 현재 고정 입력은 B가 사전에 확인되며, 알려지지 않은 원본을 임의로 이 프로필에 넣지 않는다.

원본 hash·bytes·헤더·단일 프레임·변환 옵션·라이브러리/아키텍처를 기존 계약과 묶은 별도 프로필 digest를 만든다. 실제 bytes/hash/두 출력이 계약과 다르면 해당 실행은 실패/중단하고 새 원본을 자동 채택하지 않는다. 이 메모리 프로필은 제품의 임의 URL 이미지에 적용하는 일반 상한이 아니다.

## 결정 대기 2 — 커버 준비와 예약 확대

추천은 기존 선준비를 유지하면서 준비할 때 `2B`만 예약하는 것이다. 준비 완료 뒤 출력이 없는 원본 보유 토큰은 B로 축소할 수 있지만, 줄인 금액은 다음 유효 cgroup 표본을 받기 전에는 재사용하지 않는다. 커버가 저장 차례에 들어가면 **기존 토큰에서 Eimage로의 증가분과 이미지 슬롯을 같은 pump에서 승인**한다. 기존 B를 중복 예약하거나 원본 토큰을 먼저 버리고 다시 받지 않는다.

확대 대기 중에는 이미지/다운로드/변환 슬롯을 잡지 않고 준비 원본 B만 보유한다. 준비 원본을 소비하는 기존 코드 순서는 유지한다. 메모리 제동 중 미확대 커버는 새 이미지이므로 대기하며, 전체 예약을 이미 받은 커버는 다른 이미지와 같이 정리를 진행한다. 취소 시 미시작 커버 참조·토큰도 정리한다.

대안은 커버의 저장 차례에 다운로드하는 방식이다. 원본 장기 보유는 줄지만 이전 커버 선준비와 비교 조건이 바뀌고 첫 시즌 완료에 다운로드 지연이 다시 들어올 수 있다. 사용자 답변 전 둘 중 하나로 구현하지 않는다.

## 예약·입장·반환 계약

1. 공용 admission이 이미지 슬롯과 예약을 함께 관리한다. `M + R + Enew <= 0.75L`, 유효 표본 나이500ms 이하, 입장 허용 상태, 현재 이미지 active<목표를 모두 만족할 때만 동기적으로 토큰을 만든다. 대기자에 Buffer를 미리 읽어 주지 않는다.
2. R은 살아 있는 예약과 다음 표본까지 반환을 보류한 금액의 합계다. 새 표본 사이에 작업이 빠르게 끝났다고 같은 예산을 여러 번 재사용하지 않는다. 토큰의 소비자 종료 시각보다 뒤의 새 유효 표본을 받은 뒤에 보류 금액을 제거한다.
3. M에는 이미 사용 중인 예약 일부와 캐시가 들어 있을 수 있다. 이 겹침은 보수적 입장 판단으로 명시하며 RSS/논리 bytes/캐시 예산을 M에 또 더하지 않는다. `actualMemory`, `liveReservation`, `awaitingSampleRelease`, `rejectedReason`을 구분한다.
4. hash 읽기/커버 선준비도 원본을 받기 전에 예약한다. 원본을 cache로 넘겼더라도 완료 뒤 다음 표본까지 반환을 보류한다. cache 객체의 보유/대여 수명은 기존 `SourceBufferScope`가 관리하며 reservation ledger가 cache를 임의 삭제하지 않는다.
5. 이미지 전체 예약을 받은 뒤 cache miss 재읽기·두 변환·업로드·경로 저장은 같은 토큰으로 진행한다. 다시 메모리 입장을 기다리면서 기존 이미지 슬롯을 점유하는 단계별 교착을 만들지 않는다. 각 단계의 실행 슬롯은 해당 작업 동안만 보유한다.
6. 이미지 토큰은 형제 변환/업로드, 경로 저장, 실제 원본 lease 소비 종료 뒤 반환한다. 실패/취소 때도 실행 중 native/SDK 작업 종료까지 기다린다. 내부 요청 재시도는 같은 토큰, 시즌 재시도는 이전 시도 정리 후 새 토큰이다.
7. 잘못된 소유자·이중 확대·반환된 토큰 사용·예약량 역행은 불변식 오류로 기록하고 중단한다. 반환 함수 자체는 finally 중복 호출에도 금액을 두 번 차감하지 않는다. 정상 종료 때 active 작업/토큰/대기/캐시 scope가0인지 확인한다.
8. 새 유효 표본과 실제 작업 완료만 admission pump를 깨운다. 무한 폴링이나 강제GC는 넣지 않는다. 아무 작업도 실행 중이지 않아도 잔류 M 때문에 입장할 수 없으면 대기 사유를 기록한다. 기존 실행기가 전달한 전체 deadline에서 중단하며 새5분 규칙이나 시즌 시도 횟수 변경을 추가하지 않는다. AD2c 실측 timeout은 해당 실행안에서 고정한다.

## 제동·CPU 준비·단계별 관측

- 75% 제동은 신규 이미지/hash/미예약 커버 입장을 막는다. 이미 예약한 작업의 필수 다운로드는 기존 공용 다운로드 목표 폭 내에서 끝낼 수 있다. 제동 전에 예약한 hash 읽기도 완료/보관 인계를 정리한다. 미예약 다운로드는 이 예외에 들어갈 수 없다.
- 새 입장 허용과 다운로드 stage limit를 별도로 표현한다. 다운로드 슬롯을 무조건0으로 만드는 기존 AD1 출력은 보완하되, 모든 R 읽기에서 유효 소유 토큰을 검사한다. 변환은1로 감속하고 업로드·경로 저장은 정리를 계속한다.85%1초/표본500ms 초과/취소/원본 불일치는 우선해서 전체 abort한다.
- CPU 준비 전에는 `cpuReady=false,cpuRatio=null`로 기록하고 증속 탐색을 보류한다. 이미 확인된 메모리 표본과 초기 폭으로 작업은 시작할 수 있다.2초 이후 정상 측정값이 준비되지 않거나 한번 준비된 CPU가 미준비로 돌아가면 환경 오류다.0%로 대체하지 않는다.
- 공통100ms 표본 하나를 ResourceFeed와 제어 판단에 사용한다. 제어기의 기존 누락/85% 감시는 같은 시각/값을 받으며 별도 파일 읽기나 다른 시계로 경쟁하지 않는다. 표본 전 새 작업 시작 시에도 시각 유효성을 검사한다.
- queue/start/end를 단계 바깥/실제 실행 callback/정리 뒤로 나눠 기록한다. 다운로드·업로드 bytes, 변환 출력pixels, 전체 경로까지 완료한 이미지 수를 구별하며 CPU/완료 이벤트를 중복 전달하지 않는다. 오류와 내부 재시도는 성공 처리량에 더하지 않는다.
- 감속은 이미 실행 중인 작업을 강제 종료하지 않는다. 실행 중 개수가 새 목표보다 큰 구간은 기록하고 새 시작만 막는다. `canAdmit` 요약은 실제 예약의 대체가 아니다.
