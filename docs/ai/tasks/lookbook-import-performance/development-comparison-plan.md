## 1. 이번 단계에서 답할 질문

동일한 1 CPU·2GiB와 고정 단계 제한에서, 여러 브랜드를 함께 시작하는 P와 한 브랜드의 모든 시즌 저장·정리 뒤 다음 브랜드를 시작하는 S 중 실제 이미지 다운로드·Storage 업로드·Firestore 경로 기록을 포함했을 때 어느 쪽이 나은가?

- [로컬 20회](phase-3-brand-fifo-results.md)는 속도 차이가 작고 S의 메모리 사용이 적었다. 원격 지연은 포함하지 않았다.
- 이번 비교는 **P 대 S의 구조 효과**다. 기존 배포 제품 전체 대비 개선율이나 CPU·메모리 사용률 기반 자동 동시성 조절의 효과를 증명하지 않는다.
- 제품의 글로벌 브랜드 실행권, 사용 중 추가 시즌 접수, review 이후 대기열 위치, 수동 재시도 예산은 [제품 설계 검토본](phase-4-brand-dispatch-design.md)에 보존하고 이 실험의 선행 구현에서 제외한다.
- 같은 브랜드 내부의 단계 제한은 두 후보 모두 유지한다. S라고 해서 압축·업로드를 무제한 실행하지 않는다.

## 2. 실제 URL 확인과 고정 입력 비교의 경계

**실제 URL 확인:** UNAFFECTED 목록 및 기존 6개 상세 URL에서 현재 후보·순서·해시·품질 결과를 확인한다. 기존 결과는 6개 모두 `needsReview(expected_count_unverified)`다. 원격 변화로 후보/bytes/hash가 달라지면 고정 입력 불일치로 중단하고 새 입력을 검토한다. 비교 도중 기대값을 갱신해 통과시키지 않는다.

**전송 성능 비교:** [기존 입력 manifest](input-manifest.md)의 원격 이미지 URL을 실제 GET한다. 고정된 후보 집합으로 해시 중복 제거 → 메모리 재사용 → 실제 JPEG 변환 → 테스트 Storage 저장 → 테스트 Firestore 경로 기록을 측정한다. 이는 관리자 검토를 통과한 제품 자동 등록이 아니라 실험용 연결 처리다. 제품 공개 시즌·포스트·import job을 만들지 않는다.

기존 실행 내 재사용 승인은 로컬 연결 비교에 대한 것이었다. 이번에는 그 연결 비교를 Development의 격리된 테스트 저장소로 확대하는 제안이며, 실제 검토 대기를 넘겨 메모리 캐시를 유지하는 기능은 추가하지 않는다. 실제 추출의 review 결과와 연결 실험의 성공을 별도 상태로 보고한다.

로컬 대용량 합성 이미지는 원 사이트에 존재하는 원격 파일이 아니다. 이번 첫 실제 URL 행렬에 끼워 넣거나, 다른 저장소에서 읽고 외부 사이트 다운로드 성능이라고 부르지 않는다. 3개 브랜드도 같은 UNAFFECTED 6시즌을 연도별로 나눈 합성 브랜드이며 서로 다른 호스트 성능 검증이 아니다.

| --- | --- | --- |

총 **30회** 제안. 앞의 두 부하는 브랜드 입장 정책상 동일하므로 성능 우열의 주 근거로 삼지 않고 회귀/환경 확인으로 사용한다. 총 45회 상한 중 남은 15회를 자동으로 추가 실행하지 않는다. 환경 확인·실제 URL 확인 등 준비 회차를 포함한 최종 실행 manifest에서 총량을 확정한다.

후보 순서를 교차하고 순서·seed·5쌍 대응을 실행 전에 고정한다. 매 회차 새 Runtime/캐시 scope/실험 ID를 사용하지만 Cloud Run 새 인스턴스나 cold start를 보장하지 않는다. 리비전·이미지 digest·CPU 아키텍처·인스턴스 ID·시작 상태·주변 트래픽을 기록하고 조건이 다른 쌍을 동일 조건으로 판정하지 않는다. 부족한 표본을 임의 추가 회차로 채우지 않는다.

## 4. 원격 연결 구조 제안

`승인된 고정 manifest → 인증된 실험 HTTP 진입점 → 실험 단일 실행권 → P/S 시즌 실행기 → 공용 pipeline → 원격 adapter → 저장 결과 재검사 → 종료 증거`

### 실행 경계

- 대상은 Development `outpick-test`, 버킷 `outpick-test.firebasestorage.app`, Worker 후보 리비전이다. 운영 프로젝트 요청, 다른 버킷, 임의 입력 URL/객체 경로는 거부한다.
- 기존 서비스의 no-traffic 후보 리비전과 전용 tag URL을 검토한다. 현재 서비스 기본 트래픽 URL로 부하를 보내지 않는다. 일반 제품 경로와 실험 경로가 후보에서 함께 실행되지 않도록 실험 전용 모드의 route 차단까지 검증한다.
- 기존 OIDC 검증과 canonical audience를 유지하고 인증된 지정 호출자만 허용한다. 기본 설정에서는 실험 route를 등록하지 않는다. 클라이언트가 임의 pipeline 수치나 운영 경로를 전달하는 API로 만들지 않는다.
- 회차는 한 번에 하나만 시작한다. 별도 실험 제어 문서에서 원자적으로 claim해 중복 HTTP·여러 인스턴스에도 같은 회차를 이중 실행하지 않는다. 제품 브랜드 FIFO와 다른, 유한 실험 캠페인의 단일 실행 제어다.
- `runID`/manifest digest/후보/출력 root를 결합한다. 이미 사용한 runID는 재실행하지 않으며 HTTP 응답 유실만으로 작업을 다시 시작하지 않는다.
- 이전 회차 종료를 확인하지 못하면 **캠페인을 중단**한다. 실험 lease 만료를 자동 인계 근거로 쓰지 않는다. 제품처럼 장애 뒤 계속 서비스를 제공하는 분산 복구 구현을 이번 비교에 요구하지 않는다.
- CPU 1·2GiB 유지, 실험 회차 동시 수 1, 실험 인스턴스는 가능한 후보 리비전 최대 1·최소 0으로 제한하는 실행안을 제안한다. 서비스 전체 설정이나 기존 트래픽 리비전은 바꾸지 않는다. 정확한 revision 수준 설정과 IAM은 배포안에서 확인하며 미지원/불명확하면 실행하지 않는다. 기존 합의의 실험 관련 인스턴스 총 3개 상한도 유지한다.

### 저장 격리

| 저장 대상 | 제안 경로·동작 |
| --- | --- |
| 제어·요약 | `lookbookImportPerformanceRuns/{runID}` 등 서버 전용 새 root. 제품 `brands/.../importJobs`에 쓰지 않음 |
| 실험 시즌·포스트 | 같은 실험 root 아래 준비 문서. 본문 media 배열과 커버 경로를 기록하고 제품과 같은 read/set 형태를 적용 |
| JPEG | `lookbook-import-performance/{campaignID}/{runID}/.../{variant}.jpg`. 제품 `brands/` 경로 금지 |
| 원본 다운로드 | 고정 manifest의 공개 URL만 사용. 기존 SSRF 방어·redirect·파일 크기 제한 유지 |
| 증거 | 요청 수/bytes/단계 시각/해시/원본 오류/메모리/OOM/종료 미확인/미수행을 회차별 보존 |

신규 Storage 경로는 create-only 조건(`ifGenerationMatch: 0`)을 제안한다. 같은 객체가 이미 있으면 무조건 덮어쓰거나 성공 처리하지 않고 요청 중복/응답 유실과 checksum 일치를 구분한다. 이는 객체 이름별 중복 쓰기 보호이며 Worker의 CPU 실행을 중단시키는 장치는 아니다. [Cloud Storage preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

새 root는 현 클라이언트 규칙의 기본 거부 범위에 둔다. Admin SDK는 IAM으로 접근하므로 규칙만으로 서버 오작동을 막았다고 주장하지 않는다. 서버 adapter에서 프로젝트/버킷/root/manifest를 다시 검사하고 테스트한다. 기존 삭제 함수가 실험 경로를 정리할 것으로 가정하지 않는다. 생성한 정확한 manifest에 기반한 삭제 실행은 별도 승인이다.

## 5. 측정·정확성·중단

- 측정 시작은 manifest/권한/환경 확인과 테스트 문서 준비 뒤, 첫 시즌 이미지 처리 시작 직전이다. 끝은 마지막 대상의 두 JPEG 업로드·경로 기록·실행 scope 정리 뒤다. 초기 접수·queue 지연·HTML 추출·문서 준비·사후 검사는 따로 기록한다.
- 다운로드는 로컬 파일이나 이전 회차 캐시를 쓰지 않는다. 원격 원본 bytes/hash가 고정값과 같은지 확인한다. P/S 같은 sharp/libvips·변환 옵션·출력 검증 기준을 사용한다. 아키텍처 차이로 golden 출력이 달라지면 원인을 확인하기 전 통과시키지 않는다.
- 경로 저장 adapter는 본문 문서 읽기→media 경로 set, 커버 set을 반영한다. 기존 제품 데이터 전체 생성/동기화 비용까지 재현했다고 부르지 않는다. 시험 문서 초기 준비 비용은 별도다.
- 측정 뒤 업로드된 파일을 읽어 bytes/hash와 DB 경로·variant 짝을 검사한다. 이 검사는 성능 시간에서는 분리하되 전체 실행 시간·요청량·비용에는 포함한다. 모든 출력 검증이 끝나기 전 다음 회차를 시작하지 않는다.
- 기존 100ms 표본, 500ms 초과 환경 중단, 컨테이너 85% 이상 1초 중단을 유지한다. Cloud Run에서 유효한 cgroup 전체 사용량·2GiB 한도를 얻는지 준비 검사로 확인한다. RSS로 대체하거나 미측정을 0으로 기록하지 않는다.
- 새 작업 투입을 멈추고 외부 fetch에 중단 신호를 전달한다. 현재 슬롯 취소는 이미 실행 중인 operation 자체를 취소하지 않으므로 HTTP·변환·Storage·Firestore별 정리 완료를 별도로 추적해야 한다.
- Cloud Run timeout은 프로세스 종료 확인이 아니다. HTTP 응답 유실/timeout/메모리 중단 후 정리 증거가 없으면 캠페인을 멈추고 남은 회차는 미수행이다. [Cloud Run timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout).
- 요청/전체 캠페인 제한과 별개로 시즌 실제 오류 시도는 최초 포함 총 5회를 유지하는 제안이다. 정상 재시도는 같은 회차·후보·입력에 귀속하고 비용/완료 시간에 포함한다. 무제한 SDK 재시도를 허용하지 않으며 내부 다운로드 재시도와 SDK retry 설정을 구현 계획에서 고정한다. 계측 미준비·입력 변동·품질 계약 불일치는 자동 재시도로 정상화하지 않는다.
- 최종 채택 기준은 기존 정확성 유지·실패율 악화 없음·중앙값 10% 개선 우선·5쌍 반복 악화 판정을 유지한다. 표본 부족/조건 불일치는 미판정이다. 구조 차이가 작으면 메모리와 실제 비용을 함께 검토한다.

## 6. 첫 30회 요청 규모 계산 — 무재시도 예시

기존 manifest의 단일 시즌 10회와 전체 6시즌 상당 입력 20회를 합산했다. 실제 계산을 Python으로 재확인했다. 원본 변화·재시도·준비 검사까지 포함하는 최대 과금 상한이 아니다.

| 항목 | 계산값 |
| --- | ---: |
| 본문 원본 재사용이 모두 성립할 때 이미지 GET | 3,070건 / 2,281,567,430 bytes |
| 본문 재사용이 전혀 성립하지 않을 때 이미지 GET | 5,990건 / 4,527,129,910 bytes |
| JPEG 업로드 | 6,100파일 / 868,732,010 bytes |
| 이미지 대상의 경로 기록 | 3,050건 |
| 모든 출력의 사후 원격 읽기 검증 | 6,100 GET / 약 868,732,010 bytes 추가 |

경로 기록 3,050건은 전체 Firestore 요청 수가 아니다. 준비 문서 쓰기, 본문 경로 갱신용 읽기, 제어 문서 transaction·상태·증거·사후 조회가 추가된다. Storage의 SDK 내부 요청, 업로드/다운로드 재시도도 별도다. 실제 URL 확인의 HTML·이미지 요청과 환경 준비 회차 역시 별도로 산출한다.

최종 배포·실행안에는 현행 지역별 가격/무료 잔여 확인 가능 여부, 빌드·Artifact Registry·실행·Storage 작업/보관·네트워크·Firestore·로그 비용의 추정 근거와 중단 제어를 포함한다. 기존 최대 2시간·누적 추정 US$10 기준을 유지하며 정확한 청구 상한 보장으로 표시하지 않는다. 이 문서는 아직 유료 실행 승인 요청서가 아니다.

## 7. 세부 구현 순서 제안

| 단계 | 목표·변경 후보 | 완료 기준·검증 | 결정/의존성 |
| --- | --- | --- | --- |
| D0 계약·입력 | `performance/remote-contract.ts`, 고정 원격 manifest, `remote-contract.test.ts` 후보. P/S 행렬·허용 프로젝트/root·회차 상태 정의 | 운영/임의 URL/중복 runID/경로 탈출/정책 변경 거부, 요청 수 독립 계산 | 30회 행렬·실험용 연결 저장 범위 검토 후 구현 |
| D1 원격 adapter | `performance/remote-input.ts`, `remote-storage.ts`, `remote-results.ts` 후보. 공개 HTTP와 기존 hash/JPEG/pipeline 재사용 | 가짜 HTTP/Storage/Firestore에서 실제 취소 전달, 두 variant 저장 후 경로 기록, 응답 유실·412·해시 불일치·부분 실패 검사 | 제품 processor의 private 함수 공유가 필요하면 작은 공용 함수로 분리, 기존 경로 회귀 필수 |
| D2 실행·인증 | `server.ts`, `config.ts`, `index.ts`, `performance/remote-runner.ts` 후보. 기본 off·개발 전용·한 회차 실행권·증거 기록 | OIDC 거부, 생산환경 거부, 실험 모드의 제품 route 차단, 두 호출 경합·stale 요청·정리 전 재실행 금지 | 원격 root와 인증 계약 확정. 여러 인스턴스 경합은 Firestore emulator로 검증 |
| D3 필수 로컬 검증 | `verification/lookbook-import.json` 및 필요한 실험 emulator 설정 연결. 기존 로컬 결과 회귀 유지 | lint/build/기존 필수 검사/신규 필수 ID/실제 emulator 경합 모두 통과, 소스 digest·원본 로그 보존 | skip/0개 실행/환경 미준비는 미검증. Cloud Run의 실제 계측/권한은 여기서 통과 주장 금지 |
| D4 배포·실험 실행안 | 정확한 리비전 설정, 입력/순서/준비 포함 총 회차, 예상 비용, 라우팅·중단·데이터 manifest | 실행안 사용자 확인 후 후보 배포, 준비 확인 후 본 비교. 모든 실패·미수행 기록 | 현재 단계에서 배포/실행하지 않음 |

같은 server/config/pipeline 경계를 건드리므로 구현은 순차 통합한다. Swift/Functions 제품 요청 API와 제품 대기열을 바꾸지 않는다. 실험만을 위해 새 공용 추상화나 관리자 화면을 추가하지 않는다. 코드 변경 후 ENTRYPOINTS/LOOKBOOK/TESTS와 관련 실행 문서를 함께 갱신한다.

필수 테스트 후보: manifest 고정·P/S 유일 차이, scope 종료 전 브랜드 전환 금지, run 중복/응답 유실, 실제 Firestore claim 경합, root 격리, SSRF/redirect 및 취소 신호, 원본 변동, variant 부분 성공, 조건부 업로드 충돌, 경로 기록 실패, 무재시도/재시도 요청량, 표본 지연/메모리/HTTP 중단, 기록 실패와 미수행 분모. 실제 URL 품질 판단과 관리자 화면은 추후 제품 통합 QA에서 별도로 확인한다.

## 8. 이번 조사 결과와 현재 상태

- `reuse-input.ts::connectedExecutor`가 다운로드와 Storage spy·경로 카운터를 묶고 있어 원격 adapter를 분리할 위치를 확인했다. 해당 함수를 그대로 실행하면 실제 Storage 저장이 되지 않는다.
- `pipeline/resources.ts`는 대기 취소와 operation 시작 직전 취소를 처리하지만 시작한 operation의 중단을 보장하지 않는다. 제품 fetch는 로컬 timeout AbortController를 사용하므로 상위 실험 signal 전달이 추가로 필요하다.
- `processor.ts`의 고정 출력 경로는 늦은 실행의 덮어쓰기 위험이 있다. 이번 실험은 회차별 별도 경로와 create-only 업로드로 격리하고, 제품 경로 변경은 후속 설계에 남긴다.
- 제품의 소유권 만료 복구를 완성하지 않아도, **결과 미확인 시 캠페인 중단**을 적용하는 유한 실험은 설계할 수 있다. 실제 클라우드에서 확인하기 전 가용성/정리 보장을 검증 완료로 보고하지 않는다.
- 위 조사를 바탕으로 D0~D3를 사용자 승인 후 구현하고 필수 게이트를 완료했다. 실제 변경 파일·검증 원본은 [결과 기록](development-connection-results.md)을 따른다. 배포·원격 Firebase 쓰기·실제 이미지 재다운로드는 미수행이다.
