# 부분 재사용 상황의 이미지 제출 순서 설계·구현·45회 결과

2026-10-03. 사용자가 **네 구조·초기 폭4·16/128MiB·공유 off 대조 포함45회** 추천안을 승인했고 구현·Mac/Linux 게이트·45회 로컬 비교를 완료했다. [직전45회 부하·압박 결과](phase-3-load-pressure-proposal.md)와 표본을 합치지 않았다. 아래 대안35회는 미채택 이력이며 최종 판정은 문서 하단을 따른다.

## 문제와 근거

`performance/reuse-input.ts`는 시즌 전체 해시/중복 제거와 커버 원본 준비 후, 본문→커버 목록을 `mapScheduled`에 넘긴다. 현재 `reusePolicy`는 assets 전체 제출, 공용 다운로드4·변환1·업로드4·경로 저장 제한 없음이다. `pipeline/resources.ts`의 대기열은 도착 순 FIFO다.

cache hit 본문은 바로 변환을 제출하지만 miss 본문은 다운로드 뒤 제출한다. 16/32MiB 압박에서 첫 시즌 마지막 본문 제출 사이에 다른 시즌 변환이 각각44~52/34~52건 끼었다. 32MiB 1회차의 마지막 본문은0.334초에 변환을 제출해17.001초에 시작했다. 커버는9.878초에 끝났다. 단순히 커버를 더 앞당기는 것으로는 이 지연을 해결할 수 없다.

현재 첫 시즌 지표는 '어느 시즌이든 가장 먼저 완료된 시간'이 아니라 **입력 첫 시즌 2026FW가 완료된 시간**이다. 측정 의미를 바꾸지 않는다. 다른 시즌별 완료 시간과 실제 최초 완료 시간도 보조로 기록해 첫 시즌만 유리하게 만든 결과를 숨기지 않는다.

## 목적과 유지할 계약

- 시즌들은 기존처럼 최대6개 병렬 시작한다. 이미지 작업을 어떻게 제출할지만 분리 비교한다.
- JPEG 규격·SHA·수량, 본문 순서/대상 ID, 커버 선택, 두 업로드 뒤 경로 저장, 실패·취소 후 형제 종료와 자원 반환을 유지한다. 실행/완료 순서와 화면 표시 순서를 구별한다.
- 재사용 조건은 모두 같은 커버 선준비를 유지한다. 본문→커버 목록을 유지하며 커버를 첫 묶음으로 옮기는 변경은 섞지 않는다. 제한 조건에서는 커버 저장 시작도 뒤로 갈 수 있으므로 본문/커버 종료를 따로 보고한다.
- 원본 전체 선다운로드, 캐시 예산 확대, 변환/업로드 동시성 변경은 이번 축에 포함하지 않는다. 다운로드4·변환1·업로드4·경로 제한 없음은 고정한다.
- 이미지 실행 폭은 다운로드부터 두 변환·두 업로드·경로 저장이 끝날 때까지의 미완료 이미지 수다. 단계별 제한과 다르며, 이 폭을 제품에 채택한다는 뜻은 아니다. 업로드가 느릴 때 다음 변환 제출까지 늦어질 수 있다는 단점도 있다.
- 재사용 보관 예산은 컨테이너 전체 메모리 한도가 아니다. 원본 fallback·선준비 커버·출력 JPEG·native 메모리는 별도다. 해시 단계는 이번 이미지 폭 제한 밖이므로 전체 메모리가 반드시 줄어든다고 보장하지 않는다.

## 비교할 네 구조

| 후보 | 시즌 내부 이미지 시작 | 공용 변환 대기열 | 기대 효과 / 한계 |
| --- | --- | --- | --- |
| U: 현재 대조 | 전체 시작 | 기존 FIFO | 현재 부분 재사용 지연의 재현 기준 |
| R4: 빈자리 보충 | 최대4개, 이미지 하나의 경로 저장까지 끝나면 다음1개 시작 | 기존 FIFO | 대기 중 이미지 폭 제한, 묶음의 느린 한 장을 기다리지 않음 / 여러 시즌이 번갈아 변환해 첫 시즌 종료가 늦어질 수 있음 |
| B4: 고정 묶음 | 본문→커버 순서4개씩, 묶음 전체 종료 후 다음 묶음 시작 | 기존 FIFO | 다음 묶음의 선행 제출 방지 / 묶음 내 느린 다운로드·업로드가 나머지 시작을 막을 수 있음 |
| P4: 빈자리 보충+시즌 우선 | R4와 동일 | 준비된 대기 작업 중 입력 시즌 순서, 같은 시즌은 FIFO | 늦게 준비된 앞 시즌 본문이 다른 시즌의 긴 대기열 뒤로 밀리는 현상 완화 / 뒤 시즌 완료가 늦어질 수 있고 구현·계측이 추가됨 |

**추천은 네 구조를 같은 코드·입력에서 비교하는 것**이다. R4/B4는 기존 `mapScheduled`를 재사용할 수 있다. P4는 제출량 제한과 첫 시즌 완료 우선의 효과를 R4와 나눠 확인하기 위한 후보이며 최적안으로 확정하지 않는다. U↔R4는 폭, R4↔B4는 보충/묶음, R4↔P4는 변환 큐 선택 정책을 비교한다.

초기 폭4는 현재 다운로드 슬롯4와 맞춘 작은 탐색값이다. 실측 최적값이나 메모리 안전 상한이 아니다. 최대6시즌이므로 제한 조건의 저장 중 이미지는 최대24개이며, 별도의 해시 다운로드·준비 커버·캐시 보관은 이 수에 포함되지 않는다. 이후 폭2/8 등 수치 탐색은 구조 결과를 보고 별도로 정한다.

### P4의 정확한 의미

1. 시즌 우선순위는 해당 실험 manifest의 고정 입력 순서로 정한다. 완료 시간이나 이미지 크기를 보고 사후로 바꾸지 않는다.
2. 원본이 준비돼 변환을 제출한 작업만 대기열에 넣는다. 슬롯이 비면 대기 작업 중 시즌 순위가 가장 앞선 것을 선택하고, 같은 순위는 제출 일련번호 순서다.
3. 앞 시즌의 미도착 다운로드를 기다리지 않는다. 앞 시즌에 준비된 작업이 없으면 뒤 시즌 작업을 즉시 실행한다. 이미 실행 중인 변환은 중단/선점하지 않는다.
4. 썸네일/상세 모두 같은 시즌 순위를 사용한다. 두 출력 수를 늘리지 않는다. 다운로드·업로드·경로 저장 큐와 시즌 재시도 계약은 기존대로다.
5. 유한 입력에서 뒤 시즌도 최종 처리하지만, 도중 완료의 균등한 배분을 보장하지 않는다. 지속 유입이 있는 제품에 그대로 적용하면 대기 편향이 생길 수 있으므로 이번 로컬 유한 입력 결과로 운영 적합성을 선언하지 않는다.
6. 큐 대기 중 취소는 미시작 작업을 제거하고, 실행 중 작업은 기존 계약대로 종료를 기다려 반환한다. 우선순위와 관계없는 오류 처리는 변경하지 않는다.

앞 시즌 우선으로도 첫 시즌이 항상 먼저 끝나는 것은 아니다. 준비 속도·이미지 수·진행 중 변환/업로드 때문에 뒤 시즌이 먼저 끝날 수 있다. 반대로 공정한 라운드로빈 큐는 장기 대기 완화에 유리하지만 첫 입력 시즌 완료를 더 늦출 수 있어 이번 P4와 목적이 다르다. 모든 원본을 준비한 뒤 일괄 제출하는 대안은 예산 miss 바이트를 대량 보관할 수 있어 우선 비교에서 제외하는 것을 제안한다.

## 확정한 추가 로컬 비교 — 45회

기존6시즌 입력에서 압박 대표16MiB와 비압박 대조128MiB를 사용한다. 16MiB의 기존 일부 판정이10% 경계에 가까웠다는 점을 보존하고 새 측정으로 재확인한다.32/64MiB와 단일/합성 부하는 후속 일반화 범위다.

- U/R4/B4/P4 × 16/128MiB × 각5회 =40회.
- 기존 재사용 off+전체 제출 대조5회 =5회. 모든 후보와 같은 반복 번호로 비교하되 별도 독립 대조군 여러 개처럼 세지 않는다.
- 합계45회, 반복당9조건. 매 반복 시작 조건을 한 칸씩 이동한 순서를 사전에 manifest에 고정한다. 5회로9조건 위치가 완전히 균형 잡힌 설계는 아니며 그 한계를 기록한다.
- 새 코드로 대조군도 재실행한다. 앞선45회/15회 표본을 새5쌍에 합치지 않는다. 실행 중 좋은 결과만 골라 반복을 추가하지 않는다.
- 컨테이너는1CPU/2GiB/swap·네트워크 없음, 같은 읽기 전용 입력·JPEG golden, 회차마다 새 컨테이너, 모두 trace on이다. 기존100ms/간격500ms 초과 미검증 중단/85% 1초 중단 조건을 유지한다.
- 앞선6시즌 약38초를 단순 적용하면 순수 측정 약28.5분이다. **추정치**이며 새 정책 지연·빌드·게이트·컨테이너 준비 시간은 별도다. 승인한 실험 범위 밖 원격 요청·클라우드 쓰기는 없다.

더 작은 대안은 P4를 제외한 U/R4/B4 ×2예산×5회 +off5회 =35회다. 구현은 간단하지만 첫 시즌 지연을 해결하는 데 제출량 제한만으로 충분한지까지만 확인한다. P4가 나중에 필요하면 코드 변경 후 대조군을 다시 측정해야 한다.

## 판정과 계측

- 정확성·실패율 악화 없음이 전제다. 새 코드의 U와 동일 예산에서 비교하고 off에도 비교한다. 전체/첫 입력 시즌의 '5쌍 중3쌍 이상10% 느림 + 중앙값도10% 느림'이면 해당 대조에서 채택 보류한다. 결측·중단을 악화 없음으로 판정하지 않는다.
- 전체 중앙값10% 개선을 우선한다. 첫 시즌만 개선되면 '종료 지연 완화 후보'로 보고하며 전체 속도 개선이라고 표시하지 않는다. 차이가 작으면 복잡도·메모리·읽기 절감을 함께 검토한다.
- 뒤 시즌의 개별 완료 시간, 마지막 완료, 최초 완료 시간, 본문/커버 종료, source-ready→변환 submit→start→end, 단계별 active/queued 최고치·대기, 논리 Buffer/cache/컨테이너 메모리를 기록한다. 다른 시즌 손해는 표에서 드러내고 최종 채택 전에 검토한다. 새로운 자동 탈락 임계값을 임의로 추가하지 않는다.
- cache hit/miss/거절·실제 읽기 수/바이트를 trace와 대조한다. 시즌 종료 순서가 바뀌면 캐시 반환·뒤 시즌 보관 성공도 달라질 수 있으므로 hit 수를 이전 실험과 같게 강제하지 않는다. 16MiB 압박이 실제 성립했는지 별도 판정한다.
- P4는 외부에 도착한 시점, 실제 변환 시작, 선택 순위·동순위 제출 순번을 기록해야 한다. trace의 submit을 우선순위 대기 뒤로 옮겨 대기 시간을 숨기는 구현은 허용하지 않는다.
- 큐 사이에 다른 시즌 작업이 전혀 없는 것을 성공 조건으로 삼지 않는다. 상한·정책 준수는 자동 검사, 실제 지연 개선은 실측으로 구분한다.

새 runtime이 공용 `PipelineRuntime` 확장을 필요로 하면 기본 FIFO 동작과 제품 호출부 무변경을 필수 회귀로 확인한다. 우선순위 대기와 기존 슬롯을 중첩해 계측이 이중 계산되거나 대기가 누락되지 않도록 구조를 정한다. 제품에 연결되지 않는 실험 전용 연결을 우선하고, 큰 공용 API 변경이 필요해지면 설계를 재검토한다. UI/DI/Container/Coordinator·Firestore/API 데이터 계약 변경은 없다. 같은 실행기·큐 경계를 건드리므로 구현은 순차 진행한다.

## 테스트 설계

- 대상: 비동기 실행 정책·대기열·취소·같은 실행 Buffer 수명. 표시만 바꾸는 작업이 아니므로 결정적 자동 검사가 필요하다.
- R4: deferred 작업으로4개 상한,1개 종료 시 다음1개 시작, 실패 기록 유지와 형제 종료 확인. B4:4개 중1개가 남으면 다음 묶음 미시작, 마지막 작은 묶음·빈 입력·취소 검증. 기존 테스트와 중복인 단순 사례는 재사용한다.

승인한 구현·필수 게이트·45회 실측·독립 재집계·원본 기록·진입점 문서 갱신을 완료했다. **단순 R4/B4는 후속 채택 후보에서 제외하고 P4를 종료 지연 완화 후보로 유지한다.** 비압박128MiB에서는 U와 시간 차이가 작으므로 단순한 U도 대조로 유지한다. 폭4/예산128MiB를 운영 최적값으로 확정하지 않는다.

다음은 P4와 U를 대상으로 실제128/256/512MiB 경계를 넘는 대용량 입력과 메모리 압박 비교안을 설계하는 것이다. 합의한 메모리 중단 기준을 유지하고, 입력/회차/실행 중 원본 보유량·native 메모리 관찰 범위를 먼저 구체화한다. 그 결과와 실제 프로젝트/큐/버킷 격리안을 근거로 Development의 URL·Storage·Firestore 검증을 진행한다. 이번 로컬45회 결과만으로 제품 기본값 변경·원격 배포·실제 네트워크 효과를 확정하지 않았다.
