## 현재 확정 사항과 다음 핵심 작업

- 현재 브랜드의 시즌을 제한 병렬로 실행하고, 슬롯이 비면 같은 브랜드의 남은 시즌을 시작한다. A8/B2/C… 예시에서는 B가 들어와도 A의 남은2개를 뒤로 밀지 않는다. 예시의 시즌 동시6은 제품 최종값으로 확정한 것이 아니다.
- 해당 브랜드의 선택 시즌이 저장 완료·검토 대기·최종 실패에 도달하고 실행 중 다운로드·변환·업로드·경로 저장 및 정리가 끝나면 다음 요청 차례로 넘긴다. 성공만을 무한히 기다리는 정책은 아니다.
- 자동 재시도 대기 중에는 현재 차례를 유지하며 시즌별 최초 포함 총5회다. Worker 전체의 단계별 공용 동시성 제한을 유지하는 방향이다. 실험의 다운로드4/변환1/업로드4·재사용128MiB는 제품 연결의 검토 기준이며 이미 제품 적용됐다고 표시하지 않는다.
- [Development 첫5회](development-screening-results.md)와 [역순3회](development-reverse-comparison.md)는 모두 완료했다. SP 전체 시간 이득은 두 쌍에서3.35%/0.61%, 첫 브랜드는10.57%/4.24%였다. 큰 처리량 개선이나 최적 수치의 증거로 채택하는 것이 아니라 처리 순서에 대한 제품 결정이다. 메모리 우열도 확정하지 않는다.
- **다음은 제품 FIFO 연결의 최소 세부 설계·구현 계획 작성이다.** 아래 기존 초안을 활용하되 접수 묶음/API·순번, 실행권·중복 전달, 재시도·종료·복구, 공용 pipeline 연결 순으로 필요한 계약만 확정한다. 공정성 스케줄러나 자동 동시성 조절·이미지 예약 설계를 다시 확대하지 않는다.
- 먼저 남은 결정은 (1) 같은 브랜드의 후속 선택 요청을 별도 차례로 둘지, (2) review 승인/수동 재시도의 차례·시도 예산, (3) 시즌별 요청 유지와 묶음 Worker 실행 중 최소 연결 방식이다. 추천은 닫힌 요청 묶음·추가 요청은 뒤에 접수이며, 아직 답변받지 않은 세부 정책은 아래 제안 상태를 유지한다. 서버의 접수 순번 확정 시점을 FIFO 기준으로 쓰는 안도 API 설계에서 명시한다.
- 장애로 이전 실행의 종료가 불명확할 때 다음 브랜드를 시작할 조건을 검증해야 한다. lease 만료만으로 정리가 끝났다고 간주하지 않는다. 정상 경로를 단순하게 유지하되 중복 실행·순서 우회 방지를 생략하지 않는다.
- 완료 기준 초안은 A의 남은 시즌이 새 B/C 요청에 밀리지 않음, A 저장·정리 전 B 시작 없음, 중복 전달/재시도/재시작에서도 차례와 총5회 예산 보존이다. fake/로컬 emulator로 검증 가능한 항목을 먼저 연결하고 실제 Development 검증은 이후 실행안을 정한다.

2026-10-05 이번 변경 범위는 결정·설계·진입점 문서 최신화다. 제품 코드·게이트·클라우드 설정/데이터는 변경하지 않았고 추가 실험을 실행하지 않았다. 아래 세부 데이터/API/복구 방식은 구현 계획 확정 전 검토안이다.

## 1. 목표·근거·승인 경계

- 브랜드 A의 선택 시즌들을 내부 병렬 처리한다. A의 모든 대상이 저장 완료·검토 대기·최종 실패에 도달하고 실행 중 다운로드·변환·업로드·경로 기록 및 Buffer 정리가 끝나면 B를 시작한다.
- 자동 재시도 대기 중에는 A의 차례를 유지한다. 시즌 자동 시도는 최초 포함 총 5회다. 메시지 중복, 실행권 거절, 정상적인 중간 저장 후 재개를 오류 재시도로 세지 않는다.
- CPU 1·메모리 2GiB의 기존 인스턴스당 자원을 유지한다. 인스턴스 수·요청 동시성·요금이 0으로 고정된다는 의미는 아니다. 클라우드 설정 변경·배포·실험은 별도 실행안 범위다.
- [로컬 20회 결과](phase-3-brand-fifo-results.md): 모든 회차 성공. 대용량 전체 중앙값 약 0.86% 단축, 최고 메모리 93.37%→83.36%, 입력 읽기 약 22.29% 감소. 전체 시간 10% 개선 기준은 미달이며 실제 네트워크 성능은 미검증이다.
- 현재 브랜드 FIFO 방향은 접수 순서·단순성을 위한 사용자 결정이다. 실측에 의한 큰 처리량 개선이나 모든 자원에서의 우위를 주장하지 않는다. 제품 초기 수치·API·복구 세부 구현 및 운영 배포는 미확정이다.

## 3. 제품 통합 시 후속 결정

브랜드 FIFO 방향은2026-10-05 확정됐다. 다만 아래 세부 항목의 추천안을 모두 승인받은 것으로 해석하지 않는다. 이제 제품 통합 설계에서 필요한 선택지를 좁혀 검토한다.

| 결정 | 추천안 | 대안과 차이 |
| --- | --- | --- |
| 브랜드 차례의 묶음 | 한 번의 선택 요청을 닫힌 묶음으로 확정. 같은 브랜드의 추가 요청은 새 묶음으로 맨 뒤에 접수 | 진행 중 같은 브랜드에 합류하면 대기 중인 다른 브랜드가 계속 밀릴 수 있다. |
| 실행 구조 | 묶음 하나의 시즌들을 한 Worker 실행에서 처리하고 Runtime을 공유. 오래 걸리면 저장된 진행 상태로 같은 차례에서 이어 실행 | 시즌별 HTTP를 유지하면 여러 인스턴스의 자원·예산 제어가 필요하며 로컬 공유 예산과 직접 비교하기 어렵다. |
| 시도 예산 | 검토 승인 후 저장은 기존 실행을 이어감. 명시적 수동 재시도·수정 후 재추출은 새 실행 예산, 누적 이력 보존 | 수동 재시도에도 기존 5회 한도를 적용하면 이미 소진한 작업을 사용자가 복구할 별도 동작이 필요하다. |

세부 구현 계획 확정 시 함께 명시할 값: 초기 시즌 병렬 폭, 실행 시간 분할·정리 여유 시간, heartbeat/복구 간격, 재시도 backoff. 기존 로컬 S의 설정상 시즌 상한은 6이지만 브랜드당 실제 입력은 2개였다. **2개 초과 동시 시즌의 브랜드 순차 실측을 완료했다고 주장하지 않는다.** 초기 후보 폭 2는 검증된 부하 범위에 맞추는 제안이며 6에서 조용히 변경하지 않는다.

## 4. 추천 구조의 데이터·API 초안

프로젝트 안에서 브랜드 순서를 관리하는 서버 전용 coordinator와 요청 묶음을 둔다. Development와 Production은 프로젝트별 독립이며 실험용 라우팅도 명시적으로 분리한다. 아래 문서 이름·필드는 검토용 후보이다.

| 객체 | 필요한 내용 |
| --- | --- |
| 접수 영수증 | 인증 사용자·requestID·요청 내용 digest, 요청별 결과. 같은 ID/같은 내용은 기존 영수증 반환, 다른 내용은 충돌 오류. |
| 요청 묶음 | brandID, 서버 접수 순번, jobID 목록, preparing/queued/active/retryWaiting/draining/released/blocked, 접수·종료 시각, 중복 참조와 신규 작업 구분 |
| coordinator | activeBatchID, owner, fencing generation, lease, 다음 접수 순번. claim은 단일 transaction으로 한 묶음만 허용 |
| 시즌 실행 | batchID, 명시적 run generation, attempt 번호/ID, resume checkpoint, nextEligibleAt, 마지막 오류. 기존 job 진행 상태·review 정보는 유지 |
| 전달 의도 | 묶음·dispatch generation·예약 시각·전달 상태. DB 반영 성공 후 task 생성 실패/응답 유실에도 재생성할 수 있는 outbox |
| 종료 증거 | 해당 generation의 실행 중 작업 수 0, 캐시 scope/대여 반환, 마지막 저장 상태. process가 살아 있는지와 lease 만료를 구분 |

접수 순서는 서버가 요청 묶음의 순번을 확정한 순서다. 클라이언트 탭 시각이나 task 도착 순서로 정의하지 않는다. 준비 중인 앞 묶음을 뒤 묶음이 추월하지 않도록 접수 복구 계약도 필요하다.

선택 목록의 검증·job 연결을 끝내기 전에는 실행 가능한 묶음으로 공개하지 않는다. 기존 per-job trigger도 새 방식 job을 별도로 dispatch하지 않게 막아야 한다. 중간 오류는 기존 부분 성공 결과를 보존하면서 성공한 신규 job만 한 번 확정하거나, 접수 실패 상태를 복구해야 하며 조용히 고아 job을 남기면 안 된다.

이미 실행 중인 중복 job은 소유 묶음을 옮기지 않고 기존 job 영수증을 돌려준다. 중복 참조만 있는 요청은 새 처리 차례를 만들 필요가 없다. 중복 참조를 새 묶음의 실행 대상으로도 세어 순환 대기를 만들지 않는다.

requestID를 추가한다면 iOS Repository/UseCase에서 한 사용자 요청의 재전송 동안 유지하도록 연결해야 한다. View에서 Firebase를 직접 호출하지 않고 기존 MVVM-C·Repository·UseCase·DI를 유지한다. 구버전 클라이언트와 기존 관리자 경로의 호환 정책은 구현 계획에 포함한다. 새 화면은 현재 범위가 아니다.

## 5. 정상 처리와 재시도

1. Functions가 요청 묶음을 접수하고, 준비 완료 및 전달 의도를 기록한다.
2. 전달 담당자가 task를 생성한다. 동일 generation 재전송은 멱등 처리한다.
3. Worker가 coordinator와 묶음을 transaction으로 확인한다. 다른 브랜드 차례면 무거운 일을 시작하지 않는다. 이 대기를 시즌 실패로 기록하지 않는다. 누락된 깨우기는 durable outbox/복구 담당자가 회수한다.
4. 현재 브랜드의 준비된 시즌들을 내부 병렬로 실행한다. 다운로드·변환·업로드 슬롯과 실행 내 Buffer 예산은 공유한다. source cache 128MiB는 전체 메모리 한도가 아니다.
5. 시즌별 성공·검토 대기·최종 실패가 나와도 형제 작업과 저장·정리 완료를 기다린다. partialFailed는 완료된 저장과 실패 항목을 보존하는 종료 결과로 분류한다.
6. 재시도 가능한 실패가 남으면 해당 브랜드 차례를 유지한다. backoff 동안 HTTP 요청을 계속 열어 둘 필요 없이 nextEligibleAt에 같은 묶음을 깨운다. 다른 준비된 형제 시즌의 진행은 허용한다.
7. 모든 시즌과 cleanup 종료가 확인된 뒤 현재 generation을 조건으로 묶음을 해제하고 다음 묶음의 전달 의도를 기록한다. DB 반영과 task 생성 사이 실패를 복구 가능하게 한다.

시도 예산은 Cloud Tasks 전달 헤더 대신 서버의 실제 시즌 실행 상태로 판정한다. 최초 시도 1, 재시도 가능 실패 후 다음 실제 시도 시작 때 증가, 5번째 실패 시 최종 실패다. claim 거절·중복 전달·정상 checkpoint 재개는 증가시키지 않는다. 실제 crash 후 다시 실행하는 것은 정상 checkpoint 재개로 위장해 무제한 허용하지 않는다. 운영 관측용 기존 attemptCount와 정책용 attempt 번호의 의미를 분리한다.

검토 대기에 도달하면 기존 합의대로 해당 차례의 종료 대상이다. 나중의 승인 재개는 이미 끝난 묶음을 되살려 다른 브랜드를 추월하지 않고 새 차례에 연결하는 안을 제안한다. retrySeasonAssets·수정 후 재추출·관리자 재개도 실행권을 우회하지 않게 같은 접수 경계를 사용해야 한다.

## 6. 요청 제한·실행권 상실·복구

현재 확인한 Cloud Run 요청 timeout은 900초다. 코드의 task 생성에는 dispatchDeadline이 명시되지 않는다. 두 제한을 독립적으로 다루고 실제 큐 설정과 함께 후속 실행안에서 고정해야 한다. 제한을 임의로 늘려 해결하지 않는다.

Cloud Run 요청 timeout은 컨테이너 종료와 같지 않다. Cloud Tasks가 응답을 기다리지 않게 되어도 Worker가 반드시 멈추는 것은 아니다. [Cloud Run timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout), [Cloud Tasks task 계약](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues.tasks).

- 요청 제한 전에 새 작업 투입을 중지하고 이미 시작한 처리를 정리한 뒤 durable checkpoint를 남기는 방식을 제안한다. 긴 시즌 하나도 이미지 경계에서 이어갈 수 있어야 하며, 브랜드 경계만 나누면 최대 80시즌 요청을 처리할 수 없다.
- 정상적인 이어 실행에서는 처리된 이미지·문서가 중복 생성되지 않도록 저장 단위의 멱등성을 확보한다. 메모리 원본은 실행 사이에 보존하지 않으며 다음 실행은 필요하면 다시 다운로드한다.
- heartbeat 실패/owner 상실은 신규 투입 중지와 취소 요청으로 연결한다. 취소 불가능한 업로드·변환은 끝날 때까지 추적한다. heartbeat 갱신도 읽기 후 무조건 update가 아닌 owner/generation 조건부 갱신으로 바꿔야 한다.
- 경로 기록·최종 상태 쓰기에는 fencing generation을 확인한다. **이는 이미 시작한 Storage 업로드나 이전 프로세스의 CPU 사용을 중단시키는 증거가 아니다.**
- 기존 결정적 Storage 경로는 늦게 끝난 이전 실행이 덮어쓸 위험이 있으므로 객체 generation 조건부 쓰기 또는 실행별 객체 경로와 조건부 공개 방식을 비교해야 한다. 후자는 경로/보관·정리 계약이 늘어난다. 어느 쪽도 검토 없이 적용하지 않는다.
- lease 만료만으로 다음 브랜드를 시작하지 않는다. 이전 실행의 종료를 확인할 수 없으면 blocked/draining으로 남기는 것이 엄격한 순서 보장에 맞다. 자동 복구의 종료 증거를 어떻게 얻을지(협조적 정리, 실행 격리와 종료 확인 등)는 **구현 가능성 검증 잔여**다. generation만 증가시켜 물리적 중첩이 없다고 주장하지 않는다.
- 이 복구 조건을 해결하기 전에는 “모든 장애에서 자동 복구하면서 실행 중첩 0”을 완료 조건으로 통과 처리할 수 없다. 다른 브랜드를 계속 막는 가용성 문제도 함께 검토한다.

시즌 목록 탐색은 별도 실행 경로이며 같은 서비스 자원을 사용할 수 있다. import 브랜드 순서를 보장해도 discovery까지 CPU·메모리 경쟁이 없어진다는 뜻은 아니다. 실제 Development 비교는 다른 트래픽을 통제하고, 제품에서의 간섭 처리 범위는 별도 확인한다.

## 7. 구현 계획 확정 전에 필요한 검증 설계

현재 로컬 BF01~12와 전체 265개 검사는 실험용 스케줄링 근거다. 아래 실제 분산 계약을 검증한 결과로 재사용하지 않는다.

| 대상 | 필수 시나리오 | 검증 수단 |
| --- | --- | --- |
| 접수 | 동일 requestID 동시 요청, 내용 충돌, 서로 겹치는 시즌 목록, 준비 중 실패/재개, 중복만 있는 요청 | Functions unit + Firestore emulator transaction 경합 |
| 전달 | DB 반영 후 task 생성 실패, 생성 성공 후 응답 유실, 순서 역전, 같은 task 중복 | fake Tasks + emulator outbox 복구 |
| 실행권 | 두 Worker 동시 claim, stale generation, 다른 브랜드 시작 거절, cleanup 이전 다음 브랜드 금지 | 독립 Worker 호출 + emulator barrier |
| 재시도 | 최초 포함 5회, 6번째 거절, backoff 차례 유지, transport 오류와 실제 시도 분리, 수동 실행/검토 재개의 예산 | fake clock + 영속 상태 재시작 검사 |
| 중간 저장 | 같은 이미지 재개, 두 JPEG 중 하나 실패, 경로 쓰기 실패, checkpoint 직전/직후 crash | fake HTTP/Storage/DB 실패 주입, 중복 객체/문서 검사 |
| 오래된 실행 | heartbeat 상실, timeout 이후 늦은 업로드·DB 쓰기, owner 교체, 종료 확인 불능 | 지연 가능한 가짜 작업 + 별도 프로세스 종료 검사; emulator만으로 실제 Cloud Run 종료를 입증하지 않음 |
| 자원 | 복수 시즌의 공용 슬롯/128MiB, 예산 초과 재다운로드, 취소 중 Buffer 반환 | 기존 pipeline 회귀 + 실제 Worker 연결 검사 |
| 호환 | 기존 /wake·개별 job route·review·asset retry가 순서 우회하지 않음, OIDC 권한 유지 | Worker HTTP 계약 + Functions export 계약 + 관리자 수동 QA |

Functions·Worker·Firestore emulator 검사 각각의 필수 ID를 게이트에 연결하고 코드 상태 digest/원본 로그를 남긴다. 새 export가 생기면 기존 Functions 120개 export 계약에 미치는 영향을 의도적으로 검토한다. 새 서버 전용 문서의 클라이언트 접근 거부와 권한별 job 읽기를 검증한다. 실제 클라우드 장애/네트워크 처리는 Development 단계의 별도 증거다.

## 8. 후속 변경 후보와 권장 진행 순서

아래는 의존성 검토용이며 사용자 결정 전 확정된 구현 phase 목록이 아니다.

1. 접수 묶음·실행 구조·시도 예산 정책 확정 → 종료/복구 및 Storage 쓰기 보호 가능성 검증 → 세부 구현 계획 확정.
2. Functions 접수/중복/outbox와 Firestore 계약을 먼저 구현·검증. `functions.ts`에 모든 코드를 누적하기보다 import 도메인 모듈로 책임을 분리한다. Swift requestID가 필요하면 Repository protocol·UseCase·mapper와 호출자를 함께 연결한다.
3. Worker 브랜드 실행권·checkpoint·취소/정리·공유 pipeline 연결. `processor.ts`, `server.ts`, `index.ts`, `pipeline/*` 및 새 실행 담당 모듈이 후보이며 같은 계약을 건드리므로 순차 통합한다.
4. 실제 분산 경합 필수 게이트 및 기존 회귀 완료. `verification/functions.json`, `verification/lookbook-import.json`, 필요 시 Firestore 검사 설정에 새 필수 ID를 연결한다. rules/index 변경 필요 여부는 데이터 경로·쿼리 확정 후 판정한다.
5. 기존 queued 작업 처리·구버전 요청·review 재개·롤백을 포함한 라우팅 전환안과 Development 실행안을 제시한다. 새 경로와 기존 trigger가 동일 job을 중복 처리하지 않도록 검증한다. 서비스 전체 기본값을 먼저 바꾸지 않는다.

기존45회 한도는 과거 비교 설계 이력이며 추가 실행 권한이 아니다. 승인된 첫5회·후속3회는 이미 완료했다. 제품 연결의 Development 검증은 대상·필수 시나리오·요청량·비용을 갖춘 별도 실행안으로 정한다. 테스트 데이터 삭제·운영 배포도 별도 승인 대상이다.

## 9. 이번 작업의 기록

- 현재 코드·기존 설계·공식 timeout 계약을 읽고 차이를 문서화했다. 위 테스트는 설계이며 새 제품 게이트를 실행한 결과가 아니다.
- 제품 코드, 배포 설정, 실제 Cloud Tasks/Storage/Firestore 데이터는 변경하지 않았다.
- 제품 통합 단계에서 남은 세부 정책과 종료 복구의 기술 검증 결과를 반영한 뒤 구현 계획을 확정한다. Development 비교는 완료됐고 현재는 제품 FIFO 연결 설계 단계이며, 제품 적용 완료로 보고하지 않는다.
