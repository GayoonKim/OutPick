# 대용량 입력·128/256/512MiB 보관 예산 검증 설계

2026-10-03. [제출 순서45회 결과](phase-3-submission-design.md)를 근거로 설계했다. 사용자의 “ㅇㅋㅇㅋ 다음 핵심 작업 진행해도 문제 없으면 진행”으로 **635MiB 합성 입력·준비7회 구현과 필수 게이트·실행을 승인**받았다. 아래 제안형 표현은 설계 당시 이력이며 승인 범위는 L1~L4다. 본35회·Development·제품 기본값 변경은 포함하지 않는다.

- `large-input.ts`: 원본 메타데이터를 독립6job으로 매핑하고 새 digest/고정 계약을 검증한다. `fixtures/performance-large-base.json`은 원본 픽셀 없는 메타데이터 회귀 자료다.
- `large-comparison.ts`:7회 순서·엄격 계획·분모/중단/미수행·압박 성립 집계. `reuse-entry.ts`/`reuse-comparison.ts`/`reuse-contract.ts`에 명시적 `large-input-v1` 분기를 연결했다.
- `reuse-trace.ts`: 새 입력 계약에서 성공1시도16,656건·총5시도83,280건 상한을 계산한다. 기존 분석기의1만 건 미만 조건에 맞춰 기존 기록기도 최대9,999건으로 경계를 일치시켰다. 기존 한도를 확대하지 않았다.

- P4/512와 U/512의 첫 합성 시즌은 완료됐지만 나머지 시즌 중단으로 회차 전체 실패다. 원본 `detail.firstSeasonMs`/`seasonCompletedMs`는 중단 시즌의 시도 종료도 포함하므로 성공 상태와 함께 읽어야 한다. `observations.json`은 회차 중단 시 전체/첫 시즌 성능 비교 필드를null로 제외했다.

- `manifest.json`: 고정 이미지, Mac/Linux 게이트 경로·source, derived 입력 메타데이터/계약/7회 순서·실행 조건·driver hash.

- `rows.json`, `summary.json`, `diagnosis.json`, `console.jsonl`:7회 분모와 사건/큐 분석. 전용 `analyze-large-input.mjs`로 재집계해 저장값과 deepEqual을 확인했다.
- `observations.json`:7회 자원/읽기/부분 진행/정리, 성공 완료분 총량. 원본 result↔finished↔rows 및 manifest 입력 계약 일치, summary/diagnosis 재집계 일치.

- task 문서와 `output/` 원본은 현재 로컬 자료이며 원격 백업/커밋된 상태라고 주장하지 않는다.

## 해석과 다음 추천

이번 준비 결과로 U 전체 시작과512MiB 보관을 이2GiB 대용량 조건의 후속 성능 후보로 바로 채택하지 않는다. P4/128·256만 완주했지만 각1회이므로 최적값·실패율·중앙값10% 개선·5쌍 반복 악화 판정은 아직 없다. P4/256은 더 많이 재사용해도 이번 실행이 더 빠르지 않았고 순간 메모리 피크가 높아128을 우선 검토 후보로 남긴다.

**다음 추천은 같은 P4의 재사용 off 대조군을 먼저 준비 측정해 실행 가능성을 확인하는 것이다.** 현재 U/off는 완주하지 못해 재사용 자체의 속도/메모리 효과를 공정하게 비교할 기준 시간이 없다. P4/off가 유효하면 P4/off↔128·256의 반복 비교 범위와 비용을 확정하고,512는 재시도하지 않는다. P4/off도 중단되면 더 많은 반복보다 동일 시점 메모리 관찰/제출 폭 등 실패 원인 설계가 먼저다. 이 추가 회차·프로파일링·본 비교는 이번 승인7회에 포함하지 않았으며 아직 실행하지 않았다. Development는 로컬 유효 후보/대조군을 확인한 뒤 기존 한도 안에서 실행안을 확정한다.

## 해결할 문제

현재6시즌은 중복 제거 후 본문 원본111,028,402바이트(105.885MiB)다.128MiB에도 전부 들어가므로128/256/512MiB의 보관 거절·fallback 차이를 실제 부하에서 확인할 수 없다. 보관 예산은 처리 중 입력/출력/native 메모리/컨테이너 전체 한도와 다르다. 직전 실험에서는 보관 예산16MiB인 P4도 컨테이너 최고89.32%를 기록했다.

이번 목적은 큰 자료에서 U(전체 시작·FIFO)와 P4(시즌당4개·준비된 변환의 입력 시즌 우선)의 실행 가능성·보관 거절·정합성·자원 반환을 확인하는 것이다. 1회씩의 준비 측정으로 성능 채택이나 최적 예산을 결정하지 않는다. R4/B4는 첫 시즌 반복 악화가 확인돼 이번 후보에서 제외한다.

추천 입력은 **독립 합성 시즌6개가 각각 기존6시즌의 전체 본문 목록을 처리**하는 구성이다. 시즌 내부 후보 순서는 기존 입력의2026FW→2026SS→2025FW→2025SS→2024FW→2024SS와 각 본문 순서를 유지한다. 각 합성 시즌은132후보를 해시하고131개 고유 본문을 저장한다. 커버는 합성 시즌 순위에 대응하는 기존 커버를 하나씩 사용한다.

- jobID/seasonID는 `synthetic-large-01`~`06`처럼 실제 시즌과 구별한다. brandID도 로컬 합성임을 표시하며 실제 브랜드 등록 자료로 쓰지 않는다.
- 각 job에 독립 source scope와 request context를 부여한다. 파일 경로는 기존 자료를 재사용하지만 매 읽기에서 새 Buffer를 얻는다. 다른 job이 같은 Buffer 객체를 공유하거나 전역 content cache를 쓰면 이 입력의 압박 계약 위반이다.
- 같은 원본은 **서로 다른 시즌**에서 처리하므로 시즌 간 중복 제거를 새로 도입하지 않는다. 한 시즌 내부의 기존 중복 한 개는 그대로 제거한다.
- 새 HTML을 만든 뒤 실제 URL에서 추출한 자료처럼 취급하지 않는다. 기존 frozen 원본의 무결성 확인 후, 별도 local-connected 입력 adapter가 합성 job의 본문/커버/golden 계약을 만든다. 실제 품질 판정·관리자 검토 경로를 우회하는 제품 연결은 없다.
- 전체 원본을 준비 단계에서 메모리에 보관하지 않는다. 합성 구성은 메타데이터 매핑이며 해시 단계의 실제 읽기와 scope별 보관은 측정 구간에 포함한다.

### 계산한 규모

## 우선 준비 측정 제안 — 7회

U/P4 ×128/256/512MiB 각1회 + U/off1회, 총7회다. 한 번씩의 환경·부하 적합성 검사이며5쌍 성능 비교가 아니다. 새 입력은 전 조건 동일하다.

제안 실행 순서는 **U/off → P4/128 → U/128 → U/256 → P4/256 → P4/512 → U/512**다. 의도는 작은 보관 예산부터 동작을 확인하고 두 구조 순서를 번갈아 배치하는 것이다. 순서를 manifest에 고정하며 이 한 번의 순서로 통계적 균형이 확보됐다고 표현하지 않는다.

- 고정 Linux ARM64 이미지, 회차별 새 컨테이너,1CPU/2GiB,swap·네트워크 없음, 기존 읽기 전용 원본 volume. 시즌 최대6개, 다운로드4/변환1/업로드4/경로 제한 없음 유지.
- 재사용 조건은 모두 커버 선준비, U/off는 기존 비재사용 대조다. 두 대조 사이에 커버 선준비 차이도 포함됨을 기록한다. 동일 예산 U↔P4에서는 큐/실행 폭만 다르다.
-100ms 표본·500ms 초과 환경 미검증 중단·85% 이상1초 지속 메모리 중단 유지. 새로운 메모리 한도나 임계값으로 실패를 없애지 않는다. 메모리 중단은 해당 회차 결과로 남기고, 컨테이너 정리 후 독립된 다음 조건을 진행한다. 환경 미검증·정합성 실패·정리 실패면 남은 회차를 미수행으로 기록하고 원인을 먼저 해결한다.
- 같은 회차 자동 재실행·실패 표본 교체 없음. 성공·중단·실패·미수행을7회 계획에 함께 남긴다. 시즌 job 총5회 기존 계약은 유지하며 추가 네트워크 재시도나 새 시간 제한을 도입하지 않는다.
- 기존 약38초 부하를 단순6배하면 회차당약228초,7회 순수 처리 **약26.6분**이다. 자료 구조와 메모리 압박에 따라 달라지는 **추정치**다. 빌드/게이트/입력·출력 사전 검사/결과 분석 시간은 별도다.
- 모두 성공하면 JPEG11,088개·경로5,544건·출력1,751,277,535바이트를 검증한다. 모든 조건이 재사용에 실패한다고 가정한 로컬 읽기 상한은11,088회/9,366,439,537바이트다. 원격 GET/Storage 업로드·클라우드 청구량이 아니다.

처음부터7조건×5회=35회로 들어가면 단순 추정 순수 처리만 약133분이며, 환경 미준비/메모리 중단 조건을 반복할 수 있다. 따라서7회 결과로 유효 조건과 입력을 확인한 다음 본 비교 행렬·회차를 확정한다. 준비7회를 이후 본 비교의5쌍에 끼워 넣지 않는다.

## 필요한 실행기 보완

1. 기존 고정6시즌 loader와 실험 계획은 그대로 검증하고 새 profile adapter/contract를 별도로 추가한다. 기존6개 실제 seasonID,131본문,137자산,128MiB에서 전부 hit라는 상수를 새 입력 검증에 적용하지 않는다.
2. 합성 manifest는 base digest, 합성 job/원본 시즌 매핑, 후보 순서·source hash·bytes, 커버 매핑, 원본 golden digest, 변환 규격을 포함한 **새 derived input digest**를 갖는다. base digest 하나를 합성 입력 전체의 식별자로 재사용하지 않는다.
3. 기존 JPEG golden을 원본 hash+본문/커버 역할+규격별로 대응시킨다. 각 합성 job의 예상 파일·바이트·경로와 실제 변환 결과를 검사한다. 새 JPEG 규격이나 원본 변형은 없다.
4. `reuse-contract.ts`의 입력 계약/trace 검증을 새 profile 전용 경로로 연결한다. 같은 SHA라도 서로 다른 합성 job의 파일·경로·scope 결과를 하나로 합치지 않는다.128/256MiB에 대한 기존 '모든 본문 hit' 검사는 기존 입력에만 남긴다.
5. 현재 `ReuseTrace`는 이벤트1만 건 한도다. 새 최대 입력은 성공1회에서 최악 **16,656건**이므로 한도를 그대로 쓰면 처리 성능과 무관한 실패가 발생한다. 새 profile은 대상별 최대 stage 사건과 준비/종료·허용 시도 수에서 계산한 유한 상한을 사용하고, 기록기/분석기의 상한 및 정확한 경계 검사를 맞춘다. 이벤트를 잘라내거나 기존 실험의1만 건 경계를 무조건 풀지 않는다.
6. 시작/종료 이벤트는 합성 jobID를 식별하고 모든 시즌 완료 시간을 유지한다. U/P4 선택은 새 manifest에 고정하며 P4의 우선순위도 합성 입력 순서다. 새로운 이미지 큐 정책은 추가하지 않는다.

## 테스트 설계

이전부터 적용한 `test-design-workflow` 기준으로 입력 복제·캐시 수명·비동기 실패를 자동 검사한다.

- 입력: 서로 다른 job은 같은 파일을 참조해도 독립 Buffer/scope다. 같은 job의 동일 hash 후보만 제거되고 다른 job의 저장 대상을 지우지 않는다. 매핑 순서/커버 역할/바이트/digest 변조를 거절한다.
- 실제 작은 JPEG: 복수 합성 job에서 공용 작은 예산으로 hit/miss가 섞이게 만들고, 각 job별 출력 SHA·수량·경로 및 읽기 바이트를 확인한다. 큰 자료 산술 테스트가 실제JPEG 검사를 대신하지 않는다.
- 경계: 단일 이미지가 예산보다 큰 경우, 정확히 예산과 같은 경우, 먼저 끝난 scope 반환 후 뒤 job이 보관하는 경우, 보관 거절이 있었으나 저장 대상이 중복 제거된 경우를 구별한다. 공용 예산과 전체 보관 수요를 동일시하지 않는다.
- 실패/취소: hash/fallback/변환/업로드/경로 실패·중단 후 형제 종료와 lease 반환, 대기 슬롯 제거, 후속 회차 원본 격리. 기존 회귀가 충분한 항목은 재사용한다.
- trace:1만 건을 넘는 정상 새 입력, 계산 상한의 정확한 경계, 상한 초과·시즌/대상 누락/중복·다른 profile 혼입 거절. 기존 소규모 입력의 검증을 완화하지 않는다.
- 집계:7회 완전성·미수행/중단 분모·압박 미성립·부분 결과/원본 불일치 검출.1회 기록에5쌍 성능 판정을 붙이지 않는다.
- 수동 QA: 새 화면이 없어 이번 로컬 준비 단계의 화면 QA는 없다. 실제 URL 추출/검토·Storage·Firestore는 Development 별도다.

## 선택 이력 — 승인 완료
