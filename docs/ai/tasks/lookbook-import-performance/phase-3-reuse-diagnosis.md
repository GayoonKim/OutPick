# 재사용 첫 시즌 지연 진단

후속: [커버 선준비 구현·15회 확인](phase-3-cover-preparation.md)이 완료됐다. 아래는 수정 전 원인 진단의 원본 기록이며 최신 코드/검증/다음 단계는 후속 문서를 따른다.

2026-10-03. 사용자가 이전 15회 결과의 ‘본문·커버 단계 시각으로 원인 확인’ 추천에 동의했다. 이번 범위는 원인 진단이며 커버 우선순위/이미지 제출 방식/예산/제품 정책 변경은 하지 않는다.

**완료:** Mac/Linux 222개·필수 114개 통과, off/256MiB 2회 모두 성공. 재사용 on에서 첫 시즌 커버 원본은 0.411초에 준비됐으나 다른 시즌 본문 변환 214건 뒤에 등록되어 변환 시작이 36.595초였다. 본문은 13.342초에 끝났고 커버 저장이 시즌 종료를 36.681초까지 지연시켰다. 현재 실행의 직접 대기 원인은 확인했으며, 수정 효과·최종 채택은 아직 검증하지 않았다.

## 구현·실행 범위

기존 6시즌, C 다운로드4/변환1/업로드4/경로 제한 없음, 재사용 off와 초기 대조 256MiB를 각 1회(총 2회) 측정한다. 두 실행 모두 새 이미지에 계측을 켜며 이전 15회 표본과 합치지 않는다. 이 최소 진단은 5쌍 채택 판정이나 통계적 성능 비교가 아니다. Linux ARM64 1 CPU/2GiB/swap·네트워크 없음, 기존 고정 입력, 무결성 검사 후 측정, 메모리 100ms/500ms 간격 중단/85% 1초 조건을 유지한다. 순수 처리 예상 약 80초, 게이트·이미지 준비는 별도다.

`performance/reuse-trace.ts`는 로컬 진단용 PipelineRuntime 파생 객체에서 기존 슬롯 실행을 그대로 호출하며 제출/실제 시작/완료를 기록한다. AsyncLocalStorage로 동시 본문·커버의 논리 대상 ID를 구분한다. `reuse-input.ts`는 대상 시작/바이트 준비·hit 여부/완료와 시즌 완료를 기록한다. 파일·콘솔 출력은 처리 중 하지 않고 메모리에 제한된 이벤트만 남긴다. URL·이미지 원문은 기록하지 않는다. trace 자체 오버헤드는 이번 두 회차로 보정하지 않으며 사건 순서와 대기 구간을 원인 근거로 사용한다.

`reuse-comparison.ts`는 진단용 계획 marker/ID/settings digest와 두 회차 행렬을 이전 15회와 분리한다. `reuse-entry.ts`에서 명시적 marker일 때만 trace/runtime을 연결한다. 기존 검사/종료 증거/정합성을 유지하고 trace 누락·중복·순서 오류도 진단 성공에서 제외한다. 앱 DI·API·Firestore·제품 처리 정책 영향은 없다.

테스트 설계: 기존 test-design-workflow 기준으로 동시 trace context와 슬롯 대기/실패 이벤트, 진단 계획 혼입 거절, 실제 작은 JPEG 연결의 hit/miss 사건, 완전한 대상/단계 시각 집계·누락/순서 오류를 필수 회귀로 확인한다. Mac/Linux 프로그램 게이트 후 2회 원본을 생성한다. 새 소스에 이전 218개 통과 결과를 재사용하지 않는다. UI·클라우드 수동 QA는 이번 범위 밖이다.

완료 기준은 두 환경 게이트, 두 회차의 정합성·메모리·종료 결과, 각 시즌 마지막 본문/커버/시즌 완료 시각, 커버의 다운로드 대기와 변환 대기 및 그 앞 다른 시즌 본문 작업 수, 원본·digest·기록 범위·결론·한계다. 원인이 불명확하면 추측으로 남기고 정책을 바꾸지 않는다.

## 구현과 게이트

`reuse-trace.ts`의 ReuseTrace/TracedPipeline은 동시 대상별 AsyncLocalStorage를 사용하고 실제 부모 PipelineRuntime의 FIFO에 그대로 위임한다. 소스 준비(hit 여부), asset/season 완료와 단계별 제출·시작·종료를 최대 10,000개 이벤트로 제한한다. 해시 입력 다운로드 전체가 아니라 **저장 대상의 단계 시각**을 상세 기록하며 해시 읽기 수/바이트는 기존 합산 계측을 유지한다. trace는 처리 중 파일로 출력하지 않는다.

`analyzeReuseTrace`는 137개 고유 대상·6개 시즌·본문/커버 수명·단계별 호출 수·단조 시각·두 변환 후 업로드/두 업로드 후 경로 저장을 검증한다. `makeReuseDiagnosticPlan`의 marker와 별도 ID/settings digest로 기존 15회와 혼입을 거절한다. 진단 trace가 누락되거나 불완전하면 성공으로 분류하지 않는다.

새 필수 4개를 추가해 전체 222개·필수 114개다. `reuse-trace.test.ts` 3개가 계획·맥락/대기/실패 순서·완전한 기록과 변조를, `reuse-comparison.test.ts` 1개가 실제 작은 JPEG 연결의 본문 hit/커버 miss/시즌 종료를 확인한다. 사전 lint의 줄 길이·중괄호·non-null assertion을 정리한 뒤 최종 게이트를 실행했다.

## 두 회차의 실제 증거

한국 시간 2026-10-03 **18:08:53~18:10:09**에 실행했다. 2/2회 성공, 실패·메모리 중단·환경 오류 없음. summary valid true/누락 없음, 원본 재집계와 summary/diagnosis 일치. 각 회차 137개 자산·274개 JPEG가 기존 golden과 일치했다. source 읽기는 off 269회, on 138회로 기존 계약을 유지했다. trace 때문에 실제 동시성·입력·출력 개수는 바뀌지 않았다.

전체 연결 실행 시간은 off 37.704초/on 37.169초이고 최고 컨테이너 메모리는 71.70%/68.16%였다. 단일 진단 회차이므로 이를 성능 개선율이나 메모리 개선의 증거로 채택하지 않는다. 이전 15회에서 on 메모리가 더 높았고 91.49% 최고값이 나온 사실을 대체하지 않는다. 이번 진단으로 그 최고 메모리의 원인까지 밝혀진 것은 아니다.

표본 최대 간격 off 131.178ms/on 107.957ms, 종료 Buffer·보관량·scope·슬롯 정리, cleanup 대기 파일 0, 해당 이미지의 실행 중 컨테이너 0을 확인했다. 기존 85%/1초 기준이나 실패 분모 변경은 없다.

## 다음 추천과 범위

첫 수정 후보는 **시즌의 커버 원본을 먼저 확보한 뒤, 같은 시즌 본문과 커버를 함께 변환 제출할 수 있도록 준비하는 방식**이다. cache hit 본문만 다른 대상의 준비를 앞질러 변환 대기열을 채우는 문제를 줄이는 방향이며, 공용 변환 1/업로드 4를 바로 늘릴 이유는 이번 증거에 없다. 이는 후보 제안이지 구현·효과 검증 완료가 아니다.

커버 선준비 방식과 더 일반적인 준비 완료/제출 순서 제어는 대기 시간·보관량·부분 실패 처리의 차이가 있으므로 다음 구현 전 범위를 구체화한다. 예산 초과로 일부 본문도 miss가 되는 경우와 커버 실패 시 scope 정리를 함께 검토해야 한다. 현재 합의한 해시·품질 판단 장벽, 검토 대기 시 scope 종료, 원본 보안 검사, 이미지 출력·경로 계약은 유지한다. 실제 제품 job 총 5회 계약과 Development 검증도 남아 있다.

제품 정책/기본값·클라우드·Firestore·API·커밋 변경 없이 이번 진단 단계만 완료했다.
