# 커버 선준비 수정과 세 조건 확인

2026-10-03. 사용자가 커버 원본을 먼저 준비해 같은 시즌 본문·커버를 변환에 제출하는 추천안을 확정하고 진행을 승인했다. 본문을 항상 먼저 끝내거나 커버를 무조건 우선 처리하는 요구는 아니다.

## 설계와 구현 계획

실험용 local-connected 경로에서 기존 해시/중복 제거 후, 커버를 공용 다운로드4 슬롯으로 한 번 읽는다. 커버 준비가 끝난 다음 기존 본문→커버 대상 목록을 동일한 공용 변환1/업로드4/경로 제한 없음에 제출한다. 실제 품질 검토·검토 후 새 실행 경계는 유지한다. 이 실험을 제품의 자동 승인으로 연결하지 않는다.

커버 바이트는 재사용 캐시에 추가하지 않고 현재 시즌 작업의 준비된 입력으로 보관한다. 원본 보관 예산과 처리 중 Buffer를 구별해 계측하고 컨테이너 전체 메모리 감독을 유지한다. 커버는 추가 읽기 없이 소비한다. 준비 실패/취소 시 본문 변환을 시작하지 않고 scope/바이트를 정리한다. 저장 중 실패·취소는 기존 형제 작업 drain 후 정리한다. 예산 부족으로 본문이 cache miss이면 기존 다운로드 fallback을 유지한다. 그 경우 모든 본문이 동시에 준비돼 있다는 보장은 추가하지 않는다.

변경 후보: `performance/reuse-input.ts`의 명시적 커버 준비 옵션, `reuse-comparison.ts`의 별도 확인 행렬·검증, `reuse-entry.ts`의 연결, `reuse-trace.ts`의 커버 준비 사건과 제출 시각 검증, 관련 회귀와 게이트/진입점 문서다. 제품 processor/API/Firestore/앱 DI/기본값 변경은 포함하지 않는다.

## 비교와 완료 기준

기존 6시즌에서 off/current/prepared 세 조건을 각 5회, 총 15회로 비교한다. off는 재사용 비활성, current는 256MiB 현재 흐름, prepared는 256MiB 커버 선준비다. 반복마다 세 조건 순서를 회전하고 같은 반복 번호끼리 비교한다. 모두 상세 trace on, 새 고정 이미지·새 Linux ARM64 컨테이너, 1 CPU/2GiB/swap·네트워크 없음, 기존 고정 입력·사전 무결성 확인, 메모리 100ms/500ms 간격 중단/85% 1초 기준을 유지한다. 예상 순수 처리 약 10분. 이전 코드의 15회/2회 원본과 표본을 합치지 않는다.

prepared의 전체·첫 입력 시즌 완료를 off와 current 각각의 5쌍으로 비교한다. 기존 ‘3쌍 이상 10% 느림 + 중앙값도 10% 느림’이면 해당 대조에서 채택 보류다. 실패·중단·불완전한 쌍은 악화 없음으로 처리하지 않는다. 큐 순서 개선은 준비된 커버의 변환 등록/대기·다른 시즌 본문 수와 실제 시즌 종료로 확인하며 특정 종료 순서를 테스트 정답으로 강제하지 않는다. 6시즌 한 부하의 통과로 모든 부하/운영 채택을 선언하지 않는다.

정합성/읽기: 모든 조건 JPEG274/자산137/동일 SHA·규격·출력42,259,800바이트·경로137 유지. off 읽기269회/223,800,086바이트, current/prepared는138회/112,771,684바이트다. prepared의 본문 hit131, 커버 선준비6이며 커버는 캐시 조회를 하지 않아 cache miss0이다. current의 hit131/miss6과 의미를 구분한다. 보관 예산 거절0/종료 보관·논리 바이트·scope·슬롯0을 확인한다.

테스트 설계 스킬 기준으로 실제 작은 JPEG의 커버 준비 완료 전 변환 금지·원본 1회 읽기·동일 출력, 커버 실패/준비 중 취소/예산0 fallback·종료 정리, 진단 기록에서 사전 준비와 cache hit 구분·순서 오류 거절, 15회 계획/다른 축·혼입/5쌍 실패 분모를 필수 검사로 추가한다. Mac/Linux 새 게이트를 통과한 코드로 실험하고 원본·결과·한계를 기록한다. UI·실제 Storage/Firestore 검증은 별도다.

## 구현과 필수 검증

실험용 `connectedExecutor(input, trace, prepareCover)`에 명시적 준비 분기를 추가했다. 본문 해시 barrier 다음 커버를 1회 다운로드하고 무결성/취소를 확인한다. 준비된 바이트는 별도 await 다운로드 없이 기존 저장 소비자로 전달한다. 대기 중 커버 바이트는 BufferInventory에 등록하며 형제 저장 종료 후 finally에서 반환한다. `reuse-entry.ts`는 prepared 조건만 이 옵션을 연결한다. 제품 processor·API·기본값 변경은 없다.

## 판정과 다음 범위

**커버 선준비는 재사용으로 발생한 시즌 완료 지연을 해결한 후속 후보로 유지한다.** 본문이 항상 먼저 끝나게 만드는 요구나 커버 무조건 우선 정책으로 바꾸지 않았다. 6시즌 5쌍에서는 정합성·실패·반복 악화 기준을 통과했으나, 전체10% 속도 개선·모든 부하·운영 채택을 증명한 결과는 아니다. 제품 기본값·클라우드 배포는 미변경이다.

다음 권고는 기존 단일 시즌/합성3브랜드 부하에서 off와 prepared를 확인하고, 별도로 보관 예산을 실제로 넘는 입력·예산 비교를 설계하는 것이다. 이후 Development의 실제 URL·Storage·Firestore에서 읽기 절감이 시간·비용·실패율에 미치는 영향을 확인한다. 이번 15회 승인 범위를 넘는 추가 실행 횟수/입력과 Development 격리 프로젝트·bucket·queue는 후속 실행 계획에서 구체화한다. 기존 128/256/512MiB 중 최적값은 아직 확정하지 않는다.
