# Q7 집중 계획·목록 운영 정책 이관

2026-10-07 KST. 사용자 확정: 원본 사이트 순서로 목록 표시, 나머지 추천 방향 채택, 목록·최근 운영 지침은 별도 작업으로 기록하고 현재는 Q7 완료에 집중한다. 범위 결정은 아래와 같으며 새 API·실제 종료 방법·추가 요청량/비용의 세부 실행 승인은 별도로 구분한다.

최신 정정: [시즌 실패 기록·처음부터 재시도 결정](season-failure-retry-decision.md). 중간 checkpoint 복원·미완료 실행 재연결은 제외한다. 종료 확인 뒤 해당 시즌을 처음부터 자동 재시도하고 총5회 소진하면 최종 실패로 남긴다. 전체 선택 시즌 처리 뒤 실패 목록에서 새 수동 재시도를 접수하며 이전 이력은 보존한다. 아래 기존 짧은 저장 재개 산술은 폐기한 제안 이력이며 새 실행의 요청량/비용으로 사용할 수 없다.

실패 목록 문서도 최종 확정: 시즌별 하나 유지·재시도 실패 시 최신화·성공 또는 명시적 ‘재시도 안 함’ 선택 시 제거·무선택이면 보관 기간 내 유지. 서버 시도/실행 기록은 기존 정책에 따라 보관한다. 목록 문서 제거를 시즌/파일/원본 실행 삭제나 Worker 취소로 해석하지 않는다. 현재 문서 반영만 완료했으며 구현·게이트 실행 완료가 아니다.

## 확정된 제품·운영 기준

- 목적: 최근 트렌드 확인.
- 최근1~2년의 룩북을 중심으로 최근 발매한 룩북부터 순서대로 확인·등록한다.
- 일반 시즌과 콜라보에 같은 기준을 적용하며 콜라보 우선순위는 없다.
- 후보 목록 처음10개, 더보기10개, 페이지를 넘겨도 선택 목록을 유지한다.
- 표시 단위10개를 선택 수 제한으로 사용하지 않는다. 최근1~2년은 운영 지침이며 과거 항목의 강제 차단 정책이 아니다.
- 운영 UI는 관리자 웹이다. 이 작업에서 iOS 관리자 화면을 새로 구현하지 않는다.
- 목록은 원본 사이트 순서대로 표시한다. 발매일 필드·미확인 표시·날짜 검수·날짜 재정렬은 추가하지 않는다.
- 기존 탐색 snapshot에서10개씩 조회하는 방향으로 확정했다. 이 목록 기능과 최근 운영 지침은 [관리자 웹 후속 작업](../admin-web-operations-migration/lookbook-list-operations-followup.md)으로 이관하며 Q7의 선행 조건이 아니다.

source: [관리자 웹 결정](../admin-web-operations-migration/decisions.md).

## 현재 구현과 정책의 차이

`season-discovery.ts`의 후보는 title/URL/cover/score이며, 원본 pageOrder를 기준으로 정렬한다. Worker가 저장하는 sortIndex는 이 결과 순서다. 현재 후보 데이터에 검증된 발매일 계약은 없다. `FirestoreSeasonCandidateRepository`는 published discovery의 newSeason 후보 전체를 sortIndex순으로 읽으며 페이지 조회가 없다. 관리자 웹 프레임워크·UI는 아직 미구현이다.

따라서 UI 표시 수10, 사이트에서 실제로 수집하는 범위10, 발매일 기반 정렬은 서로 다른 변경이다. 원본 HTML 한 번에29개 목록이 담긴 UNAFFECTED에서는10개씩 표시해도 HTML 다운로드 수가 줄어드는 것은 아니다. 본문 이미지 처리는 선택한 룩북만 수행한다.

기존 서버 요청 상한80과 시즌 동시성6은 별개다. 새로운 제품 선택 제한6/10은 도입하지 않는다. 기존 기술 상한80을 제거하거나80개 초과 선택을 자동으로 여러 FIFO 접수로 바꾸는 것은 이번 제안에 포함하지 않는다. 필요하면 별도 계약을 정한다.

## 확정한 범위

### 목록·운영 지침은 별도 작업

기존의 상한이 있는 목록 탐색 결과를 snapshot으로 유지하고 서버/API에서10개씩 조회하는 방향을 확정했다. 원격 사이트의 전체 탐색 비용을10개 수집 수준으로 낮춘다는 보장은 없다. 실제 cursor·만료·선택 보존·권한과 웹 구현은 관리자 웹 후속 작업에서 설계한다. 현재 Q7에 목록 API/UI를 추가하지 않는다.

날짜에 따른 정렬안을 채택하지 않았다. 원본 사이트 순서를 유지하며 ‘최근 발매한 룩북부터 확인·등록’은 운영 지침으로만 기록한다. 원본 순서가 검증된 발매순이라고 주장하지 않는다. 이전의 날짜 미확인 표시·검수 제안은 철회한다.

### Q7 완료 기준과 장시간 플랫폼 검증

사용자 확정: 기존 정상 A/B·A~J 결과와 짧은 실제 비정상 종료 정산·처음부터 재시도·시도 소진 및 실패 결과·새 수동 재시도를 Q7 완료 범위로 둔다. 중간 복원/저장 이어 실행은 제외한다. 현재12/14/15분 안전장치와 로컬 시간 경계 검사는 유지하고 실제12분/14분 장시간·플랫폼 deadline 실측은 후속 미검증 항목으로 이관한다. 선택 자유·운영 지침이 긴 작업을 기술적으로 방지한다고 주장하지 않는다.

이전 L/T/O 장시간 안은 이번 Q7 실행 범위에서 제외하되 원본 계획과 미검증 상태를 남긴다. 기존 실패/미관측 조건을 통과로 바꾸지 않는다. QL03의 원래 active 중 신규 접수 조건도 미관측 이력으로 남기며 짧은 복구 시나리오의 실제 B 대기 증거와 구분한다.

실제 종료 증거가 없으면 새 시도나 다음 브랜드를 시작하지 않는 원칙은 유지한다. 짧은 실제 종료·처음부터 재시도와 실패 결과의 새 증거가 확보되기 전 Q7을 완료 처리하지 않는다.

## 이전 짧은 Q7 저장 재개 산술 — 폐기한 제안 이력

아래는 미완료 저장 재개를 전제로 한 옛 제안이다. 최신 처음부터 재시도·실패/수동 재시도 계약의 입력·요청량·비용·승인으로 사용하지 않는다.

새 A2026SS 생성·탐색→import→정상검토승인 저장을 실행하고, 지정 자산의 공개 전 중단 구간에 새 B 생성·탐색을 접수한다. 실제 종료 증거 확인·복구 정산·미완료 저장 재개 뒤 B가 진행되는지 확인한다. 기존 정상A/B·A~J는 반복하지 않는다.

- 논리 mutation4회:브랜드 생성·탐색2 + import1 + 승인1.
- 추가 고의 종료1회. 부하 지연으로12~15분을 기다리는 실험은 포함하지 않는다. 종료 방법·정확한대상/1회표식·인가·기능해제는 R1/R2에서 별도로 확정한다.
- 최종2026SS JPEG62개/2,353,608B, 실패 실행 전체 업로드를 보수적으로 포함하면 최대계획124개/4,707,216B.
- 원본 GET:추출30+최종저장31+중단실행 전체 재다운로드 여유31=92회/7,726,194B. SDK·이미지 내부 재시도는 별도이며 과금 절대상한이 아니다.
- 최종 content 검증 GET62회/2,353,608B. 이전 미공개 객체는 metadata만 확인하고 삭제하지 않는다.
- 처리 창 최대30분·추가관리예산US$1·기존누적추정US$10 중단 기준을 제안한다. US$1은 확정요금/강제결제상한이 아니다. 이전3USD/11접수안은 승인되지 않았으며 새 예산을 이미 승인된 것으로 간주하지 않는다.

이 산술은 최소 실행안 후보다. R0의 Q7 범위 변경은 확정됐다. 복구 기술계약/필수테스트/실제 종료 방법·추가 요청량/비용의 상세 확정 후에만 해당 구현·원격 실행으로 이어간다. 이번 범위 선택을 새 고의 장애 실행 승인으로 해석하지 않는다.
