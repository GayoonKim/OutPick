# 시즌 실패 기록·처음부터 재시도 결정

2026-10-07 사용자 확정. Q7에서 추가하려던 중간 checkpoint 복원·미완료 execution/continuation 이어 실행은 제외한다. 기존 코드의 구현 완료를 뜻하지 않으며 변경 계약·검증 계획을 먼저 정리한다.

## 확정 흐름

1. 시즌별 처리 시도와 결과를 서버에 기록한다. Worker 비정상 종료도 종료가 확인된 뒤 실패한 시도로 기록한다.
2. 재시도 가능한 실패는 같은 요청 차례에서 해당 시즌을 처음부터 자동 재시도한다. 최초 포함 총5회이며 별도의 누적 재시도 시간 창은 두지 않는다. 개별 요청 timeout과 기존 플랫폼 실행 제한은 유지한다.
3. 총5회 소진한 시즌은 최종 실패로 남긴다. 완료된 다른 시즌을 다시 실행하거나 일괄 실패로 변경하지 않는다. 아직 시작하지 않은 시즌도 처리 대상에서 누락하지 않는다.
4. 선택한 시즌들의 처리가 모두 성공·검토 대기·최종 실패 등 해당 차례의 종료 상태에 도달하고 실행 중 작업이 정리되면 결과를 보여주고 다음 요청으로 진행한다. 검토 대기는 등록 성공과 구분한다.
5. 처리 결과에서 실패한 시즌을 확인해 사용자가 수동 재시도할 수 있도록 한다. 명시적 수동 재시도는 FIFO 맨 뒤의 새 요청·새 실행이며 처음부터 처리하고 새 총5회 예산을 부여한다. 이전 서버 실행 기록과 식별자를 보존한다. 실패 목록용 문서는 같은 시즌에 하나만 유지한다.

## 실패 목록용 문서의 최종 흐름

2026-10-07 사용자 최종 확정. 목록용 실패 문서와 서버 시도/실행 기록을 구분한다.

| 상황 | 실패 목록용 문서 |
|---|---|
| 최초 최종 실패 | 해당 시즌의 문서 생성 |
| 수동 재시도 접수·진행 | 같은 문서를 대기·진행 상태로 갱신 |
| 수동 재시도도 최종 실패 | 같은 문서의 최신 실패 원인·시각·마지막 요청/실행 식별자 갱신. 별도 실패 문서를 계속 추가하지 않음 |
| 수동 재시도 성공 | 실패 목록용 문서 제거 |
| 명시적인 ‘재시도 안 함’ 선택 | 실패 목록용 문서 제거 |
| 아무 선택 없음 | 기존 보관 정책의 기간 내 목록 유지. 화면 닫힘이나 무응답을 ‘재시도 안 함’으로 간주하지 않음 |

목록 문서를 제거해도 시즌/게시물/파일이나 서버 실행 기록을 함께 삭제하지 않는다. 서버 기록은 기존 합의인 실패·중단 상세 해결/최종 종료 후30일, 관련 판정 감사90일 등 원래 보관 정책에 따라 정리한다. 이는 실패 목록의 동일 시즌 문서가 계속 늘어나는 것을 허용하는 의미가 아니다.

갱신·제거는 대상의 최신 요청/실행 상태를 확인해야 한다. 이전 재시도의 늦은 응답이 새 실패 문서를 제거·덮어쓰지 않도록 한다. 실행 중인 요청 취소는 별개 기능이며 목록 제거로 진행 중 Worker를 취소하지 않는다. 실제 저장 경로·문서 식별키·인가·멱등·동시 요청 API는 후속 세부 설계에서 구체화한다.

## 실패 결과와 이력

- 결과에서 어느 시즌이 실패했는지 알 수 있도록 시즌 식별/제목/원본 URL과 현재 결과를 연결한다.
- 서버에는 기존 요청·batch/job/execution·시도 번호, 실패 단계/사유/시각, 실제 종료 확인 근거와 최종 실패 여부를 남긴다. 새 수동 재시도의 실행과 원래 실패 실행을 연결한다.
- 실패·중단 상세 보관은 기존 합의인 해결/최종 종료 후30일을 유지한다. 복구/종료 판정 감사90일 및 현재 진행·검토에 필요한 기록 보호도 임의로 줄이지 않는다.
- 재시도를 시작할 때 서버 원본 실행 기록을 삭제하거나 성공 상태로 덮어쓰지 않는다. 목록용 문서는 위 최종 흐름대로 갱신·제거한다. 전체 결과에서 성공·실패·검토 대기를 구분한다.
- 정식 결과 화면·수동 재시도 UI는 관리자 웹 작업에서 구현한다. Q7은 서버 결과/API/검증 실행기로 계약을 확인하며 iOS 관리자 기능을 추가하지 않는다.

## 유지할 최소 안전장치

- 앱/웹 화면을 닫는 것만으로 서버 작업을 취소하지 않는 기존 계약은 유지한다. 이번 결정은 새 화면 종료 취소 기능의 승인이 아니다.
- 연결 timeout·heartbeat 소실만으로 Worker가 종료됐다고 판정하지 않는다. 종료 미확인 때 새 시도와 다음 브랜드는 시작하지 않는다.
- 종료 확인 후 이전 시도의 실행권과 늦은 공개 쓰기를 차단하고, 미완료 시도의 데이터 정리 대상과 새 시도를 분리한다. 이미 완료된 시즌·기존 룩북·다른 요청의 참조 파일은 보호한다.
- 처음부터 재시도하는 과정에서도 동일 시즌/게시물 중복 생성과 이전 파일 덮어쓰기를 막는다. 삭제 범위·시점, 공개된 부분 결과 처리, 재시도 전 정리 완료 조건은 세부 데이터 계약에서 확정한다. 현재 이 문서로 원격 데이터 삭제를 실행하지 않는다.
- Cloud Tasks 재전달 횟수와 실제 시즌 처리 시도 횟수는 구분한다. 승인 저장 continuation의 현재 예산 동작을 함께 점검하고 비정상 종료마다 새5회가 무한 부여되지 않도록 상세 설계한다.

## Q7 변경 범위와 다음 핵심

현재 `followup-admission.ts`의 `manualRetry`는 `awaitingReview/correctionRequired`와 수정 runtime 조건을 요구한다. 일반적인 최종 실패 시즌의 처음부터 수동 재시도 경로가 이미 연결돼 있다고 판단하지 않는다. 기존 자산만 재업로드하는 assetRetry와도 구분해 새 계약의 접수·인가·멱등·실행/이력 연결을 설계해야 한다.

정상 A/B·A~J 원본과 결과를 유지한다. Q7 잔여는 비정상 종료 정산 → 처음부터 자동 재시도 → 성공/총5회 소진 → 실패 결과 기록 → 새 수동 재시도 → FIFO 진행을 검증하는 방향이다. 동일 실패 문서 최신화, 성공/명시적 재시도 안 함에 따른 목록 문서 제거, 무선택 유지, 원본 실행 기록 보존과 늦은 응답 경합도 로컬 필수 검사에 포함한다. 실제12/14/15분 장시간 플랫폼 경계 실측은 후속 미검증이며 기존 로컬 시간 검사·안전장치는 유지한다.
