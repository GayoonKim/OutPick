# 실행 내 다운로드 재사용 비교 — 15회 결과

후속: [2회 단계 시각 진단](phase-3-reuse-diagnosis.md)에서 커버 변환이 다른 시즌 본문 뒤로 밀려 첫 시즌 종료를 늦추는 직접 대기를 확인했다. 아래 원인 추측은 15회 당시의 상태이며 최신 근거는 후속 문서를 따른다.

2026-10-03. 사용자의 ‘추천으로 진행해’로 승인된 15회를 완료했다. Mac/Linux 218개·필수 110개 통과, 15/15회 성공·정합성 일치. 읽기 횟수/바이트는 약 49% 감소했지만 전체 시간 개선은 1% 미만이고 **첫 입력 시즌 완료가 약 2.44배로 지연**됐다. 현재 재사용 조합의 채택을 추천하지 않으며, 예산 확대보다 지연 원인 확인을 먼저 권한다. 아래 실행 전 검토·승인 이력과 실제 결과를 구분한다.

## 확인한 제약과 추천

현재 UNAFFECTED 원본 전체는 112,771,684바이트로 128MiB보다 작다. 따라서 128/256/512MiB/전체 보관에서 예산이 부족하지 않을 것으로 예상된다. 실제 보관 peak와 거절 수로 확인하되, 이 자료로 네 예산의 최적값을 고를 수 있다고 해석하지 않는다. 해시 중복 제거 후 실제 저장 입력과 커버 수는 기존 golden을 따른다.

실제 URL의 품질 결과는 needsReview다. 관리자 검토를 넘어서 Buffer를 보존하거나 정상 자동 등록으로 표시하지 않는다. 앞서 승인한 별도 `local-connected` 실험으로 해시→중복 제거→같은 실행 저장의 재사용 비용을 측정한다. 제품의 추출/품질 판단, 실제 검토 후 새 scope의 miss 계약은 기존 경로와 회귀 테스트로 유지한다. 이 연결 실험은 실제 URL의 자동 등록 성공이나 완전한 processJob/Firestore 통합 검증이 아니다.

추천은 기존 입력으로 재사용 유무의 요청·바이트 절감과 보관 비용을 먼저 분리 측정하는 15회다. 대안은 off/256MiB만 각 3회인 6회로 먼저 좁히는 것이다. 6회는 실행 시간이 적지만 합의된 예산별 관측값을 한 번에 확보하지 못한다. 대용량 합성 부하를 바로 추가하면 예산 차이를 만들 수 있으나 이미지 중복 제거·실행 scope·동시 job 수·보관 수명에 따라 결과가 달라져 별도 입력 계약이 먼저 필요하다.

## 제안하는 15회 조건

- C 구조, 공용 다운로드 4/변환 1/업로드 4/경로 저장 제한 없음, 6시즌 병렬 폭 6을 유지한다. 실행 중인 시즌 각각 독립 source scope를 사용하고 인스턴스 예산만 공유한다.
- 기존 6시즌을 한 부하로 고정하고 재사용 off/128/256/512MiB/전체 보관을 각각 3회, 총 15회 측정한다. 전체 보관은 유한 입력만이며 안전 감독기는 유지한다.
- 순서: off→128→256→512→전체 / 128→256→512→전체→off / 256→512→전체→off→128. 전 회차 새 고정 이미지 컨테이너, Linux ARM64, 1 CPU/2GiB/swap 없음/외부 네트워크 없음, 읽기 전용 입력, 무결성 검사 후 측정이다. cold-cache라고 부르지 않는다.
- 해시 단계는 실제 resolveContentHashDedupe를 호출하고 onHashedBytes로 성공한 바이트만 보관한다. 중복 pruning 후 같은 scope에서 저장하며, 종료 시 정리한다. 전체 시즌 사이에 새로운 해시 완료 장벽은 넣지 않는다.
- 보관 miss는 기존 로컬 원본을 다시 읽는다. 변환은 실제 jpegBytes, 업로드/경로는 기존 spy, JPEG SHA/규격/바이트/순서는 기존 golden과 대조한다. 임의 네트워크 지연이나 외부 재다운로드는 추가하지 않는다.
- 메모리 100ms 표본, 간격 500ms 초과 환경 중단, 한도의 85% 이상 1초 지속 시 회차 중단을 유지한다. 메모리 중단도 분모에 남기고 환경·정합성 실패는 후속 실행을 보류한다.
- 시간 예상은 직전 6시즌 약 38초를 참고하면 순수 처리 약 10분이며 준비·검증 시간은 별도다. 새 연결 경로와 메모리 효과 때문에 실제 소요시간은 달라질 수 있다. 클라우드 비용·원격 요청은 발생시키지 않는다.

## 지표와 판정

매 회차 전체 연결 완료·첫 입력 시즌 완료 시간, CPU/컨테이너 메모리/표본 간격/실제 슬롯, 원본 읽기 요청·바이트, hit/miss/예산 거절/최대 보관량, 업로드 spy·경로 수, 종료 시 Buffer·scope 정리를 기록한다. 보관 캐시 payload 계수와 논리 처리 Buffer 계수는 같은 바이트를 가리킬 수 있으므로 단순 합산해 RSS로 표시하지 않는다. 실제 cgroup 메모리는 별도로 보고한다.

기존 순차 연결 검사의 예상 대조값은 off **269회·223,800,086바이트**, 보관이 충분한 on **138회·112,771,684바이트**, hit 131/커버 miss 6/예산 거절 0이다. 병렬에서도 golden과 실제 읽기 기록으로 확인한다. 두 조건 모두 137개 자산·274개 JPEG·42,259,800 출력 바이트·137회 경로 spy를 유지해야 한다. 15회 모두 성공하면 JPEG 총 4,110개를 대조한다. 이는 로컬 읽기와 전송 spy의 수치이며 실제 HTTP/Storage 요청으로 표기하지 않는다.

재사용 on에서 요청·읽기 바이트가 줄어도 시간이 10% 개선된다고 보장하지 않는다. 로컬 읽기 비용은 네트워크 비용과 다르다. 세 번 모두 성공한 조건에만 시간 중앙값을 계산하고 중단을 감추지 않는다. 이번 3회 탐색에 5쌍 반복 악화 판정이나 최종 채택을 적용하지 않는다. 예산 거절이 모두 0이면 예산별 성능 차이의 원인을 예산 제한으로 해석하지 않는다.

## 구현 계획과 필수 검증

승인 후 변경 후보는 Worker `src/performance/`의 별도 reuse plan/runner/report/entry/test, 기존 `frozen-input.ts`의 검증된 입력 접근, `container-runner.ts`의 명시적 재사용 실행 종류, `verification/lookbook-import.json`과 관련 하네스다. 기존 구조·변환 비교 계획과 결과 schema를 재사용 실험으로 오인하지 않도록 구분한다. 실제 소스 보관/해시/변환 함수는 이미 구현된 `pipeline/source-buffer-store.ts`, `extraction/dedupe.ts`, `processor.ts` 경로를 재사용한다. 제품 기본값·HTTP API·Firestore 계약·앱 DI 변경은 범위 밖이다.

메모리도 off보다 높게 관측됐다. 특히 `reuse-256-3`은 최고 91.49%였으나 감독기 중단은 없었다. 85%/1초 표본 감독 조건을 바꾸거나 해당 회차를 제외하지 않았다. 순간 최고값의 상세 원인은 이번 계측으로 분해하지 못했고, 다른 예산이 더 안전하다는 인과적 결론도 내리지 않는다. 모든 회차 최대 자원 표본 간격 175.278ms, 종료 보관량/openScopes/논리 Buffer·슬롯 active/queued 0, 정리 대기 파일 0, 해당 이미지의 실행 중 컨테이너 0을 확인했다.

## 첫 시즌 지연의 확인 범위와 다음 추천

원본 시즌 기록을 대조하면 off 첫 반복은 2026FW 약 14.0초부터 차례로 완료됐고, 256MiB 첫 반복은 2026FW 약 33.8초부터 종료가 몰렸다. 전체 작업량/JPEG/변환 동시성은 같으며, 변환 대기열 최대는 양쪽 모두 272였다. 단순 변환 개수 증가로 설명할 결과는 아니다.

코드에서 확인한 차이는 cache hit인 본문은 다운로드 대기 없이 변환 FIFO에 제출되지만, cache miss인 커버는 공용 다운로드 후 변환에 제출된다는 점이다. 원본 커버는 해시 후보에 포함되지 않아 항상 miss 6건이다. **커버가 다른 시즌 본문 뒤로 밀려 첫 시즌 완료를 늦췄을 가능성은 추측이다.** 이번 기록에는 개별 대상/커버의 단계 제출·완료 시각이 없어 원인 확정은 못 한다. 검토 장벽을 없애거나 커버 우선순위·묶음 크기를 임의 변경하지 않았다.

다음 추천은 예산 압박 실험보다 **본문/커버의 다운로드·변환 제출/완료와 시즌 종료를 연결하는 최소 계측으로 지연 원인을 먼저 확인**하는 것이다. 원인이 확인된 뒤 커버 준비 순서 또는 이미지 제출 방식 개선의 범위·회차를 정해 동일 입력으로 재비교한다. 128/256/512MiB를 실제로 가로지르는 부하와 예산 선택, 실제 job 총 5회 계약, Development 네트워크/Storage/Firestore 검증은 여전히 별도 단계다.

이번 수정은 실험용 진입점·결과 검증과 테스트에 한정했다. 제품 기본 동시성/재사용 활성화·품질 검토·Firestore/API·배포·클라우드 쓰기·커밋 변경 없음. 데이터와 고정 이미지는 원본 재현을 위해 유지한다.
