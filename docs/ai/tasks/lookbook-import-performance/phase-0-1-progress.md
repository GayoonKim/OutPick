# 결과 검증·오버헤드 준비 측정·실행 구조 연결

이 문서는 Phase 0~1 시점의 결과다. 이후 실행 내 재사용·실제 저장 함수 회귀와 최신 게이트는 [Phase 2 기록](phase-2-reuse.md)을 따른다. 아래 재사용 미구현·152개 검증·오버헤드 수치는 당시 소스 기준 이력이다.

2026-10-03. 사용자 ‘진행’에 따라 Phase 0의 결과 검증과 계측 오버헤드 준비 측정을 진행하고, Phase 1의 공용 슬롯·묶음/보충/전체 제출 및 실제 저장 함수 연결을 구현했다. 기본 동시성·품질 판단·JPEG 규격·HTTP/Firestore 계약은 유지한다. 성능 최적값 채택, 재사용 캐시, 54회 구조 비교, 클라우드 배포 완료를 뜻하지 않는다.

`PipelineRuntime`이 없는 기본 경로는 기존 job별 asset 3개/해시 4개, 두 변환과 두 업로드 Promise.all 흐름을 유지한다. 실험 경로는 `ServerDependencies.pipeline`으로 한 객체를 주입해야 모든 요청이 같은 제한을 공유한다. 현재 `index.ts`/환경변수는 이 객체를 생성하지 않으며 요청 본문으로 실험 정책을 선택할 수도 없다. 실험 설정을 제품 기본값으로 선택한 변경은 아니다.

실험의 해시 후보와 asset 대상은 서로 다른 `LaunchPolicy`를 사용한다. `batch`는 묶음 크기와 내부 실행 폭을 별도로 받으며, 묶음 내부 성공/실패가 모두 정리된 뒤 다음 묶음을 시작한다. `refill`은 빈자리를 보충한다. `concurrency:null`과 자원별 `limit:null`은 유한 입력에 앱의 해당 개수 제한을 두지 않는 뜻이며 libuv/libvips/SDK 내부 풀 제한을 제거하지 않는다.

다운로드는 개별 시도 종료 후 슬롯을 돌려주므로 내부 재시도 대기 동안 다운로드 슬롯을 잡지 않는다. 해시 다운로드와 asset 다운로드가 같은 슬롯을 공유한다. 변환은 각 출력 JPEG, 업로드는 각 파일 단위이고 경로 저장은 두 업로드 성공 후에만 실행한다. 실험 경로의 변환/업로드 실패는 형제 작업 종료 후에 전달한다. 기본 A의 선행 실패 반환 특성은 비교 기준 보존을 위해 유지한다.

대기 중 취소는 큐에서 제거하고, 이미 실행 중인 작업은 실제 Promise가 종료할 때까지 슬롯을 돌려주지 않는다. 이것은 실행 중 SDK 요청을 강제로 취소한 구현이 아니다. 실험 전체 중단 감독기/dispatch 중단과의 연결은 후속 범위다. 중간 원본/JPEG 대기 버퍼의 합산 byte 제한과 다운로드 재사용도 아직 없다.

## 결과 검증 의미

`validateResultSet(plan, results)`는 누락/중복/알 수 없는 회차가 있으면 집합 전체를 비교 불가로 처리한다. 결과와 계측의 입력·설정·소스 식별이 계획과 맞아야 하며 동일 계측 UUID를 다른 회차에 재사용할 수 없다. 성공은 정확성 true·양의 전체 시간·예정된 계측 수·정상 종료/자원 표본을 요구한다. 계측 off는 사전 계획에서 measurementCount=0인 경우에만 허용한다.

실패·중단·환경 미준비는 기록에서 제거하지 않는다. `valid=true`는 결과 집합 형식과 정합성 검사를 통과했다는 뜻이며 모든 실행의 성공 또는 성능 채택을 뜻하지 않는다. planned/recorded와 각 outcome 수를 함께 사용한다. 컨테이너 사용 가능 여부가 false인 로컬 기록은 보존하지만, 이 검증기로 85%/1초 안전 감독 완료를 주장하지 않는다.

준비 실행기는 실제 입력 파일의 SHA-256/길이를 검사하고 계획 파일을 실행 전에 기록한다. 게이트 소스 digest와 실행기 자체 digest도 보관한다. 검증기는 전달받은 digest의 일치를 검사하는 모듈이며, 임의 호출자의 소스 파일을 다시 해시해 진위를 보증하는 보안 경계는 아니다. 이번 실행은 게이트 직후 동일 코드의 빌드 산출물을 사용했다.

## 계측 오버헤드 준비 측정

입력은 2026 SS의 본문 30개+커버 1개, 출력 62개/2353601 bytes다. 파일을 미리 읽고 실제 JPEG와 upload 함수를 사용했다. 업로드는 메모리 spy, 경로 기록도 로컬 callback이다. 입력 읽기와 출력 SHA 검사는 측정 시간 밖이다. 이미지 3개, 각 이미지의 두 변환/두 업로드를 병렬 실행했다. 계측 출력은 JSON 직렬화·메모리 수집이며 Cloud Logging 지연은 측정하지 않았다.

준비 실행 off/on 각 1회 후, off→on/on→off를 교차한 5쌍을 측정했다. 이는 54회 구조 비교와 별도다. 숫자를 본 뒤 합격선을 새로 정하지 않았으며 기술적 정합성 통과와 시간 결과를 구분한다.

| 코드 상태 | off 중앙값 | on 중앙값 | 중앙값 차이 | 쌍별 차이 범위 |
| --- | ---: | ---: | ---: | ---: |
| 결과 검증 추가 후, 저장 helper 분리 전 | 412.86ms | 414.58ms | +0.42% | −2.76%~+4.92% |
| 저장 helper 연결 후 최신 게이트 코드 | 409.43ms | 411.26ms | +0.45% | −3.04%~+8.01% |

두 실행 모두 준비 2회+본 측정 10회가 정상이며 출력 해시/bytes가 일치했다. 각 on/off 비교는 해당 실행 내부에서 같은 소스·자료를 사용했다. 첫 행과 둘째 행을 제품 개선 전후 속도 비교로 사용하지 않는다. 짧은 로컬 변환 부하의 5쌍으로 실제 Worker/네트워크/Cloud Run 오버헤드나 작은 성능 차이를 확정할 수 없다.

원본 위치는 `output/lookbook-import-performance/unaffected-2026-10-03/` 아래다.

- helper 분리 전: `overhead-c97bda28-c6c1-406b-a228-7c8dcd968c6e/{plan.json,runs.jsonl,result.json}`, 실행기 `measure-overhead.mjs`.
- 최신 helper: `overhead-c256fd9e-c6d4-4b09-967d-f55295e1a9e4/{plan.json,runs.jsonl,result.json}`, 실행기 `measure-pipeline-overhead.mjs`.
- 준비 측정의 input digest는 각 `plan.json`과 `result.json`에 있으며, 공개 원본을 다시 요청하지 않았다.

## 남은 단계

고정 자료 회귀도 실행했다. `verify-pipeline.mjs`의 원본 결과는 `output/lookbook-import-performance/unaffected-2026-10-03/pipeline-validation-06cb2791-a36e-49fb-aaad-0315eedc877e/{plan.json,result.json}`이다. 기본 경로와 묶음/공용 슬롯 경로에서 각 6개 시즌의 추출·저장을 분리한 24개 결과가 모두 정상·정합성 검사를 통과했다. 각 경로의 JPEG 274개/42259800 bytes가 기존 출력 해시와 일치했고, 메모리 경로 spy 137회는 두 업로드 완료 후에만 호출됐다. 실제 Firestore 경로를 읽고 쓴 결과는 아니다.

검사용 슬롯은 다운로드4/변환2/업로드4/경로1, 묶음8이며 초기 성능 실험값을 확정한 것이 아니다. 관측 최대 active는 4/2/2/1, 종료 시 모든 active/queued=0이다. 실제 원격 다운로드는 없으며 다운로드 슬롯에는 로컬 자료 읽기가 주입됐다. 변환 대기 시간 합계나 이 검사 실행 시간을 후보 성능 순위로 사용하지 않는다.

실행 구조의 단위/함수 연결 검증과 별개로, 전체 Worker의 Storage/Firestore 경로·ready·부분 재시도 통합 검증과 실제 관리자 화면 QA는 남아 있다. 시즌 스케줄러(A~F 전체 연결), 실행 내 재사용, 중간 byte 관측/정리, 전체 실험 manifest·중단 감독·실패 분모·최종 판정기를 연결해야 54회 구조 비교를 시작할 수 있다. 초기 조합은 실행 전에 제시하며 이번 회귀 검사의 슬롯 수를 최적값이나 실험 초기값으로 확정하지 않는다. 클라우드 실행/배포는 후속 실행안 승인 전 미실행이다.
