2026-10-03. 사용자 지정 목록의 2024~2026년 SS/FW 6개 시즌을 수집하고 로컬 무결성 검사를 완료했다. 성능 비교·Storage 업로드·Firestore 쓰기·배포는 미실행이다. 이 문서는 이미지 전체에 대한 관리자 등록 승인을 대신하지 않는다.

## 보관과 재현

로컬 원본 위치: `output/lookbook-import-performance/unaffected-2026-10-03/`. HTML·이미지·원본 URL·검사 JSON은 git 제외 output에 보관한다. 외부 사이트는 성능 반복마다 재수집하지 않는다.

- `manifest.json`: 시즌·후보 순서·원본 bytes/해상도/포맷/hash, HTML hash.
- `covers.json`: 커버 6개와 본문 중복 여부.
- `browser-checks.json`: 브라우저 본문 URL 순서 SHA-256과 확인 범위.
- `input-validation.json`: 실제 파일 hash·HTML 재추출·브라우저 순서·fallback·출력 규격/bytes 검사, `passed`.
- `instrumentation-validation.json`, `verify-instrumentation.mjs`: 계측 구현 후 실제 hash/JPEG/upload 함수 연결 검사. 추출/저장 계측 12개 정상 종료, 출력 274개가 기존 hash/bytes와 일치, 업로드는 메모리 spy. [검증 범위](instrumentation.md).
- `capture.mjs`, `capture-covers.mjs`, `verify-input.mjs`: 이번 자료 확인용 일회성 도구. 이미 있는 원본을 덮어쓰지 않도록 `wx` 사용. 공용 실행 자동화로 추가한 것은 아니다.

본문/HTML 입력 digest: `c4fb65f71fa5f26a6f9a531e58b8629ba2aff0f612c81e75e7cdeb05028f0c56`. 커버는 covers.json의 파일별 SHA-256을 별도로 검증한다. 이 digest 하나가 커버·후속 실행 설정까지 포함한다고 주장하지 않는다.

자료 수집은 당시 기본 Node 22에서 수행했으며 최종 로컬 파일 검사는 Node 24.19.0에서 수행했다. sharp/libvips 버전은 `input-validation.json`에 기록했다. 표의 압축 bytes는 현재 processor와 같은 rotate/inside/withoutEnlargement/mozjpeg 설정으로 계산한 값이다. 제품 processor 전체 실행이나 시간 벤치마크가 아니다. 출력 bytes는 계산 후 해제했고 업로드하지 않았다.

## 첫 비교 입력과 요청량

기존 추천을 유지해 단일 시즌은 2026 SS(가벼운 자료), 다중 시즌은 6개 전체(해상도·포맷·크기가 섞인 자료)를 사용한다. 세 브랜드 부하는 로컬에서 같은 6개 시즌을 세 합성 브랜드에 2개씩 배정하는 검토안이다. 실제 세 브랜드/호스트의 네트워크 성능으로 해석하지 않는다.

동일 실행 재사용 행은 메모리 보관 성공·원본 불변·자동 등록 연결을 전제로 한 비교값이다. 실제 UNAFFECTED 경로는 검토 대기로 실행이 끝나므로 현재 합의한 실행 내 캐시로 이 절감을 얻는다고 볼 수 없다. **추출→검토 대기와 승인 후 저장을 각각 측정하고, 동일 실행 재사용은 별도 로컬 연결 실험으로 분리한다. 2026-10-03 사용자가 추천안으로 확정했다.** 기존 품질 검토를 우회하지 않는다.

54회 로컬 비교를 단일/6시즌/합성3브랜드에 각 18회 배정하면, 재사용 off·무재시도 기준 이미지 GET 상당량은 10782건/8148833838 bytes, 업로드 상당량은 10980파일/1563717618 bytes다. 이는 로컬 재생 부하이며 실제 외부 요청·Cloud Storage 전송량이 아니다. HTML·Firestore·Cloud Tasks 호출과 실패 재시도는 별도로 계측한다.

Development 최대 45회에서 같은 입력을 각 15회 쓸 경우, 모두 재사용 off라는 계산 예시는 GET 8985건/6790694865 bytes, 업로드 9150파일/1303098015 bytes다. 실제 운영안은 유력 후보·데이터 격리·review 처리 방식 확정 후 다시 산출한다. API 비용 추정이나 청구 상한을 이 bytes만으로 확정하지 않는다.

재사용 예산 128/256/512MiB의 차이를 이 6개 시즌만으로 충분히 구별할 수는 없다. 본문 전체가 106.644MiB라 입력 보관만으로는 128MiB에 도달하지 않는다. 예산 초과 동작은 fake 기반 필수 테스트로 검증하고, 성능에서 예산 차이를 비교할 추가 부하 규모는 별도 제시한다. 디코딩·출력·Chromium 등은 이 보관 예산 밖의 실제 메모리 사용이다.

## 기존 Worker 게이트 결과

`verification/lookbook-import.json`을 신설하고 `scripts/run-tests.mjs`로 현재 src의 모든 테스트에 대응하는 lib 산출물을 수집한다. 게이트 reporter/result가 한쪽만 지정되거나 테스트 소스가 0개이면 실패한다. 기존 `npm test`의 빌드 단계를 유지한다.

최종 실행: `output/verification/1790997260603-fca54bb0-1335-465a-be50-efbbe87c4803/summary.json`, `passed`. lint, TypeScript build, Node 테스트 118개(필수 ID 10개), fixture corpus를 실행했다. HEAD `1d67d61faa04984783083971688a7c628df74748`+작업 트리, 입력 digest `cfea02b7bbbc0fee6a1565433351639ac67c1c9738d5623972e69d518e254fe2`, 102파일.

최초 실행 `1790997197110-18eb30c2-4578-4235-9579-28b0ab48f309`은 실패로 보존했다. 원인은 소스가 사라진 `lib/extraction/adapters/registry.test.js`의 옛 버전 기대값과 sandbox의 localhost listen EPERM이었다. 현재 소스 기준으로 수집하게 수정했으며, 테스트 기대값을 바꾸거나 실패한 현행 테스트를 제외하지 않았다. localhost 권한으로 재실행한 118개가 모두 통과했다.

위 118개는 계측 전의 기존 동작 회귀 기반이다. 이후 단계 계측과 신규 16개 검사를 추가한 최신 게이트 134개가 통과했다. [계측 구현·검증 결과](instrumentation.md)에 코드 digest·원본 로그·수치 해석을 기록했다. 새 스케줄러·캐시·총 5회 상태 전이·성능 판정·Cloud Run 메모리 감독은 아직 구현/검증하지 않았다. Phase 0 전체 완료나 성능 개선 완료를 의미하지 않는다.

후속 현황: 결과 검증과 공용 슬롯/실행 구조를 추가한 최신 게이트는 152개 통과다. 기본/실험 경로의 고정 자료 6개 시즌 출력 일치와 오버헤드 준비 측정은 [최신 기록](phase-0-1-progress.md)을 따른다. 위 118/134개 및 스케줄러 미구현 문구는 그 당시 이력이며 현재 전체 검증 상태가 아니다.
