# 정책 선택 이유와 재검토 조건

- D11: 사용자3MiB 통일/QA 조정 확정. 기존 목록2·채팅/댓글3·마이페이지5MiB를 아바타 썸네일의 단일 한도로 맞춰 호환 요청을 병합한다. 다운로드 최대 허용량이지 디코딩 픽셀/메모리 예산이나 디스크 캐시 크기가 아니다. 원본 한도와 분리하며 기존5MiB 경로 자료 실패는 QA한다.

- D10(2026-09-18): 댓글에서 메모리에만 남은 썸네일을 참여방 등 디스크 보관 사용처에서 요청할 때, 화면에는 즉시 표시하고 필요 시 백그라운드 재인코딩·저장한다. 같은 사진 저장은 단일화하고 공용 준비/I/O 예산·세대 보호를 사용한다. 압축 데이터 상시 추가 보관이나 저장 목적 재다운로드는 선택하지 않았다. 발생 빈도가 낮다는 것은 미측정 추측이며 CPU/파일 크기를 QA한다. JPEG/PNG는 실제 썸네일의 용량·변환 시간·일반 표시 품질 비교 후 선택한다. PNG 권고를 확정으로 해석하지 않는다.
- 원본-only 예외 정정: 정상 앱 upload는 두 파일 성공 후 두 경로를 함께 기록한다. 서버 parser는 개별 optional 필드라 단독 경로를 완전히 금지하지 않지만 실제 데이터 존재는 미확인이다. 필수 선행 결정에서는 제외하며 정상 쌍을 기준으로 진행한다. 기존 fallback 변경이 필요하면 실제 근거를 확인한다.

- D01: 같은 서비스의 소비자를 함께 다뤄 취소/재시도 불일치를 남기지 않는다. 댓글 제외안은 범위가 작지만 같은 문제를 후속으로 남기므로 채택하지 않았다. 방 대표·첨부 이미지는 별도 순서로 유지한다.
- D02/D06: 일반 표시에는 썸네일, 실제 확대에 원본을 사용한다. 원본은 반복 열람 효과가 확인되지 않아 메모리/디스크 캐시에 보관하지 않는다. 반복 확대 때 다운로드 지연/데이터 사용이 늘어나는 대가를 수용했다. 반복 열람이 실제 문제일 때만 캐시를 재논의한다.
- D03: 동일 사진의 재구성은 유지하고 다른 사진에는 이전 결과를 차단한다. 요청 취소만으로 늦은 callback을 모두 막는다고 가정하지 않는다. 공용 다운로드 전체가 아닌 개별 소비자를 해제한다.
- D04: 룩북과 같은 viewport 원리와 시작값을 적용하되 아바타 경로를 중복 제거한다. UIKit 자체 prefetch만 의존하는 안보다 두 UI 기술의 정책을 맞추기 쉽다. 숫자는 최적값이 아니며 실기기 증거로 조정한다.
- D05: 댓글·미참여 탐색은 일회성일 가능성이 있다는 사용자 판단을 반영해 memory-only, 참여방·내 프로필은 반복 사용을 고려해 디스크 허용. 이는 사용 빈도를 실측한 결론이 아니다. 방별 저장소·핀은 중복/참조 관리 부담으로 채택하지 않았다. 기존 디스크 읽기는 허용하고 이후 디스크 소비가 생기면 승격한다.
- D07: 고정5초 재요청 억제 제안은 사용자 결정으로 철회했다. 새로운 표시 계기에 즉시 시도하며 in-flight 중복은 합친다. 타이머 반복/실패 즉시 루프는 없다. 객체 없음/접근 거부는 앞선 합의대로 자동 반복을 멈추고 경로 변경/명시적 새로고침에서 재허용한다. 에러 분류에 로그인 갱신 등 사용자 영향이 발견되면 재논의한다.
- D08: 방을 나가도 같은 사용자를 다른 곳에서 보므로 캐시는 용량 정리에 맡긴다. 로그아웃은 재로그인 성능보다 계정별 저장 정책과 정리 일관성을 선택했다. 다른 사용자 최신화는 기존 조회 시점 기준이며 새 구독을 추가하지 않는다.
- D09: 기능별 서비스와 공용 pipeline 책임을 유지한다. 원본 비저장도 공용 예산 밖으로 우회하지 않는다. 성능만을 위한 새 캐시/라이브러리/서버 변경은 추가하지 않는다. fake 기반 비동기 경합과 실제 기기 표시 QA를 함께 사용한다.
