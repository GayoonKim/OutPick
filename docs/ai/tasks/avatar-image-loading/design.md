# 아바타 이미지 로딩 설계

상태: 사용자 설계 합의·세부 계획 작성 승인. 코드 구현 전.

## 목표와 범위

개선된 공용 이미지 pipeline 위에서 사용자 아바타의 표시 유지, 요청 수명, 선로딩, 사용처별 캐시를 통일한다. 대상은 프로필 상세·마이페이지·프로필 편집, 채팅 메시지·방 목록·참여자, 룩북 댓글·답글과 그 사용자 상세다. 같은 서비스를 사용하는 실제 사용자 표시 경로를 Phase 0에서 전수 매핑한다. Preview 전용 fake는 제품 화면으로 세지 않는다.

완료된 룩북 로고·시즌·포스트·좋아요·공유 이미지 작업을 다시 구현하지 않는다. 채팅방 대표 이미지, 메시지 첨부 사진·공유 카드·영상 썸네일, GIF, 관리자 preview, 일반 로컬 미디어, 공용 확대·저장 전체 개선은 다음 작업이다. 이번 확대 변경은 프로필 원본 정책을 주입하는 데 한정한다.

## 합의된 사용자 흐름

1. 등록·변경 때 기존 방식으로 썸네일과 원본을 저장한다. 서버 업로드 형식·해상도·경로 정책을 변경하지 않는다.
2. 일반 화면은 썸네일을 표시한다. 썸네일 경로가 없는 기존 자료는 원본 경로로 대체한다. 이 대체 경로가 원본 캐시 미저장 결정과 만나는 기술 계약은 Phase 0에서 확인한다.
3. 같은 사용자·경로의 화면 갱신은 기존 이미지와 진행 중인 요청을 유지한다.
4. 다른 사용자·경로 또는 명시적 제거로 바뀌면 이전 요청을 해제하고 이전 사진을 새 대상으로 표시하지 않는다. 결과 적용 직전 요청 identity·세션 세대를 확인한다.
5. 프로필 확대 진입 시 썸네일을 즉시 표시하고 원본을 다운로드한다. 원본 완료 후 교체하며 줌까지 기다리지 않는다.
6. 확대 원본은 화면 수명 동안만 보유한다. 공용 메모리·디스크 캐시에 읽기/저장하는 원본 재사용 경로를 두지 않는다. 공용 자원 제한·요청 병합·취소는 사용한다. 닫을 때 원본 참조·임시 파일·요청을 해제한다. UIImage 해제와 OS RSS 즉시 감소는 다른 현상이다.

## 선로딩

- 단일 화면은 현재 썸네일만 요청한다.
- 목록은 visible 우선, 진행 방향 1.5화면·반대 방향 0.5화면, 선로딩 최대 24개 고유 경로를 시작값으로 사용한다. visible 표시 요청 자체를 24개로 제한하지 않는다.
- 실제 화면에 아바타가 표시될 메시지/행을 기준으로 중복 경로를 제거한다. 숨긴 내 아바타 등은 불필요하게 준비하지 않는다.
- 범위 이탈 후 300ms 동안 요청 해제를 유예한다. 복귀 시 해제를 취소한다. 화면 종료·세션 변경은 즉시 해제한다.
- 이미 저장한 캐시를 viewport 이탈로 삭제하지 않는다. 다른 소비자가 있으면 다운로드를 유지한다.
- UIKit/SwiftUI 어댑터는 화면별 geometry·방향을 제공하고 정책 계산과 작업 수명은 별도 구성요소가 맡는다. 기존 룩북 객체는 LookbookAssetImageRequest에 결합돼 있으므로 그대로 아바타에 주입하지 않는다.
- 초기값의 최적성은 미검증이다. 실기기 QA로 조정한다.

## 썸네일 캐시 계약

썸네일 다운로드 한도는3MiB로 통일한다(D11). 기존5MiB 경로 자료의 실패 여부를 QA하고 필요하면 조정한다. 디스크 저장 형식의 한도·원본 다운로드 한도와 구분한다.

| 사용처 | 새 다운로드 저장 |
| --- | --- |
| 룩북 댓글·답글 | 메모리만 |
| 미참여방 탐색·검색 사용자 | 메모리만 |
| 참여방 메시지·참여자·목록 미리보기 | 메모리+디스크 |
| 내 프로필·마이페이지 | 메모리+디스크 |
| 다른 사용자 프로필 상세 | 진입한 곳의 정책 유지 |
| 확대 원본 | 화면 소유만, 공용 캐시 없음 |

디스크는 방별이 아니라 공용 AvatarImageCache 상한100MiB/정리목표75MiB다. memory-only 요청도 기존 디스크 캐시는 읽을 수 있다. 메모리에서 찾은 썸네일을 참여방에서 요청하면 화면에는 즉시 반환하고 디스크 보관 대상으로 승격한다. 화면별 별도 캐시·방별 영구 pin은 만들지 않는다. 참여 여부는 기존 앱 세션/방 상태를 사용하며 이를 위해 서버 조회를 추가하지 않는다.

## 실패와 재시도

- 최초 실패: 기본 이미지. 같은 사진을 이미 표시 중이면 유지한다. 다른 사용자/사진의 이미지는 유지하지 않는다.
- 스크롤로 다시 표시되거나 해당 사용자의 새 메시지가 표시되면 시간 제한 없이 재시도한다. 5초 억제·주기 타이머·실패 즉시 자기 재호출은 없다.
- 동시에 발생하는 같은 요청은 합류한다. 실패 완료를 영구 loaded 상태로 남기지 않는다. 관계없는 상태 재렌더를 새로운 표시 계기로 취급하지 않는다.
- 취소는 실패가 아니다. 늦은 성공뿐 아니라 늦은 실패도 새 이미지/상태를 덮지 못한다.
- 일시 오류는 위 표시 계기로 재시도한다. 앞서 합의한 객체 없음·접근 거부의 자동 반복 중단은 유지하며 경로 변경/명시적 새로고침에서 다시 허용한다. 네트워크 연결 감지 기반 자동 재시도는 추가하지 않는다.
- 확대 원본 실패: 썸네일 유지·명시적 재시도 버튼. 새로운 원본 요청은 동일한 무캐시 정책이다.

## 무효화와 세션

- 화면 종료/방 나가기: 해당 소비자·선로딩 해제, 이미 보관된 썸네일은 용량 정리 대상으로 유지.
- 사진 변경·제거 성공: 이전 경로 무효화 및 늦은 저장 차단. 실패한 편집은 기존 사진을 제거하지 않는다.
- 다른 사용자의 변경/제거는 기존 최신 프로필을 받은 시점에 반영한다. 서버 실시간 구독 추가 없음. nil 제거와 아직 조회하지 못한 상태를 구분한다.
- 로그아웃/계정 전환: 아바타 요청·메모리·디스크 정리, 이전 세션 결과 및 대기 저장의 재등장 차단. 정리 완료 전 새 세션 결과를 지우지 않도록 세대·순서를 관리한다.
- 계정 삭제: 기존 AccountDeletionLocalDataScrubber 경로를 유지하고 아바타 추가 상태까지 정리한다. 다른 이미지 캐시 정리 의미를 축소하지 않는다.

## 구조·기술·API·데이터

기존 Swift, UIKit/SwiftUI, async/await, actor, MVVM-C/Repository/UseCase/DI를 유지한다. 새 라이브러리·서버 API·Firestore/Storage 스키마·Rules·업로드 형식 변경은 계획하지 않는다. 로그인/권한/신고/차단 정책을 변경하지 않으며 캐시로 기존 표시 제한을 우회하지 않는다.

- 화면/셀: identity와 표시 상태, 이벤트 전달. 서버 SDK 생성 금지.
- 선로딩 구성요소: 경로 집합·방향·수명·표시 계기 관리.
- AvatarImageService: 명시적 사용처/저장 정책, 확대용 요청, 무효화.
- ImageCachePipeline/Coordinator/Processor: 공용 자원과 요청 병합·취소·세대, 승격/무캐시 지원의 최소 확장.
- AppCompositionRoot/각 Container: 같은 서비스와 세션 수명 주입. Coordinator: 프로필 진입 시 정책 전달 및 기존 화면 전환 유지.
- 로컬 요청에 필요한 값: 사용자ID, 정규화된 경로, thumbnail/original 표현, 저장 정책, 세션/표시 세대, visible/prefetch 우선순위. 공개 서버 DTO에 추가하지 않는다.
- 병합은 단순 사용자ID가 아닌 경로·표현·호환 다운로드 한도를 기준으로 한다. 원본 무캐시 요청과 썸네일 영속 요청의 정책 혼합을 막는다.

## 코드로 확인한 구현 가능성과 보완점

2026-09-18 후속 결정 우선: 메모리→디스크 승격은 필요 시 표시용 UIImage를 백그라운드 재인코딩한다(D10). JPEG/PNG는 실제 비교 후 선택하며 압축 바이트 상시 추가 보관은 도입하지 않는다. 원본-only 자료는 정상 앱 경로에서 생성되지 않고 실제 존재도 미확인이므로 필수 선행 결정에서 제외한다.

- AvatarImageService는 공용 pipeline을 사용하지만 저장 정책 인자를 외부에 노출하지 않는다. 로컬 경로는 Data(contentsOf:)로 직접 읽는다.
- ImageCacheStorePolicy는 memoryOnly/memoryAndDisk만 있고 Coordinator 성공은 항상 메모리에 저장한다. 원본에는 새로운 비저장 요청 계약이 필요하다.
- pipeline 메모리 fast path는 즉시 반환하므로 디스크 승격이 없다. 메모리 store는 UIImage만 보유하므로 원본 압축 바이트가 있다고 가정할 수 없다.
- 공용 요청 identity는 maxBytes를 포함한다. 아바타 소비자마다 기존 한도가 달라 같은 경로도 모두 합류한다고 단정할 수 없다.
- MyPage는 모든 상태 apply에서 요청을 취소한다. 댓글 CommentSafetyAvatarView는 완료 전 loadedPath를 설정한다. ParticipantListCell의 catch도 취소/identity 보호 대상이다.
- AvatarImageSource.merged는 nil을 덮지 않으므로 명시적 제거와 seed fallback 계약 확인이 필요하다.
- 프로필 viewer provider는 현재 cachedAvatar/loadAvatar를 주입한다. 공용 viewer가 fallback·다른 provider·내부 이미지 참조를 통해 원본을 보관하지 않는지 확인한다.

기술적인 미확정 사항을 확정된 사용자 정책과 혼동하지 않는다. 승격 방식, 기존 한도 정합성, 원본-only 자료의 표시 계약은 [Phase 0](phases/phase-0-contracts.md)에서 필요한 근거를 확인하고 사용자 영향이 있으면 구현 전에 논의한다.

## 완료 기준

합의 정책·저장 경계·공용 자원 제한 충족, 오표시/늦은 실패/재저장 방지, 자동 경합 테스트 실행, 대표 실기기 스크롤·확대·변경 QA, 회귀와 문서 최신화. 속도 개선 수치는 실제 결과로 보고하며 모든 기기의 최적값·통계적 우월성을 주장하지 않는다. 세부 검증은 [QA](qa-checklist.md), 순서는 [계획](plan.md)을 따른다.
