# ① 정책의 이유·대안·재검토 조건

- 전체 warmup은 화면에 없는 수백 장도 읽고 캐시 퇴거를 유발하므로 viewport 수요로 바꾼다. visible-only는 데이터 사용이 작지만 스크롤 첫 표시가 늦어 주변 선로딩을 선택했다. 개수/화면 배수/지연은 성공·취소 바이트와 표시 지연을 보고 조정한다.
- message±60 대신 사진별 frame을 쓴다.30장 묶음의 일부만 보이는 상황에서 메시지 단위로는 수요를 제한할 수 없다. UI 렌더링과 같은 계산/실제 layout 정보를 사용한다.
- 화면 밖 cap24는 보이는 이미지를 누락시키지 않는다.300ms 유예는 왕복 스크롤 재다운로드를 줄이는 선택이며 이탈 시 즉시 취소와 구분한다.
- 사용자는 네트워크 복구·앱 복귀 자체보다 방 재진입과 실제 화면 밖→안의 재시도를 선택했다. 실패 회차와 요청 유예를 나눠야 셀 재생성에 따른 반복 요청을 막고 빠른 재등장은 허용할 수 있다. 오류 종류를 이유로 새 표시에서도 영구 차단하는 아바타 정책은 복제하지 않는다.
- 목록에서 원본 fallback을 끊으면 썸네일만 손상된 자료가 자리표시자로 남을 수 있지만, 숨은 대용량 원본 다운로드·영상 디코딩 실패를 막는다. 사용자가 확대/재생할 때 원본을 요청한다. 실제 과거 자료의 썸네일 경로 누락은 자동 서버 보정/마이그레이션으로 확대하지 않는다.
- 취소는 해당 화면 소비자를 해제하는 의미다. 다른 화면이 같은 파일을 사용 중이면 공용 다운로드는 유지한다. 캐시 삭제와는 별개이며 성공한 캐시 파일은 기존 용량 정책으로 유지한다.
- 새 메시지 이미지 준비를 admission 조건에서 제거한다. 텍스트/시간/첨부 자리와 저장은 먼저 진행하고 사진은 별도 상태로 채워진다. 업로드 원장/FIFO/로컬 미리보기 보존은 독립된 기존 책임을 따른다.
- 공용 protocol에 priority를 전달하고 화면별 조정자를 DI하는 것이 후보 구조다. 범용 미디어 framework나 아바타 전용 정책 재사용은 책임 혼합이 커 채택하지 않는다. 실제 구현에서 새로운 데이터/사용자 동작 결정이 필요한 경우에만 재논의한다.
