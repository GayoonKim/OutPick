# ③ 표시용 캐시·원본 분리 — 설계 초안

최신 2026-09-22: [취소·파일 수명·캐시 재사용 세부 계획](cache-reuse-implementation-plan.md) 작성 완료·구현 전. **확대 닫기 시 저장 준비/다운로드 소비자 취소·후속 안내 없음**, 영상은 전체 다운로드를 기다리지 않고 재생 시작으로 사용자 확정. 기존 저장 지속 추천은 채택하지 않는다. 크기·용량·표시 파일 정책은 실기기 QA로 결정하며 현재 초점은②로 복귀한다.

2026-09-21. 사용자 설계 요청에 따른 문서다. **앱 캐시 분리 우선·사진 원본 앞뒤1장 선로딩·GIF/영상은 열 때만·원본 파일 저장/실패 재시도는 사용자 확정**이다. 크기/메모리/마이그레이션의 세부 기술 계약은 초안이다. 구현 계획/Phase 확정·제품 코드 수정·기기/서버 조작은 하지 않는다.

## 문제 정의와 근거의 한계

### 2026-09-22 최신 사용자 확정 — 아래 이전 추천안보다 우선

- 현재 업로드 규격을 유지한 상태에서 실제 iPhone 사진의 큰 JPEG→1024px 디코딩 비용, 대량 요청 대기, 프레임 및 메모리 사용을 먼저 확인한다. 차이가 작으면 수신 시 다운샘플링을 유지하고 캐시 재사용 개선에 집중한다.
- 업로드 전 해상도 축소, 수신 파일의 조건부/일괄 재인코딩, 표시1024px 최종 규격은 아직 확정하지 않는다. Mac 합성 이미지 측정은 실기기 제품 결정의 대체 근거가 아니다.
- 전송 확정과 원격 수신 모두 화면 표시와 독립적인 비동기 디스크 저장을 설계 방향으로 한다. 완성된 저장 작업은 셀 이탈과 분리하고 진행 중 결과 재사용·제한된 쓰기·실패 관측을 포함한다. 앱 종료 후 완료를 보장하는 계약은 아니다.
- 표시 파일은 단일 사진의 큰 버블 화질을 만족하는 공통 기준을 우선 검토한다. 묶음 전용 디스크 파일을 별도로 추가하는 안은 기본안이 아니다. 작은 묶음의 메모리 버킷 적용 여부는 실기기 부담 확인 후 결정한다.

남은 결정: (1) 실기기 결과에 따른 디스크 원문 유지/큰 입력만 변환 선택, (2) 단일 표시 화질·메모리 기준과 작은 묶음 버킷 필요성, (3) 명시적 LRU 또는 NSCache 및 압박/백그라운드 정리 수명, (4) 원본 예산·유형별 배분·사용 중 파일 보호와 초과 처리, (5) 구캐시의 점진 재사용·합산 예산·정리 시점, (6) 영상 원격 재생/캐시 채우기/저장의 중복 방지 구조, (7) 저장 중 뷰어 닫기 시 작업 지속과 결과 안내. 계정 전환·삭제 무효화 연결 및 pending 저장 합류는 구현 전 기술 계약으로 점검한다. 기존 앱캐시/원본 분리·사진 현재±1·GIF영상 열 때만·원본 저장/실패 재시도·재등장 실패 재시도 합의는 유지한다.

### 2026-09-22 수신 다운샘플링 비용 예비 측정

사용자 요청: 업로드 규격 변경을 먼저 확정하지 말고 큰 JPEG를 수신 후 최대1024px로 디코딩하는 비용이 작은지 비교한다. 큰 파일 그대로 저장도 유효한 정책 후보로 유지한다.

- Mac arm64 Swift 최적화 빌드에서 앱과 같은 ImageIO URL thumbnail 옵션(Always/Transform/MaxPixel1024/CacheImmediately)을 사용했다. 합성 gradient/pattern/noise 4032×3024 JPEG 품질0.7과 그 파일을1024×768로 디코딩 후 JPEG0.7로 저장한 비교 파일이다. 실제 사진·원본에서 직접 생성한 작은 썸네일의 화질 비교가 아니다.
- 각 경로5회 준비 후60회 교차 순서 실행, 매회 source 생성부터 thumbnail decode 반환까지 측정. OS 파일 캐시가 데워진 반복 조회이며 네트워크·앱 scheduler·UI·쓰기·인코딩 시간은 제외했다. 순수 CPU만의 측정이라고 부르지 않는다.

| 합성 입력 | 큰 파일→1024 중앙값/p95 | 작은 파일→1024 중앙값/p95 | 파일 bytes 큰/작은 |
| --- | --- | --- | --- |
| gradient |18.93/19.29ms|1.97/2.19ms|369733/40523|
| pattern |50.72/52.78ms|4.50/5.23ms|8063380/428470|
| noise |88.85/92.65ms|4.57/4.96ms|11063741/347685|

이 환경에서는 추가 다운샘플링 경로의 차이가 관측됐다. 합성 고주파 입력은 일반 사진을 대표하지 않으며 iPhone 실제 시간·스크롤 지연으로 환산하지 않는다. 준비 후 메모리 hit에서는 양쪽 모두 이 작업이 없고, 메모리 miss 뒤 디스크 재조회에서는 반복될 수 있다. 디코딩 후 픽셀 크기는 같아 최종 UIImage 비용 차이보다 준비 시간 차이를 본 것이다. 실사진 iPhone 디코딩 시간·대량 요청 대기·프레임·최대 메모리를 확인하기 전 업로드 변경/표시 파일 재인코딩을 확정하지 않는다.

실행 스크립트 `/private/tmp/outpick-decode-comparison.swift`, 결과 `/private/tmp/outpick-decode-comparison/results.json`. 제품/테스트 코드 변경·기기 조작·Storage 요청 없이 예비 측정만 수행했다.

### 2026-09-22 재사용·저장 경로 분석 — 아래 초기 제안보다 우선

제품 코드·테스트·기기 캐시 변경 없이 현재 호출 경로를 대조했다. 이전 QA 원본 로그 `/private/tmp/outpick-download-separation-device.log` 및 집계 JSON은 현재 존재하지 않는다. 기존 결과 문서의 집계는 참고하되 개별 파일 저장/퇴거/재다운로드 원인을 재입증한 것으로 취급하지 않는다.

| 항목 | 내 전송 확정 시 로컬 보존 | 서버 다운로드 후 저장 |
| --- | --- | --- |
| 진입 | `ChatViewController.handleIncomingMessage`: pending 상태와 staged 로컬 첨부를 찾을 때 | `ChatAttachmentImageService.loadImage`의 memoryAndDisk |
| 준비 | `loadLocalImage` 최대1024px → JPEG0.7 → `storeImageData`에서 다시 decode | 받은 bytes/file → 최대1024px decode |
| 메모리 | 축소 UIImage | 축소 UIImage |
| 디스크 | 축소 JPEG | 다운로드한 파일 그대로 |
| 키 | 확정 첨부의 `thumbResourcePath`에 `imageCache|` prefix | 본문이 같은 `thumbResourcePath`를 사용하고 동일 prefix 적용 |
| 완료 | disk.write 호출 종료까지 대기하지만 오류/성공 반환 없음 | 독립 persistence Task에 저장을 넘긴 뒤 표시 결과 반환 |

현재 본문/로컬 확정 연결에서는 저장·조회 key 불일치를 발견하지 않았다. 이 결론은 모든 외부 URL 별칭이나 과거 스키마까지 증명한 것은 아니다. 화면 수요 이탈은 Entry UIImage/Task만 해제하고 공용 캐시를 지우지 않는다.

확인한 구조적 원인과 관측 한계:

1. `ChatMediaViewportController.start`는 캐시 조회 전에 loading을 내보낸다. 이탈 시 idle로 이미지가 제거된 셀은 memory hit여도 비동기 결과 전 placeholder/loading을 거친다. 실제 프레임에 보이는 시간은 계측 필요하며 네트워크 재다운로드와 구분한다.
2. 표시와 확대 원본은 같은120MiB NSCache 및350MiB/trim280MiB 디스크를 사용한다. 큰 서버 썸네일과 원본이 작은 로컬 보존 파일을 밀어낼 수 있다. 메모리 hit는 disk touch를 하지 않아 디스크 정리 순서는 마지막 화면 사용 순서와 다를 수 있다. 해당 QA 항목의 실제 퇴거는 미입증이다.
3. 디스크 hit도 read/decode 대기가 있다.16MiB를 넘는 파일은 files 입장과 I/O write 슬롯을 사용하는 임시 복사 후 decode 경로다. 따라서 로딩 표시만으로 저장 실패라고 판단할 수 없다.
4. disk.write는 취소·실패를 호출자에게 반환하지 않는다. 실제 쓰기 구간 실패 metrics는 있으나 gate 대기 취소/세대 거절은 같은 성공·실패 계약으로 관측되지 않는다. 메모리 성공과 디스크 성공을 분리해야 한다.
5. 원격 저장은 비동기다. 메모리가 퇴거되고 디스크 쓰기가 아직 끝나지 않은 조건에서, 새 조회는 pending persistence에 합류하지 않고 miss 후 다운로드를 시작할 수 있다. 코드상 가능한 경합이며 실기기 재현 사실로 단정하지 않는다.
6. 로컬 확정 보존은 pending/staged 첨부가 있어야 한다. 해당 조건이 없는 과거 메시지·재진입 복구는 서버 다운로드 경로가 담당한다. 작은 로컬 파일이 퇴거한 후 같은 키를 큰 서버 파일로 채울 수 있어 저장 비용이 달라진다.

표시 파일 정책은 아직 미확정이다. 서버 파일 그대로 저장하면 변환 비용은 없지만 위 저장 크기 차이가 남는다. 추천 후보는 기존 로컬 최대1024px를 출발점으로 원격 입력도 표시 상한을 넘을 때만 축소 저장하고, 이미 적합한 작은 파일은 재인코딩 없이 재사용하는 조건부 정책이다. 실제 인코딩 품질/파일 한도는 별도 결정과 QA 대상이다. 무조건 전체 재압축·기존 캐시 일괄 변환·업로드 변경은 확정하지 않는다. 메모리 즉시 조회, 저장 결과 계약, pending write 합류, 원본 예산 분리는 이 정책과 별도로 해결해야 한다.

사용자: 대량 미디어를 기다리면 표시되지만 화면 밖으로 스크롤했다 돌아오면 다시 로딩된다.②에서 직렬 다운로드는 분리했고 실제 동시6개 전송을 확인했다.

- 캐시가 전혀 동작하지 않는 것은 아니다. 실측에서 memory/disk hit가 모두 발생했다.
- 화면 조정자는 수요 영역을 벗어나300ms 뒤 UIImage를 해제한다. 셀 해제와 공용 캐시 삭제는 서로 다른 동작이다. 복귀 시 메모리 miss라도 디스크 hit면 다운로드 없이 읽기/디코딩이 필요하다.
- `ChatAttachmentImageService`는 표시를 최대1024px로 다운샘플링하지만 공용 pipeline의 저장 payload는 다운로드한 원래 bytes/file이다. 표시가 작다고 디스크 저장도 작아지는 것은 아니다.
- remote pipeline은 디코딩된 이미지의 NSCache(기본120MiB 비용 한도)와 ChatImageCache(350MiB 초과 시280MiB까지 정리)를 사용한다. NSCache는 모든 항목의 보존이나 정확한 LRU 순서를 보장하는 제품 계약으로 사용할 수 없다.
- `ChatViewController`의 확대 진입은 정적 이미지 원본을 가까운8개와 나머지로 나눠 선로딩한다. 원본 경로도 같은 remote pipeline/디스크 용량을 사용한다. 본문 썸네일과 경로는 달라도 저장 용량과 디코딩 정책이 섞여 있다.
- `SimpleImageViewerVC` 저장은 현재 표시 UIImage를 우선 사용하고 원본 실패 시 썸네일로도 내려갈 수 있다. 원본 조회도 같은1024px decoder를 사용하므로 이름만으로 원본 품질 저장을 보장하지 않는다.
- GIF 원본은 별도45MiB NSCache<Data> 경로이며 공용 이미지 요청 병합/파일 저장과 분리돼 있다. 영상은 `OPVideoDiskCache` 등 별도 경로를 확인해야 한다.
- 앞선 완료241건/추가53건은 파일 전송 hash 집계다. 본문 썸네일만의 집계가 아니며 확대 원본 요청이 섞일 수 있다. 캐시 정리5회와 개별 경로 퇴거의 대응은 아직 입증되지 않았다. 저장 실패·정리·미저장·원본 transient 요청 등을 추가 계측 없이 한 원인으로 단정하지 않는다.

## 확정 범위

사용자가 **앱 캐시 분리부터 진행**을 선택했다.

- 서버 썸네일 생성/재처리/기존 Storage 파일·DTO 변경 없음. 기존 큰 썸네일의 첫 다운로드 바이트량은 남는다.
- 앱 안에서 본문 표시용 파일과 원본 파일의 key/namespace/저장소/예산/용도를 분리한다.
-①의 실제 화면 수요·취소·재등장 재시도 및②의 network/files/I/O 분리를 보존한다.
- 캐시를 무제한 늘리거나 셀마다 계속 이미지를 붙잡아 재로딩을 숨기는 방식은 채택하지 않는다.
- 범위 밖: 서버 배포, 로그인/권한 UX 변경, 룩북/아바타 캐시 전체 재설계, 업로드 재설계. 새 처리 흐름은 기존 service/Repository/DI 책임을 따른다.

## 사용자 흐름과 표시 계약 제안

1. 같은 이미지가 표시 중이면 재설정·경로 확인만으로 빈 placeholder로 바꾸지 않는다.
2. 범위 이탈 시 화면 소비자는 해제한다. 공용 표시 캐시는 독립적으로 유지한다.
3. 재등장 시 표시용 메모리 hit를 먼저 적용한다. 메모리 miss면 작은 표시용 디스크 파일을 읽고 디코딩한다.
4. 디스크 miss면 진행 중인 동일 변환/저장 작업을 확인한다. 완성 직전의 작업을 무시하고 네트워크를 중복 시작하지 않는다.
5. 둘 다 없을 때만 서버 썸네일을 요청한다. 먼저 표시하고, 제한된 변환 작업으로 작은 파일을 저장한다. 인코딩/저장 완료를 첫 표시의 선행 조건으로 삼지 않는다.
6. 저장 실패는 이미 표시한 이미지를 지우지 않는다. 다음 수요에서 제한된 재시도를 허용하고 무한 저장 재시도 루프를 만들지 않는다.

완료 기준은 “모든 이미지가 영원히 재로딩되지 않음”이 아니다. 동일 key·동일 버전·캐시 수용 범위 안의 재등장에서 불필요한 다운로드가0이어야 한다. 메모리 압박/용량 초과 퇴거는 허용하되 원인을 관측 가능하게 한다.

## 데이터와 API 경계 제안

| 용도 | 저장 내용 | 소비자 | 금지할 혼용 |
| --- | --- | --- | --- |
| 본문 표시 캐시 | 방향 보정된 정적 축소 이미지 | 사진 묶음/GIF 정적 thumbnail/영상 poster/공유 카드 | 다운로드 원문·GIF 전체 Data·MP4·원본 저장 |
| 원본 파일 캐시 | 실제 원본 bytes/file | 열어 본 상세·GIF 재생·영상 재생·사진 보관함 저장 | 표시용 JPEG를 원본으로 취급 |
| 확대 표시 메모리 | 화면/줌에 필요한 디코딩 결과 | 활성 뷰어 | 원본 bytes 저장과 디코딩 UIImage 보유 수명을 동일시 |
| 전송 중 로컬 원본 | 기존 outbox 보호 파일 | 업로드/복구 | 일반 캐시 퇴거·구버전 정리 대상으로 취급 |

- 호출 의도를 명시한 API 후보: `loadPreview(resource, rendition, priority)`, `cachedPreview(...)`, `acquireOriginalFile(resource, purpose)`. 기존 path-only API를 한꺼번에 갈아엎지 않고 실제 본문/뷰어 호출 지도를 바탕으로 확정한다.
- 표시 cache key: 계정 scope + 정규화된 resource identity + 리소스 버전 + 표시 rendition/format schema. attachment.hash가 thumbnail 실제 버전인지 검증하기 전에는 임의로 thumbnail content hash라고 취급하지 않는다.
- 원본 key는 같은 identity/version을 사용하되 별도 namespace. path가 같아도 preview/original을 덮어쓰지 않는다. signed URL의 일시 query만으로 캐시가 분할되거나 인증이 섞이지 않게 기존 정규화 계약을 확인한다.
- 목적상 다른 rendition의 저장은 분리하되 같은 원천 다운로드를 합류시킬 수 있는 경계를 검토한다. 세부 크기마다 전체 다운로드가 반복되는 구조는 피한다.
- 서비스/저장소가 취소·요청 세대·파일 lease를 소유한다. View는 파일 위치나 인코딩을 알지 않는다. Coordinator는 확대/닫기/저장 흐름을 연결하고 Container가 서비스/예산을 주입한다.

## 표시용 크기·인코딩·메모리 제안

### 다음 설계 점검의 추천안 — 사용자 미확정

- 디스크에는 리소스별 기준 표시 파일 하나를 저장하고, 메모리에는 실제 버블의 pixel 요구에 맞춘 소수 크기 버킷을 사용한다. 디스크 key에는 표시 포맷/schema를 포함하되 셀 너비나 회전별 버킷은 넣지 않는다. 메모리 key에는 버킷을 포함한다. 기존 rendition별 디스크 분리 후보보다 중복 저장과 크기 변경 시 재다운로드를 줄이는 안이다.
- 기준 표시 파일의 긴 변은 현재 decoder 상한인1024px를 초기 후보로 한다. 작은 입력은 확대하지 않고 종횡비·방향을 보존한다. 확대 화면은 이 파일의 상한을 높이는 대신 별도 원본 파일을 사용한다. 크기 수치는 QA에서 조절하되 schema 변경과 기존 파일 재사용을 구분한다.
- 불투명 사진은 JPEG, 투명 이미지에는 PNG를 우선 검토한다. JPEG 품질과 저장 한도는 fixture/실기기 QA로 조정한다. 무조건 원문보다 작다고 보장하지 않는다. 픽셀·파일 한도를 넘거나 인코딩에 실패하면 표시 성공은 유지하고 저장 실패 사유를 기록한다. 실패 항목을 반복 재인코딩하는 루프는 제한한다.
- 첫 표시를 디스크 인코딩 완료까지 막지 않는다. 기준 이미지 디코딩·버킷 변환·인코딩은 제한된 작업 수와 메모리 예산 안에서 수행한다. 동시에 보유하는 원문/기준 이미지/버킷 이미지/출력 Data 비용도 계산해야 한다.
- 표시 메모리는 decoded byte 비용 기준의 명시적 LRU를 추천한다. 셀 수요 해제와 캐시 퇴거를 분리하고, 같은 리소스의 불필요한 여러 버킷 보유를 제한한다. LRU 한도는 캐시 소유분의 한도이며 화면이 참조하는 이미지까지 포함한 앱 RSS의 절대 상한은 아니다.
- 기존 파일은 요청된 썸네일 경로에 한해 읽고 새 표시 파일로 변환한다. 새 파일 저장 성공 전에는 이전 파일을 먼저 지우지 않는다. 구/신 표시 저장소 합산 예산으로 점진 정리하며 outbox는 제외한다. 기존 혼합 캐시 파일을 검증 없이 실제 원본으로 승격하지 않는다.
- 계정 범위와 삭제 세대를 작업 시작부터 저장 완료까지 유지한다. 일반 로그아웃/계정 전환 연결부는 추가 확인 후 확정하며, 계정 삭제의 현재 `removeAllRegisteredCaches`/고정 폴더 삭제 목록에는 새 저장소도 연결해야 한다.

사용자 판단 항목은 기준 표시 품질 유지와 축소 파일 재인코딩 허용이다. 위 내용은 추천안이며 구현 승인이나 최종 확정으로 취급하지 않는다.

- 정적 표시 파일은 현재1024px 상한을 출발점으로 검토한다. 작은3열 타일과 단일 큰 사진의 실제 pixel 요구가 다르므로 표시 크기에 맞춘 소수의 버킷을 검토하되 픽셀/용량 수치는 QA로 정한다. 회전 때마다 다른 key를 만드는 연속 크기 방식은 피한다.
- JPEG/투명도 보존 포맷 선택은 fixture로 검증한다. 모든 이미지를 JPEG로 강제해 투명 배경/텍스트/색을 손상시키지 않는다. GIF 본문 캐시는 정적이며 애니메이션 원본을 대체하지 않는다.
- display memory는 decoded pixel 비용으로 관리한다. 모든 이미지에1024px를 일괄 적용하면 작은 타일도 메모리를 크게 차지하므로 파일 용량만 줄이고 메모리를 방치하지 않는다.
- 최근 재등장 이미지 재사용을 안정화하려면 byte 한도가 있는 명시적 LRU가 필요한지 NSCache와 비교한다. 활성 화면의 UIImage 참조와 캐시가 같은 객체를 참조하는 것은 이중 디코딩과 구분해 측정한다.
- 메모리 경고/백그라운드/계정 종료에서는 해제 정책을 명시하고, 복귀는 디스크 캐시로 복구한다. 화면 밖 원본 디코딩 이미지를 warm cache에 쌓지 않는다.
- 공용 `promotionEncoding`은 현재 메모리 hit의 디스크 승격이며, 정상 download payload의 큰 원문 저장을 자동 대체하지 않는다. 단순히 옵션을 켜는 것으로③가 해결된다고 보지 않는다. preview 전용 persistence 변환 계약을 설계해야 한다.

## 원본·저장 정책 — 사용자 확정

사용자가 주변 원본 선로딩 일부 유지를 선택한 뒤 아래 범위와 저장 정책을 확정했다. 실제 방문만 다운로드하는 최초 추천안은 채택하지 않는다.

- 현재 사진을 최우선으로 받고 앞뒤 각1장의 정적 사진 원본을 낮은 우선순위로 선로딩한다. 현재의 가까운8개+나머지 전체 로딩은 제한된 범위로 교체한다. 페이지가 바뀌면 멀어진 소비자만 취소하며 다른 화면/저장 소비자가 있으면 전송을 유지한다.
- GIF·영상은 실제로 열 때만 원본을 받고 자동 주변 원본 선로딩에서 제외한다. 주변 페이지가 GIF이면 그것을 건너뛰어 더 먼 원본까지 선로딩할지 등의 경계는 요청 범위를 넓히지 않는 방향으로 구체화한다.
- 파일은 재열기/저장에 재사용하되 디코딩 이미지·GIF frame·영상 player는 활성 화면 중심으로 해제한다. 큰 GIF/영상 원본 전체를 무제한 Data로 읽지 않는다.
- 저장 버튼은 해당 원본 파일을 저장하고 GIF는 animation을 보존한다. 원본 실패 시 축소 화면 이미지로 대체하지 않고 실패/재시도를 제공한다.
- 원본 총예산·사진/GIF/영상 간 분할 여부·TTL/LRU·사용 중 pin 정책은 구체 API/현 영상 캐시를 검토한 뒤 확정한다. 재다운로드 가능한 cache와 업로드에 필요한 보호 파일은 분리한다.

## 구버전 캐시와 무효화 제안

- 새 preview namespace/schema를 사용한다. 기존 ChatImageCache 파일은 작은 새 표시 파일로 오인하지 않는다.
- 기존 다운로드 파일이 있으면 필요해진 항목에 한해 로컬 변환해 재사용하는 migration을 검토한다. 전체 방 파일을 한 번에 변환하거나 서버에서 다시 받는 migration은 피한다.
- 기존 cache를 영구 중복 유지하지 않도록 새/구 버전 합계 디스크 예산과 단계적 정리 시점을 정해야 한다. 기존 원본/thumbnail 구분은 attachment metadata를 대조하며 filename만 보고 추측하지 않는다.
- 삭제/경로 교체/계정 전환의 revision을 변환·쓰기까지 전달한다. 늦은 변환 결과가 삭제 후 새 cache를 부활시키지 않게 한다.
- outbox/사용자 선택 원본/전송 복구 파일과 공유 캐시의 소유권 경계를 보존한다. 실제 기기의 캐시 삭제나 마이그레이션은 현재 설계 턴에서 하지 않는다.

## 관측·검증 설계

역할별로 preview/original/localPending을 구분하고 다음 결과를 key hash·세대·크기·사유로 기록한다. 원문 URL/토큰/사진 내용은 로그 금지다.

- memory hit/miss/eviction, disk hit/miss/corrupt, transform pending/hit/failure, write success/failure, eviction reason/bytes, download start/completion/cancel.
- “저장 성공→동일 경로 재등장”을 같은 key/version으로 연결해 miss의 원인을 설명할 수 있어야 한다. 저장 대기·미완료 취소를 저장 실패로 집계하지 않는다.
- 제어 가능한 fake 전송/encoder/store로 원문보다 작은 저장 파일, 동일 범위 왕복 다운로드0, 메모리 제거 뒤 디스크 재사용, 저장 대기 중 재등장 합류, 저장 실패 재시도, 늦은 결과/계정 무효화, capacity 초과만의 퇴거를 검증한다.
- 원본 API가 preview를 반환하지 않음, 원본 저장/GIF animation 보존, 한 소비자 취소 시 공유 파일 유지, 뷰어 종료 후 decoder/player 해제를 검증한다.
- 실기기 QA는 같은 기존 미디어 방의 왕복과 확대 전후를 비교한다. 첫 로딩/재등장 로딩/원본 요청을 분리하고 decode time·프레임 끊김·RSS·저장 바이트를 함께 본다. 전체 캐시 삭제나 추가 원격 다운로드는 사용자 범위를 확인한 뒤 실행한다.

## 설계 완료 전에 남은 항목

추가 확인: `DefaultChatVideoPlaybackResolver.playbackAsset`은 캐시 miss 시 원격 URL을 반환하면서 `Task.detached`로 `OPVideoDiskCache.cache`를 별도 시작한다. 저장 시 캐시가 아직 없으면 `fileDownloader`로 추가 다운로드할 수 있다. 따라서 재생·캐시 채우기·저장의 전송 경로가 분리돼 있다. 실제 중복 전송 바이트량은 아직 측정하지 않았다. 재생 시작 지연을 유지하면서 파일 재사용/취소를 연결할지, 완전 파일 수신 후 재생할지의 선택은 다음 원본 수명 설계에서 다룬다. 이번 표시 캐시 점검에서 임의로 완전 다운로드 후 재생으로 바꾸지 않는다.

1. 확정한 사진 앞뒤1장/GIF·영상 열 때만/원본 파일 저장 정책을 뷰어 수명·저장 Task·파일 lease 계약으로 구체화.
2. 영상/계정 무효화 호출 지도와 원본/표시 API의 구체 책임 확정. `OPVideoDiskCache`는512MiB로 제한하지만 전체 Data 다운로드·재사용 시 recency 미갱신·사용 중 파일 보호 부재가 보인다. 실제 재생 진입과 연결을 추가 대조해야 한다. `PhotoLibrarySaving`은 현재 saveImage(UIImage)/saveVideo(URL)만 있어 원본 사진·GIF 파일 저장 계약을 별도로 설계해야 한다. `ChatDeletionSyncUseCase`의 이미지 remove 호출은 새 namespace/원본까지 연결될 필요가 있다.
3. 표시 rendition·인코딩·메모리 보존·구버전 migration 방식 결정. 수치 최적화는 이후 QA, 형식/품질/수명 계약은 구현 전에 결정.
4. 선택된 정책을 확정 문서에 반영한 뒤 사용자가 요청하면 세부 구현 계획을 작성한다. 현재는 Phase/task 계획이나 구현 완료로 표시하지 않는다.
