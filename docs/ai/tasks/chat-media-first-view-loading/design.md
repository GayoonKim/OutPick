# 채팅 미디어 ① 화면 주변 로딩 설계

상태: 2026-09-21 사용자 정책 합의·구현 승인 후 ① 로컬 코드 구현. 자동 테스트 실행/실기기 QA 미실시. 실제 검증 결과는 progress 참조. ②·③은 순서만 합의했으며 상세 정책을 확정하지 않았다.

## 요구사항과 가치

채팅 진입·스크롤·새 메시지 수신 시 실제 화면에 필요한 이미지를 먼저 표시한다. 초기 메시지 전체의 이미지 다운로드가 표시·저장을 막지 않게 하고, 화면 밖 작업과 취소된 응답이 현재 표시를 방해하지 않게 한다. 사진·GIF 정적 썸네일·영상 썸네일·룩북 공유 카드를 동일한 화면 수요로 관리한다.

사진의 원해상도 업로드·300,000,000바이트 허용 정책은 유지한다. 서버 저장 경로, Firestore/Socket DTO, GRDB 스키마, 전송 FIFO, 캐시 용량·파일 형식의 변경은 이 단계의 목표가 아니다. 확대·재생 화면은 자신의 원본 요청을 소유하며 상세 원본 저장/품질 문제는 ③에서 다룬다.

## 확정 사용자 동작

| 상황 | 동작 |
| --- | --- |
| 채팅 첫 진입 | 메시지 데이터를 표시하고 실제 배치 후 개별 이미지 좌표로 수요 계산. 초기 메시지 전체 warmup 제거 |
| 현재 보이는 이미지 | 수량 상한 없이 우선 요청. 화면 밖 선로딩과 같은 경로면 기존 요청에 합류/우선순위 승격 |
| 주변 선로딩 | 스크롤 방향 1.5화면, 반대 0.5화면, 화면 밖 고유 요청 최대24개. 현재 보이는 요청은 이24개에 포함하지 않음 |
| 화면 주변 범위 이탈 | 300ms 뒤 해당 화면의 소비자를 해제. 유예 중 복귀하면 기존 작업 유지 |
| 실제 표시 영역 밖→안 | 실패한 이미지는 표시 회차당 한 번 재시도. 주변 선로딩 영역에 계속 남아 있어도 적용 |
| 선로딩 실패→첫 표시 | 실제 표시 시 한 번 재시도 |
| 표시 중 실패 | 자리표시자 유지. 셀 재구성·작은 스크롤·네트워크 복구만으로 자동 반복하지 않음 |
| 방 재진입 | 해당 방의 새 표시 세션으로 실패 재시도 허용 |
| 화면 완전 가림/백그라운드 | 채팅 본문 소비자 즉시 해제. 복귀 시 현재 위치의 수요 복원 |
| 취소 후 다시 필요 | 취소는 실패가 아니므로 정상 요청. 이전 응답은 세대 검사로 차단 |
| 썸네일 오류 | 원본 사진·GIF Data·영상 MP4·원격 포스터 생성으로 자동 대체하지 않음 |
| 사용자 확대/재생 | 기존 Coordinator 경유 해당 화면에서 원본 요청 |
| 새 메시지 | 전체 첨부 다운로드를 기다리지 않고 표시·기존 저장 경로에 전달. 실제 필요한 첨부만 요청 |
| 로컬 전송→서버 확정 | 같은 첨부의 이미 표시된 사진 유지. 이후 조회에는 최신 경로 적용 |

수치는 QA 시작값이다. cap은 다운로드 동시 실행 수가 아닌 화면 밖 희망 요청 수다. 300ms 해제 유예의 기존 소비자가 잠시 함께 존재할 수 있으며, 공용 실행 슬롯 상한과 따로 계측한다.

## 실제 표시와 요청 수명

- 실제 표시: 이미지 영역이 채팅 collection의 유효 표시 영역과 교차하는지 계산한다. 단순한 내부 collection의 visibleCells 여부로 판정하지 않는다.
- 메시지30장 묶음은 첨부별 사각형으로 나눈다. 인스턴스가 없는 주변 메시지는 기존 동일 레이아웃 계산으로 좌표를 얻고 배치 후 실제 좌표로 갱신한다. 모든 셀을 만들거나 렌더링해서 선로딩 후보를 구하지 않는다.
- 공유 카드는 카드 이미지 영역을 사용한다. 텍스트 메시지·삭제 메시지·빈 썸네일 경로는 요청을 만들지 않는다.
- 최초 배치, 스크롤, 페이지 prepend, 데이터/경로 변경, 회전·키보드에 따른 배치 변경, 화면 복귀에서 갱신한다. 좌표가 확정되기 전에는 전체 목록 선로딩으로 대체하지 않는다.
- 화면이 부분적으로 보이는 상태는 화면 전체 이탈과 구분한다. UIKit 표시 수명과 기존 Coordinator 전환을 따르며 임의 시간 폴링을 추가하지 않는다.
- 가림/백그라운드로 일시 정지할 때 실패 표시 회차를 무조건 새로 만들지 않는다. 같은 사진의 단순 앱 복귀는 새 실패 재시도 계기가 아니다. 재배치 결과 실제 표시 밖→안, 방 재진입, 콘텐츠 경로 변경은 별도로 판정한다.
- 취소 유예 타이머와 true visibility 회차는 독립적이다. 실패한 사진이 실제 화면 밖에 나갔다300ms 안에 복귀해도 새 표시 회차다. 실행 중인 같은 요청은 중복 생성하지 않는다.

## 상태와 식별

표시 항목은 기존 messageID+종류+attachment index를 유지한다. 공유 카드는 messageID+카드 이미지 식별을 쓴다. 인덱스 위치나 셀 주소를 identity로 쓰지 않는다. 요청은 정규화된 thumbnail resource path와 다운로드 계약으로 구분한다.

방 화면 단위 조정자가 항목별 `실제 표시 여부/표시 회차/마지막 실패 회차/최신 경로`와 경로별 `실행 요청/소비자/우선순위/취소 유예/요청 세대`를 보유한다. 실패 정보는 셀 재사용만으로 사라지지 않는다. 방 세션 종료 시 정리한다. 삭제된 항목은 즉시 해제한다.

| 상태 전이 | 처리 |
| --- | --- |
| 미요청→visible/prefetch | 소비자 등록·캐시 조회 후 필요 시 다운로드 |
| prefetch→visible | 합류/승격. 진행 중 다운로드 재시작 없음 |
| running→success | 최신 항목·경로·요청 세대·세션이 일치할 때만 적용 |
| running→failure | 실패한 표시 회차 기록. 자동 재요청 루프 없음 |
| failed→새 visible 회차 | 해당 회차 한 번 요청. 같은 경로의 진행 요청에는 합류 |
| running→cancelled | 실패 회차를 만들지 않고 소비자 해제 |
| 로컬→서버 경로 변경 | 기존 사진 유지, 다음 조회는 최신 경로. 과거 요청 응답이 최신 경로를 덮지 않음 |

오류 종류별로 이 재등장 계약을 예외 처리하지 않는다. 파일 없음·접근 거부도 같은 회차에서는 반복하지 않고 새 표시/방 진입 계기에서 재확인한다. 새 수동 재시도 버튼은 추가하지 않는다.

## 책임·기술·API 설계

기존 UIKit + MVVM-C/UseCase/Repository/DI와 ImageCachePipeline을 유지한다. 새 SDK·서버 서비스·DB는 필요하지 않다. 아래 새 이름은 구현 후보이며 기존 파일인 것처럼 취급하지 않는다.

- `ChatMediaViewportPolicy`: 개별 이미지 frame·방향·visible/주변 수요를 고르는 순수 로직. 기존 아바타의 viewport 원리를 참고하되 Avatar 전용 캐시 정책/실패 상태를 재사용하지 않는다.
- `ChatMediaViewportController`: 방 화면의 위 상태와 요청 핸들 소유. 셀에는 표시 상태를 전달한다. 화면 밖 셀 configure가 독자적으로 요청을 시작하지 않게 한다. 추가 장기 이미지 캐시를 만들지 않는다.
- `ChatMediaPreviewLayout`: 기존 묶음 행 수·크기 계산을 공유할 필요가 있을 때만 분리. 실제 렌더링과 viewport 계산이 두 벌의 공식을 갖지 않게 한다.
- View/Cell: 표시와 사용자 이벤트·좌표 제공. `ChatImagePreviewCollectionView`, `ChatImagePreviewCell`, `LookbookShareMessageContentView`의 자체 Task를 새 수명 관리와 중복시키지 않는다. 같은 첨부의 표시 연속성과 재사용 reset 유지.
- `ChatAttachmentImageLoading/Service`: 명시적 visible/prefetch 우선순위를 받는 썸네일 조회 계약을 제공한다. 기존 일반 API 소비자의 동작은 보존한다. UIKit 셀에서 Firebase/Repository 생성 금지.
- `ImageCachePipeline/Coordinator`: 기존 경로별 요청 합류·소비자별 취소 사용. 서비스의 prefetch가 내부에서 다시 visible 기본값으로 바뀌지 않게 한다. 마지막 소비자만 실제 다운로드를 취소한다.
- 초기 조회 UseCase: 이미지 warmMedia 이벤트를 제거하고 데이터 조회·표시/세션 이벤트만 유지한다. 사용되지 않는 mediaPrefetchConcurrency 값과 fake도 함께 정리한다. 기존 메시지 조회 개수/읽음/페이지 정책 변경 없음.
- `ChatViewController`: 초기/스크롤/수신 일괄 warmup을 viewport 갱신으로 교체한다. 큰 VC에 새 상태 기계를 추가하지 않고 조정자로 위임한다.
- Container는 기존 첨부 로더를 사용한 화면별 조정자 factory를 제공하고 Coordinator가 VC에 주입한다. 기존 공유 pipeline을 방마다 새로 생성하지 않는다. Coordinator는 가림·복귀·확대/재생 전환을 담당한다.
- 초기 이미지 준비와 수신 처리의 `await cacheImagesIfNeeded`를 제거하되 기존 message save queue·outbox 확인/정리는 유지한다. 전송 성공 미리보기 보존을 임의 삭제하거나 업로드 취소 정책을 바꾸지 않는다.

서버/API/데이터 계약 변화는 없다. 추가 상태는 앱 메모리의 화면 세션에만 존재한다. Storage 인증·권한과 이미지 내용은 현재 경로를 사용하므로 새 권한·수집·정책 기능은 없다.

## 완료 기준과 후속 경계

① 완료는 모든 채팅 미디어 표시 요청이 화면 수요로 설명되고, 재등장 재시도·공유 소비자 취소·표시 연속성·새 메시지 선표시가 검증되는 것이다. ①만으로 cold 다운로드 직렬화나395MiB 썸네일 전체 보관 문제가 해결됐다고 보고하지 않는다.

②는 공용 network/I/O budget 경계이므로 룩북·아바타·캐시 persistence 영향 조사 후 별도 설계한다. ③은 표시용 축소 저장·원본/GIF/영상 저장·원본 품질·확대/저장 수명 계약을 별도 합의한다. 세 단계는 동일 service/VC/pipeline 경계를 공유하므로 순차 진행한다.
