## 사용자 확정 사항

- 순서: 세부 설계 → 세부 구현 계획 → 구현 승인 → 구현·필수 검증·실험 → 결과 분석 → 최종안 반영. 운영 배포는 별도 승인이다.
- 비교 대상은 현재 방식, 시즌 내부 묶음, 빈자리 보충과 단계 분리, 브랜드별 시즌 순차와 각 방식의 조합, 대상 전체 시작이다.
- 우선 관심 대상은 여러 시즌을 각각 시작하되 각 시즌의 이미지를 묶음으로 나눠 순차 시작하고 묶음 내부를 병렬 처리하는 방식이다.
- 로컬의 동일 자료 비교 후 Development에서 실제 URL·Storage·Firestore 연동과 성능을 확인한다.
- 다운로드 재사용은 구조·동시성 비교와 별도 항목으로 포함한다. 같은 Worker 실행에서 자동 등록까지 이어질 때만 재사용하며 관리자 검토 대기·재시작을 넘기는 영구 캐시는 제외한다.
- UNAFFECTED 실제 추출/검토 대기와 승인 후 저장은 분리 측정한다. 동일 실행 재사용은 별도 로컬 연결 실험으로 분리하며 품질 검토를 우회하지 않는다. 2026-10-03 사용자 확정이다.
- 브랜드별 순차 후보는 관리자 검토 대기 또는 최종 실패 시 다음 시즌을 진행한다. 시즌 job 자동 실행은 최초 시도 포함 총 5회(추가 시도 최대 4회)로 사용자 확정했다. 추가 5분 한도는 두지 않는다. 개별 요청 timeout·lease·플랫폼 실행 한도와 다운로드 내부 재시도는 별개이며 제거하지 않는다.
- 정확성 유지·실패율 악화 없음이 전제다. 전체 완료 시간 중앙값 10% 이상 단축을 우선하고, 차이가 작으면 단순성·비용을 비교한다.
- 기존 QA URL로 대상 후보를 만들고, 실행 전에 예상 요청량과 실험 규모를 제시한다.
- 재사용은 읽기 전용 메모리 Buffer, 인스턴스 공용 보관 256MiB부터 시작해 128/512MiB/전체 보관과 비교한다. 예산 초과분은 대기하지 않고 필요 시 재다운로드한다.
- 첫 실험 규모는 로컬 구조 비교 54회, Development 기준선과 유력 후보 최대 2개 × 3부하 × 각 5회 = 최대 45회다. Development 최대 2시간·동시 인스턴스 최대 3개, 작업별 누적 추정 미화 10달러에서 중단하는 조건을 사용자 확정했다. 청구 지연으로 정확한 결제 상한을 보장하지 않으며 배포/실험 실행 승인은 이후 구현 계획을 따른다.
- 보조 기준도 사용자 확정이다. 컨테이너 전체 메모리 85% 이상이 1초 이상 관측되면 해당 실험을 중단한다. 첫 시즌 또는 특정 부하의 완료 시간이 기준선보다 10% 이상 반복 악화되면 자동 채택을 보류한다. 최적 동시성을 실측한 값이 아니라 실험 중단·결과 검토 기준이다.

## 현재 상태와 근거

2026-10-03 이 대화에서 조회한 운영·개발 import 큐는 동시 6개, dispatch 초당 3개다. Worker 요청 동시성은 인스턴스당 2개, asset 환경값은 3이다. 당시 실제 트래픽 리비전은 운영 `lookbook-import-worker-00026-qes`, 개발 `lookbook-import-worker-development-00012-fih`이며 각각 100%였다. 이 기록은 그 시점의 조회 결과이며 실행 전 다시 확인한다.

현재 코드에서는 후보 다운로드와 SHA-256 확인을 시즌당 4개씩 수행하고, asset 처리는 다운로드 → 두 JPEG 변환 → 두 업로드 → 경로 저장 전체를 시즌당 3개 슬롯으로 묶는다. 두 변환·두 업로드는 출력 파일 개수이며 별도 동시성 설정값이 아니다. 후보 해시 단계의 바이트는 asset 단계에서 재사용하지 않는다.

- [기존 운영값 결정](../tasks/lookbook-import-worker/decisions/phase-10.md): 보수적 첫 운영값이며 추후 상향 검토.
- [기존 실행 기록](../tasks/lookbook-import-worker/progress/phase-10.md): 성공·오류 관찰은 있지만 단계별 자원과 수치의 체계적 비교 근거는 부족.
- [채팅 동시성 비교](../qa-media-upload-concurrency-2026-09-12.md): 준비 전체와 제한 PUT의 결과가 달랐다. 측정 방법을 참고하며 iPhone 결과를 서버 최적값으로 대입하지 않는다.
- `tools/lookbook-import-worker/src/processor.ts`: 실제 파이프라인, claim/lease, review, materialization, asset 저장.
- `tools/lookbook-import-worker/src/extraction/{image-candidates,dedupe,quality}.ts`: 후보·순서·해시·품질 계약.
- `functions/src/lookbook/import/functions.ts`: job 생성·중복 확인·Cloud Tasks enqueue·review 재개.

## 범위와 유지할 계약

외부 URL 후보 추출부터 asset 저장까지의 성능을 대상으로 한다. 새 화면·일반 사용자 API·이미지 품질 변경은 제안하지 않는다. 앱의 View·ViewModel·Coordinator·Container 구조는 유지한다. 서버 실험이 앱의 진행·검토·부분 실패·재시도 표시를 훼손하지 않는지 수동 확인한다.

전체 후보 해시 확인과 품질 판단 이전에 일부 포스트를 먼저 등록하는 변경은 포함하지 않는다. hash 실패 후보 보존, 예상 수량 검증, 승인된 review snapshot, 후보 표시 순서, deterministic ID, 두 파일 저장 후 ready 확정, 기존 부분 실패 재시도 계약을 유지한다. 성공 판정을 빠르게 만들기 위해 검증을 생략하지 않는다.

추출 정확성 fixture와 성능 자료는 분리한다. 기존 fixture의 축약 HTML·rendered HTML은 브라우저 실행이나 실제 다운로드 성능을 재현하지 않는다. 외부 서버에 대한 URL 보안 검사·인증 경계를 완화하지 않는다. 로컬 fake transport를 제품의 공개 URL 검증 우회 경로로 만들지 않는다.

## 작업 단위와 스케줄링 경계

시즌 job, 이미지 묶음, 이미지 한 장의 전체 처리, JPEG 출력 한 개, 업로드 파일 한 개를 구분한다. 묶음 크기와 실행 폭은 독립 설정이다. 묶음은 성공뿐 아니라 실패 기록과 진행 중인 관련 작업의 종료까지 기다린 뒤 다음 묶음을 연다.

시즌별 묶음은 해당 job이 소유한다. CPU·메모리를 공유하는 인스턴스 내부의 단계 자원 관리는 bootstrap에서 만든 공용 객체를 주입하는 안을 추천한다. job마다 독립 세마포어를 만들고 그 합을 인스턴스 상한이라고 부르지 않는다. 인스턴스 공용 제한도 서비스 전체 제한은 아니다. 다중 인스턴스의 전체 유입은 Cloud Tasks 등 바깥 계층에서 별도로 제어한다.

한 자원의 슬롯을 다른 자원 대기 중 점유하지 않도록 설계한다. 다운로드·변환 완료 데이터는 다음 단계에 소유권을 넘기고, 성공·실패·취소 후 해제한다. 작업 개수와 함께 대기 데이터의 바이트를 계측한다. 품질 판단 장벽 전에 업로드·변환을 시작하지 않는 조건과 재사용 보관 예산이 충돌할 경우, 예산 초과분은 재다운로드 가능한 miss로 처리하는 안을 검토한다. 예산 대기만으로 모든 해시 작업이 멈추는 교착을 허용하지 않는다.

브랜드별 시즌 순차 후보는 다중 인스턴스 공통 실행권이 필요하다. 단일 프로세스 Map만으로 운영 순서를 보장하지 않는다. 우선 비교 실행기에서 브랜드별 dispatch 순서를 재현하고, 유력 후보이면 실제 claim·lease·dispatch의 영속 상태와 장애 복구를 검증하는 접근을 추천한다. 실행기에서 보인 속도를 제품의 분산 순서 보장 완료로 보고하지 않는다.

영속 제어가 필요할 경우 기존 Firestore·Cloud Tasks 경계를 우선 사용한다. 필드·실행권 소유자·세대·만료·다음 작업 선택·재시도 후 순서·복구 주체는 구현 계획 전에 별도 확정해야 한다. 대기 중인 HTTP 요청이 Cloud Run 슬롯을 오래 점유하거나 정상 대기를 오류 응답으로 바꿔 Cloud Tasks 재시도를 소진하지 않도록 한다.

총 5회는 실제 시즌 job 자동 실행의 예산이다. 현재 Cloud Tasks `maxAttempts`/task retry count는 dispatch 단위이므로 이를 5로 바꾸는 것만으로 job 전체 예산을 보장하지 않는다. job의 시도 이력과 claim을 함께 검증하고 새 dispatch generation에서 같은 job의 예산이 조용히 초기화되지 않게 해야 한다. 중복 전달·stale dispatch·claim 거절·브랜드 차례 대기는 실제 실행 횟수로 세지 않는다. review 승인·수동 재시도·asset retry의 기존 실행 단위와 예산 연결은 구현 계획에서 명시적으로 대조하고 제품 동작을 바꾸는 선택은 논의한다. 비교 후보의 자동 재시도 조건은 동일하게 맞추고 기존 총 3회 정책 그대로의 기준선과 구분한다.

## 다운로드 재사용

비교는 현재 재다운로드 방식과 같은 실행 안의 바이트 재사용 방식으로 나눈다. 동일 입력에 대해 구조·동시성 설정은 고정한다. 비교 결과에는 제거된 외부 요청·바이트, 재사용 hit/miss, 보관 비용·최대량을 함께 남긴다.

재사용 식별에는 job 실행 세대, canonical URL, source page/Referer와 필요한 요청 맥락을 반영한다. 파일명이 같다는 이유로 서로 다른 실행이나 출처의 데이터를 공유하지 않는다. 해시 계산에 사용한 바이트와 변환에 전달한 바이트의 일치를 확인한다. HTTP 오류·불완전 응답은 재사용 대상으로 게시하지 않는다.

완료·실패·검토 대기·취소·실행 종료에 보관 자료를 정리한다. 프로세스 재시작과 review 승인 후 새 요청은 cache miss로 처리한다. 외부 원본이 두 다운로드 사이에 바뀌는 경우 기존 방식과 재사용 방식의 결과가 달라질 수 있으므로, 고정 자료의 성능 비교와 원본 변경 시나리오를 분리한다.

사용자는 메모리 Buffer 재사용과 공용 256MiB부터 예산별 비교를 선택했다. 임시 파일 방식은 이번 초기 비교에 포함하지 않는다. 실제 RSS·보관량·정리 비용을 함께 측정한다. Cloud Run의 임시 파일 시스템도 메모리를 소비하므로 추후 파일 방식으로 바꿨다고 메모리 비용이 사라지는 것은 아니다. [Cloud Run 공식 계약](https://docs.cloud.google.com/run/docs/container-contract#file_system_access).

- YOUTH: `https://youth-lab.kr/page/collection_detail.html?product_no=6052&cate_no=25&display_group=1`

각 후보의 후보 수·파일 바이트·해상도·포맷·정적/렌더링 분기·품질 결과를 사전 점검하고 실험 manifest를 고정한다. 최신 페이지가 달라졌으면 과거 fixture 기대값을 실제 URL의 정답으로 쓰지 않는다. 실제 URL의 저장 자료·임시 이미지·원본 로그는 테스트용 위치에서 관리하며 기존 축약 fixture에 전체 페이지나 원본을 추가하지 않는다.

로컬 자료는 동일 바이트와 응답 지연을 반복 재현한다. 자료 식별값·컨텐츠 해시·이미지 수·용량 분포·실행 설정을 결과에 연결한다. fake 지연만으로 클라우드 성능을 입증하지 않으며 실제 sharp 변환을 사용하는 측정과 별도로 구분한다.

초기 구조 비교 규모 제안은 6구조 × 3부하 형태 × 3반복 = 54개 측정 실행이다. 부하 형태는 한 브랜드 한 시즌, 한 브랜드 여섯 시즌, 세 브랜드 각 두 시즌이다. 이미지 자료는 같은 분포를 사용한다. 준비 실행·오류 주입 테스트·수치 조정·Development 반복은 이 54개에 포함하지 않는다. 시즌당 이미지 수와 바이트량을 정한 뒤 총 요청량을 산출하며 현재는 전체 실험 비용 상한으로 취급하지 않는다.

동시성 후보는 묶음 8/16/32/all, 다운로드·해시 4/8/16/all, 변환 1/2/4/8/all, 파일 업로드 4/8/16/all, job 생성 10/20/all, 경로 저장 제한/all이다. 아직 사용자 확정값이 아니다. 모든 조합의 전수 곱을 실행하지 않고, 포화·대기·실패 지표를 보고 한 축씩 비교한 뒤 유력 조합을 결합한다. Cloud Run 요청·큐·인스턴스 설정 조정은 내부 비교와 분리한다.

다운로드 요청량은 실제 해시 후보 수와 저장 대상 수를 기준으로 산출한다. 중복 제거·커버·retry·Playwright 부가 요청 때문에 이미지 수에 단순히 2를 곱한 값과 다를 수 있다. 업로드는 재시도 전 기준 저장 대상당 두 파일이며 Firestore 작업 수는 실제 수행 호출을 집계한다. 시뮬레이션과 실제 클라우드 비용을 혼동하지 않는다.

Development에서는 동일 리소스 조건의 기준선과 유력 후보를 비교한다. 로컬 운영체제·CPU·SDK 환경 차이가 있으므로 로컬 승자를 최종 승자로 확정하지 않는다. 전용 테스트 데이터와 실행 식별자를 사용하고 기존 개발 데이터를 덮어쓰지 않는 격리 방식을 제안한다. endpoint·queue·revision 격리와 수집 자료 정리 범위는 배포 전 계획에서 명시한다.

## 계측 계약 제안

- 식별: run ID, 소스 revision과 입력 digest, 정책/수치, workload ID, job/asset의 비식별 연결 키, attempt, cold/warm.
- 시간: 큐/슬롯 대기, HTML, 렌더링, 이미지 수신, 해시, 각 변환, 각 업로드, DB 확정, 첫 시즌 완료, 전체 완료, 실패 후 수렴.
- 동시성: 제출·대기·실행·완료·실패 수, 최대 in-flight, sharp queue/process, 이미지당 라이브러리 스레드 설정.
- 자원: 프로세스 CPU user/system, event-loop 지연, RSS/heap/external/arrayBuffers, 재사용·업로드 대기 바이트, 임시 파일량, Chromium 포함 컨테이너 메모리·CPU.
- 전송: 실제 수신·송신 바이트, 요청 수, 재시도 수, 측정 구간의 유효 처리 속도. 전체 회선 대역폭이나 NIC 점유율을 측정한 것으로 확대하지 않는다.
- 저장: 후보·중복·post·asset 성공/실패 수, 결과 순서, 두 파일과 Firestore 경로·ready 상태 일치.

동일 프로세스의 병렬 작업에서 CPU 차분을 각 작업 CPU로 단순 귀속하거나 합산하지 않는다. RSS 표본은 순간 최대값을 보장하지 않으며 Chromium 자식 프로세스·파일 시스템 메모리를 포함하는 Cloud Run 지표와 대조한다. Node·sharp·libvips·Playwright 버전과 내부 thread pool 설정을 기록한다. [sharp 성능 문서](https://sharp.pixelplumbing.com/performance/).

개별 시간은 단조 시계로, 서로 다른 프로세스의 연결에는 UTC와 실행 ID를 사용한다. 원본 URL query·토큰·쿠키·이미지 본문은 계측 로그에 넣지 않는다. 성공 실행만 남기는 선택 편향을 피하기 위해 실패·중단·환경 미준비도 결과로 보존한다.

## 판정 기준

필수 정확성 검사가 통과한 후보만 성능을 비교한다. 같은 자료·조건에서 실행 순서를 교차하고 cold/warm·외부 URL 변경·다른 작업 간섭을 기록한다. 초기 3회는 탐색용이며 유력 후보는 반복을 늘려 기준선과 대조하는 안을 제안한다. 작은 표본의 p95를 안정적인 꼬리 지연 근거로 사용하지 않는다.

확정한 우선 지표는 `(기준선 중앙값 - 후보 중앙값) / 기준선 중앙값 >= 0.10`이다. workload별 비율을 먼저 보고하고 총합·가중 평가 방식은 실행 전에 합의한다. 한 종류의 큰 개선으로 다른 종류의 반복 실패를 숨기지 않는다. 반복 간 변동이 개선폭과 비슷하면 추가 비교 또는 미확정으로 남긴다.

실패율은 시도·asset·job별 분모를 명시하고 retry 전후를 분리한다. 소수 실행에서 실패 0건인 사실을 실패 확률 0 또는 통계적 비열등성 증명으로 확대하지 않는다. 통제 자료의 예상 밖 실패·결과 불일치는 채택을 막고, 실제 외부 실패는 원인과 추가 표본 필요성을 분석한다.

첫 시즌 또는 특정 부하의 완료 시간이 10% 이상 반복 악화되면 자동 채택을 보류한다. 반복 악화는 동일 조건의 짝지은 5회 중 3회 이상 10% 악화하고 중앙값도 10% 악화하는 것으로 사용자 확정했다. 이는 실험 조기 중단 기준이 아니다. 컨테이너 전체 메모리 85% 이상이 1초 이상 관측되면 해당 실험을 중단한다. 시간·인스턴스·추정 비용 한도는 위 확정 사항을 따른다. 초과 실행은 실패 또는 중단이며 통과로 기록하지 않는다. 메모리 표본 누락을 정상으로 간주하지 않는다.

## 검증과 완료 조건

자동 검증은 순서·중복 제거·품질 snapshot 보존, 묶음 경계와 개수 제한, 인스턴스 공유 제한, 일부 실패 후 다른 in-flight 종료 대기, permit 누수·교착, 두 업로드 성공 전 ready 금지, 부분 실패 재시도, stale generation/lease, review 재개, 재사용 소유권·정리를 대상으로 한다. fake transport/storage/repository와 제어 가능한 종료 신호를 사용한다. 단순 코드 문자열 검사로 동시성 동작 검증을 대신하지 않는다.

브랜드별 순차가 유력하면 다중 인스턴스 claim·lease 만료·중복 전달·재시도·검토 대기 후 다음 job의 실제 동작을 추가 검증한다. 빠른 실험용 단일 실행기만 검증하고 분산 동작까지 통과했다고 기록하지 않는다.

`tools/verification-gate/`를 재사용해 `verification/lookbook-import.json`으로 기존 Worker 테스트와 reporter/필수 ID를 연결했다. 새 동시성·계측·캐시·재시도·성능 판정의 필수 테스트 ID는 구현과 함께 추가해야 한다. 누락·skip·0개·환경 미준비·시간 초과는 차단으로 처리한다. 성능 결과 schema와 입력/설정 일치도 프로그램으로 검사하고, 사람이 판단할 체감·품질·tradeoff는 별도 기록한다.

앱 수동 QA는 기존 관리자 화면의 진행·검토 대기·부분 실패·재시도와 결과 순서·표시를 확인한다. 설계 변경 없이 iOS 코드 수정을 전제로 하지 않는다. 검증 결과는 검사 당시 코드 digest와 원본 로그에 연결한다.

세부 설계 완료 조건은 비교·입력·자원·실패/재시도·보관·실험 한도·합격 기준이 합의되고 미확정 기술 경계가 해소되는 것이다. 구현 완료는 비교 실행기·계측·필수 게이트를 갖췄다는 뜻이며 성능 개선 완료와 다르다. 최종 개선 완료는 실측으로 고른 조합의 정확성·성능·복구를 재검증하고 하네스를 갱신한 상태다.

## 구현 계획과 남은 검토 경계

job 최초 포함 총 5회, 재사용 매체·초기 예산, 첫 실험 규모·반복 수, Development 시간·인스턴스·추정 비용 한도, 85%/1초 메모리 중단과 10% 반복 악화 시 채택 보류를 확정했다. 공개 자료는 현재 후보의 정확성 확인과 고정 manifest가 필요하며 이를 기준으로 전체 요청량을 산출한다. review 승인·수동 재시도의 예산 경계와 브랜드 순차의 영속 제어는 제품 상태 전이에 영향을 주므로 해당 구현 전에 계약을 확정한다.

구체적 관측값·비용 산식·추가 제안은 [사전 조사와 조건 제안](../lookbook-import-performance-survey-2026-10-03.md)에 분리했다. 재시도 5분 제안은 사용자 의견으로 철회했다. 확정한 조건도 성능 실험 설계 기준이며 제품 기본값이나 배포·실험 실행 승인으로 취급하지 않는다.

[세부 구현 계획](../tasks/lookbook-import-performance/plan.md)은 파일별 변경 범위·의존성·phase 완료 기준·검증 방법을 담은 검토본이다. 이 문서는 코드 수정·배포·데이터 삭제를 승인한 문서가 아니다.
