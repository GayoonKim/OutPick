# ADR-021: 사용자 계정과 앱 내 공개 프로필을 분리한다

## 상태

accepted

## 결정

- `users/{uid}`는 현재 사용자만 읽는 비공개 계정 문서로 사용한다.
- `userPublicProfiles/{uid}`는 인증 사용자가 닉네임·아바타를 조회하는 앱 내 공개 문서로 사용한다.
- 이메일은 Firebase Auth를 단일 기준으로 삼고 Firestore에 복제하지 않는다.
- 관심 무드와 계정 상태는 비공개 계정에만 저장한다.
- 공개/비공개 문서의 생성·변경은 callable Functions가 검증하고 트랜잭션으로 수행한다.
- 닉네임 유일성은 서버 전용 hash index로 보장한다.
- iOS의 현재 세션, Chat, Lookbook 댓글 작성자, 사용자 상세는 공개 프로필 도메인인 `UserPublicProfile`을 직접 소비한다.
- avatar 제거는 공개 프로필의 두 Storage 경로를 명시적 null로 변경한 뒤 기존 객체를 삭제하며, 후속 삭제 실패 경로는 로컬에 보존해 재시도한다.

## 이유

- 채팅 참가자와 메시지·댓글 셀은 다른 사용자의 닉네임·아바타가 필요하지만 이메일·관심 무드·계정 상태는 필요하지 않다.
- 하나의 `users` 문서를 모든 인증 사용자에게 공개하면 기능에 필요 없는 개인정보까지 읽을 수 있다.
- 두 문서를 클라이언트가 독립적으로 쓰면 부분 성공과 닉네임 index 불일치가 생긴다.

## 트레이드오프

- 프로필 변경이 callable과 두 문서/인덱스를 거치므로 구현 파일이 늘어난다.
- 기존 단일 `UserProfile` 소비자를 공개 프로필 또는 현재 계정 경계로 나눠야 한다.
- 공개 프로필 cache invalidation을 별도로 관리해야 한다.

## 보류한 대안

- `users` 한 문서의 rules로 field-level read를 제한하는 방식은 Firestore 문서 일부만 숨길 수 없어 선택하지 않았다.
- 공개 문서를 클라이언트가 직접 쓰는 방식은 닉네임 충돌과 계정 삭제 정합성 때문에 선택하지 않았다.

## 재검토 조건

- 차단 사용자별 프로필 가림처럼 공개 프로필 read에 서버 필터가 필수가 될 때.
- 앱 외부에 공개되는 사용자 프로필 기능을 추가할 때.
- Firebase Auth 외 별도 identity provider가 이메일 기준 저장소가 될 때.
